## 2. 需求修订后的目标与边界

### 2.1 必须实现的目标

1. 保留现有外部 gRPC VMM 集成能力，包括外部连接、外部管理、已有项目层级语义、外部搜索、详情、写入、删除、健康检查和现有可用工作流。
2. 新增或改造内置原生 Rust Core 集成路径：Core 直接以内存对象和内部 Rust 接口运行，不再向外提供服务接口，也不通过外部 gRPC 作为内部调用前提。
3. 明确划分“内置原生 Rust 路径”和“外部 gRPC 路径”的共同层、独立层、能力差异和数据边界，禁止因为存在相似业务名就强行复用结构或行为。
4. 在 VulcanCode 宿主内注册一套固定、类型安全、可复用的 LLM、Embedding、Rerank 内部调用接口，复用当前资料库已经使用的内部 LLM/向量能力，供 Core 以及未来其他内置库共同使用。
5. 内置路径采用一级项目记忆模型：VulcanCode 项目对应一个 VMM 记忆项目；项目显示名称不参与绑定，创建/重新绑定时默认使用合法化后的项目 tag，绑定实际使用稳定 ID。
6. 记忆启用时补齐现有 VulcanCode 项目的未绑定关系；启用后新增 VulcanCode 项目时自动按照当前策略创建或绑定对应记忆项目。
7. 默认绑定策略为“绑定到固定项目”，固定项目的初始显示名称为 `default`，由 VulcanCode 创建内置数据库结构时直接保留项目 ID `1`，并受不可删除保护；它不是默认的“每个项目分离创建”。
8. 内置路径支持项目的“归属记忆项目”和“额外可连带查询项目”配置；查询关系按项目明确配置，不能把外部 VMM 的整体共享能力冒充成该能力。
9. 外部 gRPC VMM 支持前缀控制、项目自动组合或统一关联、项目级整体共享；外部路径不实现内置路径的逐项目选择性分组查询。
10. 新建 VulcanCode 项目后的提示必须反映真实绑定结果；名称变更不能破坏已有 ID 绑定。
11. 内置原生与外部 gRPC 是全局二选一；项目可以在当前后端内分别选择绑定策略，但不能按项目混用两个后端。

### 2.2 明确不在本方案中的事项

1. 不删除、关闭或隐式替换外部 gRPC VMM 功能。
2. 不把外部 gRPC 的 Team、Space、User 字段从外部协议或外部 DTO 中删除，以迁就内置一级项目模型。
3. 不为外部 VMM 虚构选择性项目组查询；外部只按其真实支持的默认空间、项目级共享或统一项目语义工作。
4. 不通过项目名称、tag、路径或拼接字符串作为唯一绑定身份。
5. 不因为修改 VulcanCode 项目名称、tag 或 VMM 记忆项目显示名称而自动重绑已有关系。
6. 不在记忆未启用时创建 VMM 记忆项目或发起绑定请求。
7. 不静默迁移、删除、合并或覆盖现有外部 VMM 数据。
8. 不以“尝试多个字段”“逐个猜测接口”“失败后换另一种后端”的方式掩盖协议和归属不确定性。
9. 不在本轮方案确认前迁移 Core 源码、修改数据库、调整配置、删除托管运行时或提交代码。

## 3. 统一术语和身份规则

| 术语 | 定义和权威字段 |
| --- | --- |
| VulcanCode 项目 | 工作区中的 `TaskProjectSummary` 项目；稳定身份是其现有 `id`，当前 ID 由项目 slug、路径哈希等规则生成，标题和路径不是绑定主键。 |
| 内置 VMM 记忆项目 | 原生 Core 使用的一级记忆项目；稳定身份是内置 VMM 项目 ID，系统固定项目的 ID 为 `1`，展示名称可修改。 |
| 外部 VMM 项目 | 远端 VMM 中的项目；VulcanCode 绑定只持久化稳定 `project_id`，Team/Space/Project 层级与名称在维护操作需要时通过远端项目读取。 |
| 绑定 | 一条持久化关系：`VulcanCodeProjectId -> VmmMemoryProjectId`，并记录后端类型、绑定模式、状态、版本和必要的展示缓存。 |
| 固定项目 | 全局配置指向的单个 VMM 记忆项目；保留项目 ID `1`，默认名称是 `default`。固定性由 ID `1` 和保护属性表达，不能依赖当前显示名称。 |
| 分离创建 | 为某个 VulcanCode 项目创建独立的 VMM 记忆项目；项目 tag 仅作为创建时的默认显示名称。 |
| 绑定已有项目 | 用户从已有 VMM 项目列表中选择一个稳定 ID，不在界面使用自由输入名称代替选择。 |
| 归属记忆项目 | 当前 VulcanCode 项目写入或主要归属的 VMM 记忆项目；必须通过绑定 ID 解析。 |
| 额外查询项目 | 当前 VulcanCode 项目检索时额外读取的其他 VMM 记忆项目；只建立显式的直接边，不默认传递到被关联项目的查询。 |
| 外部前缀 | 外部 gRPC 模式下用于生成远端项目定位的 Team/Space 或等价前缀配置，默认示例为 `vulcan/space`；它不是内置项目绑定主键。 |

### 3.1 身份不可混用规则

1. VulcanCode 项目 ID、内置 VMM 项目 ID、外部远端项目 ID 和外部路径必须分字段保存。
2. 名称可以作为 `display_name` 或创建默认值保存，但不能作为 `binding_id`、数据库主键或重绑依据。
3. 外部路径只使用并记录远端返回的稳定 `project_id` 作为项目绑定身份；`team_id`、`space_id`和规范路径在维护界面需要时根据该 ID向远端读取，不进入 PreCheck、PostAction 等热路径，也不能代替内置项目 ID。
4. 固定项目 ID `1` 被重命名后，仍受到不可删除保护；所有默认兜底绑定均指向 ID `1`，保护逻辑不得根据当前名称判断。
5. VulcanCode 项目改名或 tag 改动后，已有绑定不变；新建记忆项目时才读取新的 tag 作为初始名称。

## 4. 目标架构

目标结构如下，具体 crate 名称和模块名要在第 8 节的事实勘察门禁完成后冻结：

```text
VulcanCode Composition Root
├─ 统一宿主能力注册
│  ├─ Internal LLM Port
│  ├─ Internal Embedding Port
│  ├─ Internal Rerank Port
│  └─ 复用资料库现有的内部向量/VLDB能力
├─ 记忆业务语义层（只复用已验证的交集）
│  ├─ PreCheck / PostAction / ChatCompact
│  ├─ Profile
│  ├─ Search / Details / Write / Delete
│  ├─ 结果、诊断、取消和幂等语义
│  └─ 后端能力声明
├─ 内置原生 Rust 后端
│  ├─ VulcanMemoryMeshCore
│  ├─ 内部 HostEffect / StoragePort 适配器
│  ├─ VulcanCode 注册的 AI Port
│  ├─ 一级项目与直接查询关联
│  └─ 独立的内置记忆数据命名空间
├─ 外部 gRPC 后端
│  ├─ 现有 TonicVmmClient / gRPC 协议
│  ├─ 外部 User / Team / Space / Project 管理
│  ├─ 前缀或统一项目映射
│  ├─ 项目级整体共享
│  └─ 外部健康、管理 HTTP 和远端错误语义
└─ VulcanCode 项目生命周期编排
   ├─ 启用时全量对账
   ├─ 新建项目后绑定
   ├─ 绑定 UI 和重试
   └─ 按稳定 ID 维护关系
```

### 4.1 全局后端和过渡实现的区分

用户可见的 VMM 后端是全局二选一：内置原生 Rust Core 或外部 gRPC VMM。源码中当前存在宿主管理 `vmm-local` 子进程的路径，它只是要被替换的历史实现，不是第三种长期后端。

| 状态 | 连接形态 | 本方案处理方式 |
| --- | --- | --- |
| 内置原生 Rust Core | 进程内 Rust 类型和 trait 调用，不需要外部服务接口 | 目标内置后端，按本方案新建或改造。 |
| 当前宿主托管 VMM | VulcanCode 管理本地 `vmm-local` 子进程，源码中部分访问仍通过 `TonicVmmClient` | 作为迁移期间的现状单独盘点；原生路径完成后移除，不保留为第三种用户模式。 |
| 外部 gRPC VMM | 连接用户配置的远端或独立 VMM gRPC/管理服务 | 永久保留为独立外部后端，不随原生 Core 迁移删除。 |

不能使用 `managed_install_enabled` 等现有托管字段直接推断用户选择的后端。目标配置必须有一个全局后端模式；现有托管字段不再作为第三种模式暴露，也不触发旧内置数据迁移或自动清理。

### 4.2 复用和独立矩阵

| 领域 | 可以考虑复用的部分 | 必须独立的部分 | 冻结条件 |
| --- | --- | --- | --- |
| Core 业务语义 | PreCheck、PostAction、Profile、记忆 CRUD 的领域结果、保留策略、诊断状态 | 外部请求字段、传输错误、用户/团队/空间身份、远端分页和管理动作 | 逐操作比对命令、结果、生命周期和失败语义后才能共用。 |
| AI 调用 | 现有 `vulcan-ai-contract` 的结构化请求/响应校验和宿主 `ConfiguredInferenceService` 的能力 | 外部 VMM 自己的远端推理协议、远端模型路由和服务生命周期 | 只允许内置库通过统一内部 Port；不得让各库自行创建客户端。 |
| 项目模型 | VulcanCode 项目生命周期事件、显示名称、绑定状态展示 | 内置一级项目与外部 User/Team/Space/Project 四级/多级语义 | 任何共享 DTO 不能用可选字段掩盖两种模型差异。 |
| 绑定 | “已绑定/未绑定/失败/重试”等状态和幂等编排 | 内置稳定 ID 绑定、外部前缀路径、外部整体共享 | 分别保存后端类型和身份字段。 |
| 查询 | 统一的用户操作意图、检索结果展示和审计入口 | 内置显式多项目查询、外部默认空间整体共享 | 通过能力声明控制 UI 和请求，不做隐藏降级。 |
| 生命周期 | 启用、禁用、新增项目、重命名、归档等宿主事件 | 内置存储初始化、外部连接健康、现有托管子进程移除 | 每个后端有独立状态机和显式失败处理。 |
| 配置 | 启用状态、可见功能、诊断和状态投影的通用框架 | 内置绑定策略、外部前缀/空间/三节点、现有托管字段的退出边界 | 新 schema 版本和后端切换必须有明确版本与审计记录，不引入旧内置数据兼容迁移。 |

结论：全局只选择一个后端；共享的是经过验证的业务意图、结构化结果和宿主生命周期钩子；传输、存储、身份、作用域、项目绑定和能力限制必须保持独立。

## 5. 统一内部 AI 调用接口

### 5.1 设计目标

统一接口服务于所有内置 Rust 库，不是只为 VMM Core 临时包一层。当前 `knowledge_base_services.rs` 已通过 `ConfiguredInferenceService` 使用内部 LLM 和 Embedding 能力；本方案应从这条已存在的宿主能力链路整理统一 Port，禁止重新创建第二套 Provider。调用方只依赖固定的内部 Port；真正的模型客户端、路由、用量控制、并发调度和遥测仍由 VulcanCode 宿主注册和实现。

建议以 `vulcan-ai-contract` 已有的结构化契约为基础增加或整理一个内部调用 Port，名称暂不在方案阶段冻结。接口至少覆盖以下三类方法：

| 能力 | 依据当前契约的方向 | 约束 |
| --- | --- | --- |
| LLM | 以 `ResponsesExecutionRequest` 及其对应响应/校验类型为基础 | 必须有调用用途、模型/路由快照、超时、取消、请求身份和可观测性上下文。 |
| Embedding | 以现有 Embedding 请求、批量结果和 `EmbeddingSpaceFingerprint` 为基础 | 保持输入顺序、维度和空间指纹校验；不得把部分失败静默当成完整成功。 |
| Rerank | 以现有 `RerankRequest`、结果和候选顺序契约为基础 | 明确候选身份、排序分数、模型路由和结果校验；禁止无提示换用另一模型。 |

### 5.2 推荐接口边界

接口概念上应具备以下属性，实际类型签名需在事实勘察阶段依据现有异步、错误和取消模式冻结：

1. 内部 Port 只暴露结构化 Rust 请求、结构化 Rust 响应和显式错误，不把 JSON 字符串作为 Core 与宿主之间的协议。
2. Port 由 VulcanCode Composition Root 注册，以 `Arc` 或同等共享句柄注入 Core 和其他内置库；Core、VMM 库或未来库不能自行实例化 LLM、Embedding、Rerank 客户端。
3. 请求必须携带调用者、用途、请求 ID、截止时间/取消句柄、路由或配置快照以及必要的用量、追踪元数据。
4. 结果必须保留模型、路由、维度/空间指纹、候选身份和服务诊断等后续校验所需的信息。
5. Provider 不可用、模型不支持、超时、取消、限额、维度不匹配和响应校验失败必须分别显式返回；不能通过二次猜测、隐式备用模型或旧连接字段掩盖。
6. `ConfiguredInferenceService` 以及资料库当前使用的内部向量/VLDB Provider 作为宿主能力的适配实现，复用当前调度、合并、遥测、用量控制和向量存储注册；不能让 Core 直接依赖 Service Kernel 的具体实现而形成反向依赖，也不能再创建独立 Provider。
7. 外部 gRPC VMM 的远端调用保持自己的协议和路由。除非用户明确要求，不能把“外部 VMM 访问”偷偷注册为内置 Core 的 AI Port 实现。
8. Embedding/向量生成和向量库读写、检索、元数据索引是不同职责：前者纳入统一 AI Port，后者复用资料库已经使用的 VLDB Provider，并在需要时以独立的存储 Port 注入；不能用 Embedding Port 代替向量存储 Port。

### 5.3 依赖方向

```text
vulcan-ai-contract（结构化请求、响应、错误、内部 Port）
             ↑
     vulcan-service-kernel（ConfiguredInferenceService 适配实现）
             ↑
     Composition Root / Native Memory Runtime
             ↑
     VulcanMemoryMeshCore 与其他内置库
```

上图只是依赖方向建议。第 8 阶段必须检查当前 crate 依赖，避免为了放置 trait 形成 `vulcan-ai-contract -> service-kernel -> vulcan-ai-contract` 循环。

## 6. 项目绑定模型

### 6.1 内置绑定记录

概念模型至少包含如下信息，最终字段名、数据库位置和迁移版本由事实勘察阶段冻结：

| 字段类别 | 内容 | 权威性 |
| --- | --- | --- |
| 源项目 | `vulcan_project_id` | VulcanCode 项目稳定 ID，主关联键。 |
| 后端 | 全局 `integration_backend` 及配置版本快照 | 全局只能是内置原生或外部 gRPC 二选一；绑定记录可保存快照用于审计，但不能让项目混用后端。 |
| 目标项目 | `vmm_project_id` | 内置路径保存 VMM 稳定 ID；外部路径只保存远端 `project_id`。 |
| 外部自动创建默认值 | 固定前缀或用户指定的 Team/Space 名称 | 仅用于没有项目级配置时自动创建新的远端项目，不写入既有项目绑定，不代替稳定 ID。 |
| 绑定模式 | 固定、分离创建、绑定已有、统一项目等 | 记录当次决策，不依赖当前全局配置重新推断历史。 |
| 展示缓存 | 目标显示名称、路径等 | 仅用于 UI 显示；缓存过期不能触发重绑。 |
| 状态 | 已绑定、待处理、失败、已失联等 | 由后端操作结果驱动；失败后由项目设置显式重新绑定或创建并绑定，不能仅凭本地字段存在判断成功。 |
| 版本审计 | 创建时间、更新时间、操作 ID、错误摘要和配置版本 | 支持并发、重复提交、排障和显式迁移审计。 |

### 6.2 归属和额外查询

内置路径为每个 VulcanCode 项目解析出：

1. 一个归属记忆项目 ID，用于写入和主要召回。
2. 零个或多个显式额外查询记忆项目 ID，用于本次项目的附加召回。
3. 直接关系集合，不自动沿着 B 再去查询 B 所配置的 C；除非用户明确建立 A 到 C 的关系。
4. 同一目标 ID 去重、稳定排序和明确的权限/可见性检查。

示例：A 的归属是 A，并配置额外查询 B、C；召回 A 时读取 A+B+C。B 和 C 不会因为被 A 引用而自动读取 A，也不会自动继承 A 的额外关系。

### 6.3 默认固定项目

1. 默认全局绑定策略是“绑定到固定项目”。
2. 固定目标使用 VMM 项目 ID `1`，由 VulcanCode 初始化内置数据库结构时直接创建/保留，初始显示名称为 `default`，并将 ID `1`保存为全局兜底目标。
3. ID `1`的目标不可删除，只允许修改显示名称；删除校验使用稳定 ID和保护属性。
4. 固定目标改名不解除保护、不改变任何已有绑定；绑定永远指向 ID `1`，不指向名称 `default`。
5. 内置数据库的 schema/bootstrap 必须幂等地创建项目 ID `1`及其不可删除属性；不能用名称或临时 ID替代该要求。
6. ID `1`的删除保护必须在 VulcanCode 的 repository/service API 和数据库约束层生效，不能只依赖 UI 隐藏删除按钮；所有删除入口收到 ID `1`都必须显式拒绝并返回保护错误。
7. 固定目标在 schema/bootstrap 创建或校验失败时，启用流程必须显示失败并保持未完成状态，不能把项目标成已绑定。

### 6.4 绑定策略

后端模式是全局二选一；下表是当前选定后端内部的项目绑定策略，不代表项目可以选择不同后端：

| 策略 | 新项目默认行为 | 启用时未绑定项目行为 |
| --- | --- | --- |
| 绑定到固定项目 | 绑定到固定目标 ID `1`，初始显示名为 `default` | 每一行默认选择固定目标。 |
| 分离创建 | 以当前 VulcanCode 项目 tag 作为初始显示名称创建独立记忆项目 | 每一行默认选择创建绑定项目，创建名称预填项目 tag。 |
| 绑定已有项目 | 按配置的默认已有目标 ID 绑定 | 每一行从已存在的项目列表选择目标；没有目标时必须显式报错。 |

用户在启用对话框中可以逐行改变选择，允许一批项目混合使用不同绑定策略；但所有行必须使用当前全局后端。

新增 VulcanCode 项目默认不生成项目级绑定覆盖，而是继承当前全局绑定策略；只有用户在项目设置或启用列表中明确选择目标时，才形成项目级明确配置，并因此不再进入全局自动创建分支。

### 6.5 外部 gRPC 项目关联

外部路径单独保存：

1. 外部 gRPC 目标、凭据和管理地址。
2. 可配置的固定 Team/Space 前缀，默认示例为 `vulcan/space`；只有新增项目不存在项目级明确目标时才继承全局自动策略。全局策略为自动创建时，按配置的 Team/Space 名称和项目 tag 生成远端项目；有项目级配置时不进入该自动创建分支。
3. 用户可以指定项目所属空间；项目级明确指定的空间、项目和绑定关系不受后续全局默认前缀修改影响。
4. 支持创建并绑定自定义的 Team/Space/Project 三节点名称；创建完成后只把远端返回的 `project_id` 写入项目绑定。
5. 独立项目手动绑定已有外部项目时，不受默认前缀组合规则限制；可以绑定前缀之外的远端 Team/Space/Project，绑定只保存远端 `project_id`。
6. 支持可选的全局统一关联目标项目；全局策略设为统一关联时，新项目直接绑定该远端项目，不创建新的 Team/Space/Project；既有项目不因修改默认配置而自动迁移。
7. 外部 VMM 自身支持的查询级别/共享配置继续由 VMM 决定；VulcanCode 保存或传递外部配置，但不实现、管理或修改该查询级别。

外部项目关联必须记录远端 `project_id`。正常 PreCheck、PostAction、Search 等热路径直接使用该 ID；Team/Space/Project 层级解析、确保创建、名称维护、前缀变更和失联修复属于维护路径，只有在新增、绑定、显式刷新、改名或远端错误需要重新解析时调用管理接口。

外部路径不实现内置的“额外查询项目”关系，也不因保存了多个 Team/Space/Project ID就增加 VulcanCode 自己的分组召回逻辑。

## 7. 启用、创建、改名和恢复生命周期

### 7.1 禁用状态

1. 只创建或更新 VulcanCode 项目，不创建 VMM 记忆项目，不写入 VMM 绑定请求。
2. UI 不显示“已绑定”成功文案；可以显示“记忆未启用，因此尚未绑定”的明确状态。
3. 后台启动、刷新和项目读取不能因为发现缺失绑定就偷偷创建目标。
4. 重新启用时再执行完整对账和补齐。

### 7.2 从禁用切换为启用

执行顺序必须保持可恢复和可审计：

1. 校验当前全局二选一后端的配置以及所需 AI/连接能力。
2. 持久化启用配置，但把“配置已保存”和“项目绑定已完成”作为两个状态展示。
3. 如果当前是内置固定策略，先由数据库 schema/bootstrap 幂等确保固定目标 ID `1`存在并受保护，再读取其当前显示名称。
4. 枚举当前所有有效 VulcanCode 项目，使用稳定项目 ID 查找现有绑定。
5. 对每个缺失绑定的项目构造未绑定列表；已存在且有效的 ID 绑定不因名称变化进入未绑定列表。
6. 弹出绑定列表框，让用户确认每行的创建/固定/已有项目目标。
7. 以完整、带稳定 ID 的绑定决策提交幂等对账操作。
8. 每一行返回成功或失败状态；全部完成后才报告启用对账完成。
9. 失败项目保留“绑定失败”状态，不能把全局成功 toast 当作逐项目成功；用户可到项目设置中重新绑定，或创建新的记忆项目并绑定。

### 7.3 启用状态下新建 VulcanCode 项目

1. 先完成 VulcanCode 项目自身的持久化，取得稳定 `vulcan_project_id`。
2. 读取创建时的有效绑定策略快照。
3. 固定策略绑定固定目标 ID `1`；分离/自动创建策略仅在项目没有项目级明确目标时生效，并以合法化后的项目 tag 为初始名称创建新记忆项目；已有策略直接绑定配置的目标 ID。项目级配置优先，不再触发全局自动创建。
4. 绑定成功后持久化绑定记录和展示快照。
5. 绑定失败时保留 VulcanCode 项目，立即提示“绑定失败”；项目设置提供“重新绑定已有项目”和“创建并绑定”入口，不自动修改已有绑定，也不把失败伪装成后台已完成。
6. 项目创建接口返回结构化绑定结果，UI 不通过猜测配置或再次查询名称生成提示。

### 7.4 名称和 tag 变更

1. 修改 VMM 记忆项目显示名称只更新目标项目本身及必要的展示缓存，不更新任何绑定 ID。
2. 修改 VulcanCode 项目标题/tag 只影响 VulcanCode 显示以及未来“分离创建”时的默认名称，不改变已有目标 ID；创建或重新绑定时优先使用当前合法化后的 tag 作为初始显示名。
3. 当前没有 VulcanCode 项目目录迁移功能；项目目录调整通过删除旧项目并重新添加项目处理，重新添加后由用户在项目设置中手动绑定到目标 VMM 项目。
4. 如果用户明确发起“更换归属记忆项目”，这是独立内容迁移操作，必须显示影响范围、旧目标和新目标，不属于普通改名；迁移完成后源项目由用户手动清空或删除。

### 7.5 默认配置只作用于新增项目

1. 修改内置固定/分离/已有项目的默认配置，只影响之后新增的 VulcanCode 项目。
2. 修改外部 gRPC 固定前缀、默认空间、统一目标或自定义三节点默认值，只影响之后新增且没有项目级明确配置的项目。
3. 既有项目的绑定 ID、外部 `team_id`、`space_id`、`project_id` 和规范路径不因默认配置变化而自动修改。
4. 用户需要改变既有项目目标时，必须在项目设置中显式执行重新绑定或创建并绑定，并明确展示旧目标和新目标。

### 7.6 显式项目迁移

项目迁移是用户主动发起的独立操作，不由改名、改默认配置或普通重新绑定隐式触发：

1. 以源记忆项目 ID和目标记忆项目 ID执行，名称只用于展示确认。
2. 迁移是内容移动和归属关系改写，不是复制或插入：源项目的项目 session、session 关联记忆、向量节点和项目画像直接改归属到目标项目，不在目标创建第二份同源内容。
3. 迁移前必须先执行检测，不直接写入：读取目标 session 数量、源项目当前 session 数量、预计迁移后 session 数量，并列出待迁移条目摘要和必要记录信息；迁移成功后源项目应为空项目级容器。
4. 同时检测向量节点、项目画像条目和引用关系，预览目标已有数量、源待迁移数量、预计合并后数量以及 session 名称冲突数量。
5. 没有 session 名称冲突时，用户确认后才执行；有冲突时，确认按钮变为带圈感叹号的风险确认状态，并明确显示冲突条目数量和自动改名规则。
6. 冲突处理直接修改待迁移 session 的名称：目标已有相同名称时追加 `-1`，仍冲突则追加 `-2`，依次递增到不冲突后再迁移；不保留原 session 作为独立副本，也不再把原 session 作为后续会话匹配入口，但必须同步修正迁移所需的记忆来源/引用关系。
7. 项目画像按画像自身稳定 ID直接改写所属项目关系并移动到目标，不插入副本、不产生画像冲突、不执行画像改名；个人画像属于个人级数据，不参与项目迁移。
8. 向量迁移只修改向量数据库中的节点 ID、归属项目引用和必要索引元数据，不重新生成 Embedding，不重新计算向量，不调用模型重建向量。
9. 迁移完成后源项目只保留项目容器和必要的空项目元数据；用户可以随后手动删除该空项目。迁移操作本身不删除源项目容器。
10. 迁移失败必须保留可恢复状态，不能出现 session 已迁移但向量静默丢失，或向量已迁移但 SQLite 仍指向旧项目的无记录状态。
11. 内置路径由 VulcanCode/Core 实现上述检测、确认、session 改名、画像改绑和节点 ID迁移语义；外部 gRPC 若需要迁移，只适配并调用外部 VMM 已有迁移 API，不在 VulcanCode 重新实现外部迁移。

预检结果至少按以下维度展示，不允许只显示一个“将迁移 N 条”的笼统提示：

| 项目 | 目标当前数量 | 源项目待迁移数量 | 重复/冲突数量 | 预计迁移后数量 |
| --- | ---: | ---: | ---: | ---: |
| session | 当前目标 session 数 | 源项目 session 数 | 按最终冲突键统计 | 目标现有与实际新增之和 |
| 记忆/向量节点 | 当前目标条目/节点数 | 源项目待迁移条目/节点数 | 节点或引用冲突数 | 改写归属后的条目/节点数 |
| 项目画像 | 当前目标画像条目数 | 源项目画像条目数 | 按稳定 ID 校验关联，不以画像重复插入 | 改写归属后的画像条目数 |

预检还要提供可展开的待迁移记录摘要、冲突记录摘要、源/目标稳定 ID、当前版本或内容指纹以及预期改名结果。预检只读，不产生目标条目、绑定变化或向量写入；用户确认时必须携带预检版本/指纹和幂等操作 ID，若源或目标在预检后发生变化则要求重新预检。相同幂等操作 ID的重复提交只能返回既有结果，不能再次追加 session 后缀或重复改写向量节点。成功迁移后再次预检源项目时，源项目级待迁移数量应为零。

内置迁移执行顺序固定为“锁定源/目标版本 → 建立条目与 ID 映射 → 更新 SQLite 归属和引用 → 更新 VLDB 节点 ID/归属元数据 → 对账提交 → 写入迁移结果”；任一步失败都必须由账本记录可恢复状态并支持重试/补偿。外部模式不在本地展开这套执行算法，只透传外部 gRPC VMM 已定义的预检、确认、冲突和结果字段；外部 API 未提供的字段不能由 VulcanCode 猜测生成。

### 7.7 归档、恢复和清空删除

1. 归档 VulcanCode 项目默认只改变项目生命周期，不删除 VMM 记忆数据和绑定。
2. 恢复时优先按原 VulcanCode 项目 ID恢复原绑定；不存在或失效时显示待处理，不按名称自动寻找替代项目。
3. 用户可以显式对 VMM 项目执行清空性删除；清空等同于把现有 VMM 项目重置为“新创建的空项目”，删除全部项目级信息，包括项目画像、项目 session、项目 session 关联的记忆、向量节点、索引和项目级关联，不要求删除 VMM 项目本身，也不需要执行项目绑定检测。
4. 清空后 VMM 项目容器、稳定项目 ID和其有效绑定仍然存在，只是项目内容为空；个人级画像不属于项目级信息，不纳入本次清空，由 VMM 自身能力维护。
5. 删除 VMM 项目是不同于清空内容的高风险操作；执行删除前必须按稳定 VMM 项目 ID检测绑定的 VulcanCode 项目。
6. 如果存在绑定项目，先列出具体项目，并明确提示删除后这些项目的 VMM 功能将被关闭，用户需要进入项目设置重新配置；只有用户在风险确认后才执行 VMM 项目删除。
7. VMM 项目删除完成后，相关 VulcanCode 项目保留，但其 VMM 状态变为未配置/已关闭；删除 VulcanCode 项目与删除 VMM 项目仍是两个明确操作。
8. 固定项目 ID `1`禁止删除，只允许改名；普通 VMM 项目删除不删除个人画像，个人画像仍使用 VMM 自身能力维护。

## 8. 启用时绑定列表框方案

### 8.1 触发条件

只在以下条件同时成立时弹出：

1. 记忆后端从未启用切换到启用，或执行明确的“重新对账”。
2. 发现至少一个有效 VulcanCode 项目没有有效绑定记录。
3. 后端具备列举/创建/绑定所需能力。

若没有未绑定项目，不弹出逐项目列表，只显示对账结果。

### 8.2 行模型和默认显示

每行代表一个 VulcanCode 项目，至少显示：

| 列 | 内容 |
| --- | --- |
| VulcanCode 项目 | 项目显示名称/tag；内部绑定行键是稳定 VulcanCode 项目 ID。 |
| 绑定方式 | 下拉选择“绑定到固定项目”“创建绑定项目”“绑定已有项目”；实际选项可按当前后端能力裁剪。 |
| 目标项目 | 随绑定方式变化：固定模式显示固定目标名称；创建模式显示可编辑的创建初始名称；已有模式显示已有目标下拉框。 |
| 状态 | 待确认、处理中、已绑定、失败。 |
| 错误/说明 | 显示后端返回的可行动错误，不把失败折叠成空白。 |

默认固定策略下的示例应为：

```text
projecta  | 绑定到固定项目 | default  | 待确认
projectb  | 绑定到固定项目 | default  | 待确认
```

只有当用户把某一行改成“创建绑定项目”时，才显示类似：

```text
projecta  | 创建绑定项目 | projecta  | 待确认
```

把某行改成“绑定已有项目”后，右侧必须是已有 VMM 项目下拉框，不能继续使用输入框，也不能根据输入名称再次猜测项目。

固定模式右侧显示 ID `1`当前的实际名称；即使用户把 `default` 改成其他名称，行的绑定目标仍是 ID `1`。

### 8.3 交互和校验

1. 内置固定目标应已由 VulcanCode schema/bootstrap 创建并受保护；启用时校验 ID `1`及其保护属性，若 invariant 失效则明确报错并阻止提交，不通过名称猜测或临时创建替代。
2. 已有项目下拉选项至少带稳定 ID、展示名称和必要路径；同名项目必须仍可区分。
3. 创建模式的名称可作为初始显示名编辑，但提交后绑定使用返回的稳定 ID。
4. 每行可以单独切换绑定方式，允许一批项目混合使用不同绑定策略；但所有行必须使用当前全局后端。
5. 提交后保留每行状态；失败行不自动重放，用户可在项目设置中显式重新绑定或创建并绑定。
6. 关闭对话框不等于取消启用配置；界面必须明确显示“启用已保存但仍有项目绑定失败”，并提供进入项目设置处理的入口。
7. 外部 gRPC 模式使用固定前缀、项目级空间/三节点绑定和 VMM 自身查询配置，不展示内置路径的选择性项目关联控件。

## 9. 新建项目后的提示和返回契约

### 9.1 服务返回

当前 `addProjectFromPath` 主要返回 `WorkbenchSnapshot | null`，而绑定结果是另一条事实链。建议把项目创建接口扩展为结构化结果，至少包含：

1. 新建或恢复的 VulcanCode 项目稳定 ID。
2. 工作区快照或现有刷新结果。
3. `memory_enabled` 和实际后端模式。
4. 绑定状态：未启用、已绑定、失败。
5. 实际绑定目标稳定 ID和当前展示名称（UI 需要时提供名称；ID仍由后端作为权威）。
6. 是否创建了新的 VMM 项目。
7. 可展示的错误、项目设置处理入口和操作 ID。

具体放在 RPC、service 层还是 `WorkbenchSnapshot` 的附属字段，要依据当前 API 兼容约束选择；不能只改 toast 而不让服务返回真实绑定结果。

### 9.2 用户提示

启用且绑定成功时，创建完成提示应增加：

```text
项目创建成功，已绑定到 VMM 记忆项目「{实际显示名称}」
```

其中 `{实际显示名称}` 来自绑定结果的目标项目，不从当前 tag 或配置名称重新拼接。

不同状态应使用不同文案：

| 状态 | 文案方向 |
| --- | --- |
| 记忆未启用 | 保留普通项目创建成功提示，不声称已绑定。 |
| 已绑定 | 项目创建成功，并显示实际 VMM 记忆项目名称。 |
| 绑定失败 | 明确“项目已创建，但 VMM 记忆绑定失败”，引导进入项目设置重新绑定或创建并绑定。 |
| 目标被重新命名 | 显示新的名称，但不改变原有绑定。 |

只有服务确认绑定成功后才能显示“已绑定”；配置保存成功、请求已发送或本地任务入队都不能直接当作绑定成功。

## 10. 内置原生 Rust Core 集成方案

### 10.0 内置实现形态冻结

1. `vulcan-memory-mesh-core` 只作为经过审查的 Rust 源码来源，不作为 VulcanCode 运行时依赖，也不继续以通用 Core 产品的方式维护跨项目兼容层。
2. 将实际需要的 contracts、domain、engine、storage 语义和测试按依赖清单直接复制到 VulcanCode 的独立 crate 或 `vulcan-memorymesh-*` 模块中，复制后由 VulcanCode 独立演进。
3. 复制前删除或排除 FFI、Go SDK、C ABI、gRPC Server、网络服务、外部进程启动器、跨语言 DTO 和不再使用的通用兼容代码；不得为了保持旧形态而保留无调用方的适配层。
4. VulcanCode 负责项目、绑定、SQLite、LanceDB、账本、迁移、清空、删除、恢复和运行时编排；不通过修改 Core 源仓库来补充这些宿主功能。

### 10.1 Core 迁移原则

1. 第 0 阶段重新检查 `vulcan-memory-mesh-core` 当前源码和版本，形成复制白名单、删除清单、来源提交和许可证记录；不以工作区依赖方式替代直接复制。
2. 只复制内置运行所需的 Core contracts、domain、engine、storage 语义和测试；FFI、C ABI、Go SDK、gRPC Server、外部进程启动器、网络服务和 UI 不进入内置代码。
3. 保留 Core 的 `CoreCommand`、`HostEffect`、`StorageQuery`、`Mutation`、`StoragePort` 和错误/诊断契约的语义，不把宿主项目字段直接塞进 Core 内部领域类型。
4. 内置适配器负责把 VulcanCode 的稳定项目 ID、内置 VMM 项目 ID、归属和直接查询集合转换为 Core 所需的 `ScopeAccess` 或等价作用域结构。
5. Core 只看内置后端提供的内部 Host/Storage/AI Port；它不监听端口、不生成外部接口、不创建网络客户端、不创建独立 LLM/Embedding/Rerank 客户端。
6. Core 记忆数据与 VulcanCode 代码语义索引数据保持逻辑和物理命名空间隔离；可以共享宿主注册的 AI/向量基础设施，但不能让代码索引或记忆数据互相污染。

### 10.2 内置存储

内置路径使用 VulcanCode 宿主管理的现有 VLDB 能力，不再为 VMM Core 创建第二套向量 Provider 或独立存储服务。记忆数据根目录固定在 `.vulcan/code/vmm` 下，并与代码语义数据分离；SQLite 和 LanceDB 必须是两个独立的存储对象/目录，不能共用文件、表或清理入口。

1. VulcanCode 负责创建 SQLite/LanceDB 数据结构；schema/bootstrap 必须幂等创建内置固定项目 ID `1`及其不可删除保护属性。SQLite 负责项目/绑定元数据、Core 状态、mutation 账本、pending/recovery、retention、outbox 和可恢复性所需的权威记录。
2. LanceDB 负责记忆向量等派生检索数据，由宿主 VLDB 适配器管理；向量索引不能反过来成为绑定关系的唯一权威。
3. 记忆路径复用资料库已经使用的内部 LLM、Embedding/向量 Provider；只改变数据命名空间和数据根，不复制 Provider 实例。
4. Core `StoragePort` 的查询和 mutation 通过内置存储适配器实现；Core 不直接打开 VulcanCode 数据库文件，也不直接创建 LanceDB 客户端。
5. 记忆向量、代码语义向量、配置状态和 outbox 使用独立表/表前缀/目录或等价隔离边界，并提供单独备份、迁移、清理和一致性检查。
6. 多项目直接查询时，SQLite 中的绑定和关联记录先解析为稳定 ID集合，再由 VLDB 读取向量；不能通过向量库中的名称字段反推项目关系。

内置路径不使用外部 VMM 的远端存储作为本地记忆存储，也不把外部 gRPC 的项目数据迁移到 `.vulcan/code/vmm`。

### 10.3 内置会话工作流

PreCheck、PostAction、Profile、ChatCompact、搜索/详情/写入/删除等操作应通过内置后端适配器接入现有 Agent 生命周期。适配器必须明确：

1. 当前会话、项目和请求的稳定身份来源。
2. PreCheck 召回时如何合并归属项目和额外查询项目。
3. PostAction 和直接写入始终使用 session 唯一绑定的归属项目；额外查询项目只扩展召回，不扩展写入地址。
4. Profile、pending/recovery、retention 和 outbox 的内置持久化归属。
5. 取消、超时、宿主重启、未确认 mutation 以及 session/向量迁移中断的恢复方式。
6. 同一操作在内置路径和外部路径返回的共同结果如何投影；不同错误必须保留后端来源和阶段。

## 11. 外部 gRPC VMM 保留与隔离方案

### 11.1 必须保留的现有能力

以下模块只能在确认外部 gRPC 调用方和回归测试完整保留后重构，不能因为内置 Core 不再需要就删除：

1. `crates/vulcan-vmm/src/transport.rs` 中的 `TonicVmmClient` 和 `VmmClient` 外部实现。
2. `crates/vulcan-vmm/src/protocol/` 下的 memory、management、profile、握手和相关生成协议。
3. 外部管理 HTTP 代理、远端健康检查、外部凭据、超时和连接诊断。
4. Service Runtime 中已有的外部 Health、User、Project、Profile、Search、Details、Write、Delete 等 workbench actions。
5. Agent Runtime 的外部 VMM hooks 和 native tools 的外部实现分支。
6. 外部项目的 Team/Space/Project 层级、远端项目 ID和 VMM 自身查询/共享语义。

### 11.2 外部项目策略

1. 在外部模式下提供可配置的固定前缀，默认示例为 `vulcan/space`；项目 tag 用于生成 Project 节点的默认显示名和规范路径，不直接使用可能不合法的项目名称。
2. 用户可以指定项目所属空间；项目级明确指定的空间和项目绑定独立于全局固定前缀，后续修改默认前缀不影响该项目。
3. 支持创建并绑定自定义 Team/Space/Project 三节点名称，保存远端返回的 `team_id`、`space_id`、`project_id` 和规范路径。
4. 独立项目手动绑定已有外部项目时，不受默认前缀组合规则限制；可以绑定前缀之外的远端 Team/Space/Project，绑定只保存远端 `project_id`。
5. 新增 VulcanCode 项目不存在项目级明确目标时，继承全局项目策略：若全局设置为绑定统一外部 VMM 项目，则直接绑定该目标；若全局设置为自动创建，则按已配置的 Team/Space 名称（默认前缀为 `vulcan/space`）和项目 tag 自动创建并绑定远端 Project。项目级明确配置不会进入全局自动创建分支。
6. 全局策略只影响新增且没有项目级明确配置的项目；已有项目的外部关联不因修改统一目标、前缀或空间而自动迁移。
7. 外部 VMM 的查询级别、默认空间项目记忆共享等能力由 VMM 自身配置决定；一旦外部 VMM 的共享配置开启，按其默认空间共享语义生效，不能在 VulcanCode 中改造成可选择的项目分组。VulcanCode 负责保存必要配置和项目维护，不实现或修改该查询策略。
8. 外部模式的 UI/API 不提供内置路径的“额外查询项目”选择器；只提供外部前缀、项目空间/三节点维护和 VMM 已有配置的必要入口。
9. 外部项目迁移只调用并展示外部 VMM 自带迁移 API 的请求、预检、确认、成功和失败结果；VulcanCode 不重算数量、不处理冲突改名、不操作向量、不执行回滚或补偿，也不把外部失败转换为内置结果。

外部项目维护时，如果已取得 `project_id`，应保存对应的 `team_id`、`space_id`和规范路径。正常 PreCheck、PostAction、Search 等热路径优先使用已解析的 `user_id`、`project_id`；Team/Space/Project 解析、确保创建、名称维护、前缀变更和失联修复属于维护路径，不应在每次 PreCheck 等调用中重新查询。

### 11.3 外部和内置错误边界

外部连接失败、远端认证失败、远端不存在、协议版本不匹配、管理操作失败和内置存储失败必须分别归类。不能因为内置 Core 可用就把外部错误自动切换成内置结果，也不能因为外部可用就把内置失败隐藏起来。

## 13. 配置和迁移规则

### 13.1 新配置概念

全局配置至少需要表达：

1. 是否启用记忆。
2. 内置原生 Rust 或外部 gRPC 的全局后端模式，严格二选一；不再提供当前托管 `vmm-local` 模式。
3. 默认绑定策略，默认值为固定目标。
4. 内置固定目标 ID `1`及展示名称缓存、保护属性。
5. 是否允许/如何创建内置分离项目。
6. 外部 gRPC 目标、默认固定前缀、项目级空间/三节点覆盖、统一目标和管理凭据。
7. AI Port 的用途路由和能力要求，而不是每个库的独立模型客户端配置。

项目级配置至少需要表达：

1. 该 VulcanCode 项目的归属记忆项目绑定 ID或覆盖策略。
2. 额外查询项目的稳定 ID集合（仅内置模式）。
3. 项目是否继承全局绑定策略，或者有明确的项目级覆盖。
4. 外部模式下可选的 Team/Space/Project 三节点 ID、规范路径和名称缓存。
5. 后端能力不支持某项配置时的显式不可用状态。

### 13.2 现有配置边界

当前配置存在 `user_id`、`project_id`、managed install、外部管理地址、作用域和功能开关等字段。新方案按全局后端二选一分别解释；当前未发布内置集成按新安装场景实现，不承担旧内置数据兼容迁移，外部配置则必须继续可用：

1. 外部 gRPC 模式继续保留并使用其需要的数值 User/Project 语义。
2. 内置原生模式不使用外部 User/Team/Space 层级来模拟一级项目。
3. VulcanCode 按新安装场景设计，不提供当前旧内置 VMM 数据的兼容迁移或自动清理逻辑；原生方案直接使用新数据结构并移除 `vmm-local` 运行时配置。
4. 配置保存不能因为缺少新字段就自动覆盖用户已有外部配置；外部配置只在全局选择外部模式时加载和展示。
5. 全局后端切换只改变当前使用后端；另一后端的既有配置、绑定和数据保留，不迁移、不删除，切换回来可以继续复用。
6. 新内置配置保存固定 ID `1`和其他绑定策略；已有绑定不自动变化，默认配置只作用于新增项目，既有项目须在项目设置中显式重新绑定或创建并绑定。
7. 配置中保存目标稳定 ID、外部 `user_id`/`team_id`/`space_id`/`project_id`和展示缓存；缓存变更不触发配置重绑。
8. 外部默认前缀、默认空间和统一目标的变更只影响新增且没有项目级明确配置的项目；已绑定项目的三节点 ID和规范路径保持不变。

### 13.3 能力声明

后端必须返回能力矩阵，例如：

| 能力 | 内置原生 | 外部 gRPC |
| --- | --- | --- |
| 一级 VMM 项目 | 支持 | 不适用，保留远端原协议层级 |
| 固定目标绑定 | ID `1`，支持 | 按外部固定前缀/统一目标语义实现 |
| 分离创建 | 支持，默认名称使用 tag | 按固定前缀或项目级自定义三节点实现 |
| 选择已有项目 | 支持 | 按外部远端 `project_id`及 Team/Space 解析结果实现 |
| 逐项目额外查询 | 支持 | 不由 VulcanCode 管理 |
| 默认空间整体共享/查询级别 | 不采用该外部语义 | 由 VMM 自身配置决定，VulcanCode 不修改 |
| Team/Space/User 管理 | 内置不需要 | 保留现有支持 |
| 外部 healthz/管理 HTTP | 不需要 | 保留 |

UI 和服务 API 先读取全局后端模式，只展示当前所选后端的配置和项目能力：选择内置时不展示外部前缀、Team/Space/Project、外部管理地址等专有配置；选择外部时不展示内置固定 ID `1`、额外查询项目、`.vulcan/code/vmm` 存储等专有配置。未选择的后端信息不以禁用控件形式混在当前界面中，也不能把“不支持”隐式降级为另一种语义。

## 18. 用户已确认的决策与仍需确认的问题

### 18.1 已确认决策

以下决策以用户本轮回复为准，已经写入前文目标、配置、生命周期、UI、测试和验收条款：

1. 内置原生 Rust 与外部 gRPC 是全局二选一，不能按项目混用两个后端。
2. 当前托管的 `vmm-local` 移除，不作为第三种长期运行模式。
3. 外部 gRPC 增加可配置固定前缀，默认示例为 `vulcan/space`；支持指定空间，支持创建自定义 Team/Space/Project 三节点并绑定；项目级明确空间不受后续全局默认前缀修改影响。
4. 任何显示名称修改都不改变 ID 绑定。
5. 绑定失败直接提示失败；项目保留，用户可在项目设置中重新绑定已有项目，或创建新的记忆项目并绑定。
6. 内置固定项目使用 ID `1`，默认显示名称为 `default`；ID `1`不可删除，只允许改名，默认/兜底绑定指向 ID `1`而不是名称；ID `1`由 VulcanCode 创建数据结构时直接保留并由宿主阻止删除。
7. 创建记忆项目的默认名称使用项目 tag，不使用可能不合法的项目名称；tag 的外部合法化复用当前项目规范化规则，tag 只用于默认名、显示和重新绑定时的建议，不能作为唯一绑定身份。
8. 启用绑定列表允许逐项目分别设置绑定方式，可以混合使用固定项目、创建项目和绑定已有项目。
9. 外部已取得 `project_id` 时只记录该稳定 ID；`team_id`、`space_id`和必要路径在新增、绑定、改名、刷新或失联修复等维护路径按需通过远端 API 获取，PreCheck 等热路径不执行层级解析。
10. “归属项目 + 额外查询项目”只属于内置原生路径；外部查询级别和共享由 VMM 自身配置决定，VulcanCode 不管理、不修改，也不显示该配置。
11. 内置 LLM、Embedding/向量能力复用资料库已有的内部 Provider，并以统一内部接口整理；不创建重复 Provider。
12. 内置记忆使用 VulcanCode 宿主管理的 VLDB，目录放在 `.vulcan/code/vmm` 下，SQLite 与 LanceDB 分离，并与代码语义数据隔离。
13. 修改默认配置不修改既有项目，只影响新增项目；既有外部项目和既有绑定不自动迁移。
14. 全局后端切换保留另一后端的既有配置、绑定和数据，不迁移、不删除，切换回来可以直接复用。
15. 当前按新安装场景实现；VulcanCode 不处理旧内置 VMM 数据的兼容迁移、启动探测或自动清理，用户自行处理既有环境数据。
16. 用户可以显式执行项目迁移，将 A 项目的 session、session 关联记忆、向量和项目画像直接改绑到 B；迁移前必须预检并确认，session 冲突时显示重复数量、使用带圈感叹号的风险确认，并按 `-1`、`-2` 规则直接改名；不保留原 session 作为后续会话匹配入口，个人画像不参与项目迁移。
17. 项目迁移不是复制或插入；完成后 A 只剩空项目级容器，用户可以随后手动删除。向量迁移只调整向量数据库节点 ID/归属关系，不重建向量；项目画像按自身 ID改写所属项目关系，不产生画像冲突。
18. 清空 VMM 项目等同重置为新创建的空项目，删除全部项目级信息，包括项目画像、项目 session、session 关联记忆、向量、索引和项目级关联，但保留项目容器、ID和有效绑定；删除 VMM 项目则必须先列出绑定的 VulcanCode 项目，确认后关闭这些项目的 VMM 状态并执行删除；固定 ID `1`不可删除。
19. PostAction 和直接写入只使用 session 的唯一绑定项目；额外查询项目只扩展召回，不扩展写入地址。
20. 外部配置只在全局选择外部 VMM 时显示；内置专有配置只在选择内置时显示，两个后端的专有配置不混在同一界面。
21. 项目当前没有目录迁移功能；用户通过删除并重新添加项目处理目录变化，再手动重新绑定 VMM 项目。
22. 外部项目迁移不在 VulcanCode 内重实现，只适配并调用外部 gRPC VMM 已有迁移 API，由外部 VMM 管理迁移细节。
23. `vmm-local` 的移除范围是 VulcanCode 的托管模式、启动器、监控器、托管配置和专属资源；暂不删除 `VulcanMemoryMesh` 仓库中的 `cmd/vmm-local` 源码。
24. 外部 gRPC 迁移的成功、失败、预检和确认均以外部 VMM 返回为准；VulcanCode 不承担外部迁移业务结果的判断、修正、补偿或回滚责任。

## 20. 执行变更总结（实现完成后填写）

### 20.1 核心修复与调整概述

本次实现完成了 VMM 双后端的实质分离。Native 后端直接把经过来源固定的 VMM Core 领域代码纳入
VulcanCode Rust 工作区，通过进程内 HostEffect 驱动和宿主 VLDB 数据面运行；ExternalGrpc 后端继续
使用 `TonicVmmClient`、远端管理 HTTP 与既有 User/Team/Space/Project 协议。历史托管
`vmm-local` 子进程、安装器、监控器、打包脚本和专属配置已移除，不再作为第三种运行模式。

统一宿主 AI 能力已由 `vulcan-ai-contract::HostAiPort` 冻结并在 service-kernel 中通过
`ConfiguredInferenceHostAiPort` 落地。Native VMM 的 LLM、Embedding、Rerank Effect 以及知识库
原有 LLM/Embedding 调用均复用同一个 `ConfiguredInferenceService` 实例；知识库的 prompt、Schema、
索引 generation、向量表和混合检索没有被替换。VCE 属于并行任务，本任务只验证其共享 HostAI 契约
消费边界，没有修改 VCE 领域实现。

Native 项目模型已实现稳定数字 ID、固定项目 ID `1`、按 ID 绑定、唯一写入归属与直接附加查询关系；
启用对账、默认固定绑定、按 tag 自动创建、绑定已有项目、新建 VulcanCode 项目后的真实结果提示、
项目设置重绑、迁移预检/冲突改名、清空与删除保护均已接通。ExternalGrpc 支持默认
`vulcan/space` 前缀、显式三节点或已有远端项目绑定，并只保存远端稳定 `project_id`；其迁移及查询
级别仍完全由远端 VMM 管理。

Native 数据面固定使用 VulcanCode 宿主管理的 VLDB，落在 `.vulcan/code/vmm/sqlite/vmm.sqlite3`
和 `.vulcan/code/vmm/lancedb`。SQLite 保存关系状态、Core 快照、绑定与恢复账本，LanceDB 保存向量；
项目迁移复用原向量值并改写归属，不重新生成 Embedding。跨 SQLite/LanceDB 的变更使用持久账本恢复，
PostAction 分析使用耐久队列恢复。
