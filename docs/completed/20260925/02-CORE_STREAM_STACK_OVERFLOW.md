# Core 会话执行启动栈溢出修复

状态：已完成代码修复、定向回归、真实调试核心重建与持续健康验证。

## 目标与证据

用户报告编译后载入即闪退，桌面提示核心尚未就绪。Windows 两次应用崩溃记录均为栈溢出 `0xc00000fd`，进程 34260 的已有转储证明核心已经运行约十秒后，在会话执行准备链的栈探测处崩溃。

实际链路：服务登记闸门 → 会话流任务 → 运行时流 → 运行时启动 → 执行准备。多个大型异步状态机的轮询栈帧叠加，未观察到递归循环；界面连接错误是崩溃后的表现。

## 决策与执行步骤

1. 使用现有本地崩溃转储及匹配符号定位，不重复启动崩溃服务，不读取或上传用户会话正文。
2. 在已确认的大型 Future、Stream 嵌套边界使用堆存储，缩小调用方状态机和轮询临时值；不提高全局线程栈，不启用脱离原任务生命周期的准备任务。
3. 移除仅在诊断开关开启时改变调度语义的实验分支，保留有价值的时序日志。
4. 添加独立子进程中的固定小栈回归，先证明旧实现失败，再验证修复后返回原有明确准备错误，且未发送供应商请求。
5. 检查取消、登记闸门和事件顺序；完成定向测试及 Core 构建。使用已授权重启入口恢复核心并核对健康身份。
6. 记录变更、测试事实和边界，独立中文提交。

## 验收标准

- 固定小栈上的真实执行准备不再终止进程。
- 默认诊断关闭和打开使用同一条任务生命周期；等待和取消关系不改变。
- 编译后的 Core 可以稳定运行，桌面重连不再因本次栈溢出失败。
- 不包含并行会话的供应商配置和其他界面修改。

## 执行决策补充

1. 原实现的独立子进程回归在固定一兆字节线程栈上返回 `0xc00000fd`；不安装供应商运行时，不访问用户会话。
2. 首轮装箱后准备失败路径通过。将相同回归扩展到已准备驱动后，发现事件处理仍有栈压力；第二份本地转储定位到增量事件处理及大型事件的迭代搬移。
3. 因而不仅装箱等待中的异步状态，也在供应商循环内部装箱 `yield` 事件，并在生成器轮询返回后还原原事件接口。这样缩小循环的临时栈空间，保持所有公开事件类型、顺序、所有权和取消关系。
4. 不使用独立调度任务分摊栈：脱离父任务的准备执行会使停止和取消关系更复杂。不提高工作线程栈：那会增加全局资源占用，并掩盖状态机继续膨胀的问题。
5. 验证在独立目标目录进行，并行界面会话仍可使用默认目标目录；实际核心重建时尊重其编译锁，不终止其他会话的编译进程。
6. 内部事件产出增加一次短期堆分配，换取嵌套轮询的栈空间；在生成器返回后即还原事件并释放该分配。既有文本合并节奏不变，不宣称本任务完成性能基准测试。

## 执行变更总结

### 一、核心修复与调整概述

- 根据 Windows 已有转储确认核心进程发生栈溢出，桌面连接提示是核心退出后的次生表现。
- 运行时流、供应商驱动、准备及引导等待边界改用堆存储；供应商循环内部产出事件也使用堆存储，再还原既有对外事件接口。
- 登记启动闸门持有装箱后的任务，保持先登记后运行和统一中止归属。
- 删除诊断开关控制的独立调度实验分支和仅打印大小的诊断测试，保留固定小栈行为回归。
