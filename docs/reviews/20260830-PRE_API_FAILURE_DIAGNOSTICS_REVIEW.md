# 手动模型切换、零调用执行失败与原始错误丢失复核

## 结论

用户补充的控制台日志已把最初的通用故障定位为请求配置错位：会话选择已经提升为 DeepSeek，
但请求仍使用旧的 OpenCode Go。不是用户不允许切换，也不是供应商拒绝了请求。
上一轮恢复确实补齐了旧回合，但没有解决新请求使用旧选择的问题；本轮沿模型选择、准备许可、
控制器及错误展示链路修正根因。未对真实供应商发起调用，未替换运行中的桌面程序。

## 已确认的代码缺陷

### 模型选择的持久化权威与请求构建脱节

选择器写入 V1 `pending_request`，而主会话请求构建读取旧的 `active_provider_id` 镜像。
随后 `prepare_physical_api_durable` 无条件提升 pending，再让旧请求与新 active 比较，必然不一致。
普通消息提交携带的模型选择也只更新镜像，未同步到同一份 V1 请求配置。

修复后，普通提交把模型选择写入既有 V1 配置接口；首次分发、目标续跑、队列续跑和中途切换
从同一配置快照取路由及控制项。实际模型变更仍由既有提升入口产生一次结构化记录，首次选择
不产生切换记录；不要求新请求沿用旧供应商或模型。

如果选择器写入晚于请求构建，唯一 writer 在提升前返回明确的重新准备结果，不修改事件或分配
API。原有路由重建流程读取最新配置后继续同一逻辑回合，保留请求尝试编号。控制器不把该结果
标为失败，遥测也不制造已发送请求。原本仅作用于工作区镜像的两段旧提升函数已删除。

复核同时发现思考档位存在两个已有编码来源：设置端使用 `off`、`x-high`，API 事实使用空值、
`xhigh`。比较时只规范这两组有源码依据的等价编码；新 API 的高强度键统一为 `x-high`。
不改写历史，不放宽供应商、账号、模型或物理 API 终态的一致性检查。

### 原始错误在收尾过程中丢失

运行时通过 `ExecutionRunReport.error` 携带真实错误。`handle_finished_stream_event` 把报告交给
仅内存投影后，无条件使用 `stream_finished_without_v1_api_terminal` 作为 V1 错误正文。
因此配置、请求准备、编解码或其他 API 前错误最终变成同一个编号。

修复采用既有 `DisplayNoteEvent.redacted_detail` 保存生产端已安全处理的原始错误，
稳定 `reason_code` 仍保留用于分类与旧异常恢复。错误和回合闭合仍由唯一 writer 原子提交。
预检查、准备、压缩、模型切换、Hook 关联及启动失败分支有原始错误时也通过同一接口传递。
只有没有原始错误的流耗尽等边界继续使用固定诊断编号。

控制台同步记录已取得所有权的真实失败及实际请求次数；即使后续落盘失败，也能保留诊断线索。
已有 API 终态回执、进程中断续跑、幂等闭合、旧回合恢复规则均未放宽。

### 前端合成了没有证据的派发信息

分支展示在没有 `apiStats` 时原来走“不是 prepared 就是 dispatched”的分支，
并伪造 `provider_id: unknown` 和空模型字段。这不代表请求真正发给了供应商。

修复后：缺少 API 事实时派发状态为 `unknown`，不输出不存在的供应商或模型字段；
原始错误已是现有公共契约结构时直接使用同一解析器，不再次包裹或覆盖原始阶段、路由和派发状态。
