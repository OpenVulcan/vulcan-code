## 拆分决策与充分性

### 为什么需要拆分

传输、投影解释器、媒体生命周期和纯解析算法存在不同的状态与依赖边界；集中在一个文件使这些边界与对应测试难以核查。按现有职责移动实现，不引入核心库、不改变协议、不新增架构层级或兼容兜底。

### 第一阶段已确定的归属

| 产物 | 职责 | 保留边界 |
| --- | --- | --- |
| `execution/framing.rs` | 有界 SSE、JSONL、NDJSON、完整 JSON 增量分帧 | 内部缓冲、分隔与编码校验不暴露；仅父执行模块可用解析器入口及返回帧 |
| `execution/usage.rs` | Profile 用量抽取、累加器去重和响应开始前的有界暂存 | HTTP/WebSocket 共用；门控内部状态私有 |
| 上述模块的 `tests.rs` | 分别迁移原 4 个分帧测试、5 个用量门控与抽取测试 | 保留函数名、测试属性、原始断言、输入及字节串 |

### 不需要拆分及原因

- 解析器自身的字段、缓冲算法、分隔符识别和 UTF-8/JSON 校验属于一个闭合职责，不再按函数大小切碎。
- 用量事件门控与抽取均服务于同一个流生命周期；暂存上限留在所属模块，不能移到通用常量仓。
- 客户端共享状态与构造关系保留单一权威；后续可以按职责拆实现块，不改变共享实例。
- 跨职责端到端回归留在适合其链路的位置，不能为私有函数测试额外扩大公开接口。

### 当前拆分是否足够

尚不足。第一阶段仅处理流分帧和用量事件；其余职责待逐段读取、调用追踪后再确定具体产物，不能以剩余行数作为唯一决策依据。
