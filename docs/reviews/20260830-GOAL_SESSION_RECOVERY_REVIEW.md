# 目标恢复与会话草稿阻塞根因复核

## 已确认的问题

代码基线为 `9c048bc4`。本次开始时工作树干净。用户会话 `c28d5af1-5d89-4eac-bbfb-bc2e9369c3e5` 的真实持久化文件只读检查结果：

1. 第 96 回合已在 seq 267/268 写入结束边界及统计，但 seq 269/270 的目标编辑事件仍错误归属该回合。严格重建因此拒绝加载。当前目标编辑方法已有“不使用已结束回合”的修改，但旧数据尚未恢复，通用追加入口也缺少同样的准入约束。
2. 第 105 回合因目标恢复而开启；没有 `api_started`，随后记录 `goal_blocked` 和 `stream_finished_without_v1_api_terminal`，却没有回合结束边界。现有失败处理只释放运行流 owner，未闭合逻辑回合；只修复第 96 回合后仍可能不能提交新消息。
3. 草稿 RPC 会先加载完整运行时，以上异常会阻止草稿读取。前端只显示统一 toast，并保持加载锁，没有重试入口；切换会话时还可能把加载过程中的空草稿交给保存逻辑。
4. `goal_status` 未进入分支转录的 notice 类型分支，回退为普通 Markdown；其正文直接来自 `reason_code`，因此出现裸 `goal_resumed`。规范视图和分支视图需要共用状态提示组件。

## 修复边界

- 写入端：通用追加必须指向当前开放回合；暂存入口拒绝已结束回合和更早回合，错误在分配 seq 和修改状态前返回。
- 失败终结：没有活动 API 时，错误与回合闭合在同一文档修订内提交；重复处理不追加重复错误或终态。
- 恢复端：严格加载器保持原校验；单独的运行时入口只允许纠正活动尾段内已证实的 `goal_state`/`goal_saved` 成对错误归属。事件正文和序号不变，修订递增；未知损坏或封口段损坏不放行。
- 发布顺序：纠正候选通过全部严格校验，再投影遗留 API 前失败回合，并由唯一 writer 原子 flush；成功后才向注册表发布 owner。重建失败或写入失败不发布半成品。
- 前端：目标事件共用带图标、边框的标记提示卡；草稿错误保留具体原因及重试入口，未加载成功的临时空态不能回写。

### 复核中收敛的边界

- 保留物理 API 已中断后的 Continue 能力：重复流终结不能把已有中断 API 的回合误当作 API 前失败结束。
- 已结束回合之后的系统错误采用会话作用域，重复结算保持幂等；恢复候选遇到不可表示的修订号直接报错，不溢出。
- 自动恢复只处理已证实的活动尾段事件对，仍拒绝重复边界、错序统计及未知损坏。物理持久化失败时原 metadata 和活动银行文件保持不变，可再次加载恢复。
- 真实文件只保存了 API 前失败的通用终态标识，没有原始供应商错误细节；不能据此断言当时网络或供应商发生了什么。本次确定并修复的是错误事件归属、遗留开放回合和草稿恢复阻塞。
