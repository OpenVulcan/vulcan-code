### 已修复：授权撤销与目标接纳竞态

### 已修复：失败问答无法收敛

发现投递错误按文本分类并直接记为失败，可能覆盖实际上已接纳的目标；目标未接纳而来源已失败时，撤销仍索取不存在的目标结算，导致历史编辑永久等待。采用双方门内的目标缺席证明，仅对停止、授权撤销和绑定失效等确定性拒绝记为失败；暂时性错误留给出站箱。等待失败立即返回，撤销只在来源侧结算，启动恢复也能终结撤销授权后的滞留意图。提交：`9006cc92`。原生协作端口十四项与封存事件恢复用例通过。

### 已修复：方向引导在原回合闭合时悬空

目标在方向消息接纳后可能先停止或关闭原业务回合，未应用方向缺少终态效果，后续也不会再进入原回合的供应商边界。选择在原回合闭合的原子事务中写入精确失败效果，使成功回合与停止回合都不会留下无法应用的方向。提交：`95c4f69e`。领域测试与服务定向测试通过。

### 已修复：应用前失败未回到来源

目标已有 `Failed` 效果但没有来源接纳与目标确认链，双方历史保护会永久等待。选择让失败效果生成 `terminal = null` 的可靠结果，复用目标记录、来源接纳、目标确认和冷恢复链；模型投影使用独立 `task_delivery_failed` 类型，界面显示为任务消息失败。这样保留既有幂等和双方回执，同时不虚构业务回合终态、最终 Assistant 或问题答案。跨项目授权撤销不阻止原请求方取得自己已发送消息的失败分类；成功业务正文仍按当前授权校验。领域全部四百六十二项、AI 协议六十一项、服务任务消息十一项、前端卡片十四项与类型检查通过。独立提交以 Git 历史为准。

### 已修复：目标停止后滞留的已接纳任务消息

发现目标在繁忙期间已接纳 `task_start` 或 `task_steer`，随后用户停止，可能再无供应商边界触发应用或失败；来源一直等待结果。先考虑在结果修复入口于目标规范生命周期门内重读停止状态并生成失败，但停止与后续修复之间允许恢复运行插入，不能保证“停止取消此前已接纳工作”。因此改为在领域停止操作的同一原子修订中为未应用消息写入 `TargetStopped` 效果；结果修复入口仍负责归档等已停止状态的可靠收敛和结果回传。停止服务在可靠停止操作后触发一次修复，启动索引会选出任一无效果的入站任务消息。领域全部四百六十三项和服务协作一百四十项通过。旧断言原本期待唤醒时额外增加修订，现已改为验证停止后唤醒不再写入。本项独立提交以 Git 历史为准。

### 已修复：提问已接纳后撤权导致双侧悬空

跨项目临时提问在目标已接纳、尚未进入供应商上下文时，来源撤销 `Ask` 授权，目标投影原先直接报错。来源出站恢复只处理“目标未接纳”的拒收，对已接纳的目标既不记失败也不回传；提问和历史保护因此长期悬空。决定沿用通知投影的双侧规范生命周期锁：撤权后先在目标写入 `AuthorizationRevoked` 失败，再将准确目标修订和事件序列回传来源；如果两次写入之间中断，来源出站箱从目标失败操作日志恢复，目标失败不再索取不可成立的问题结算。这样避免把未经授权的正文投给模型，也避免按错误字符串推断失败。两项真实服务定向用例已通过，分别覆盖正常撤权投影和目标已落盘但来源确认丢失；本项单独提交。

### 已修复：撤权失败回执对原提问方不可见

上一修复让失败事实可靠落盘，但模型端 `wait_question` 在读取失败状态前仍按已撤销的 `Ask` 授权拒绝整个快照，原提问方无法获知失败并决定撤销。决定只对已证明为原来源参与者、问题无答案且来源投递已失败的快照放行；目标方及未失败正文继续实时校验授权。撤权后等待返回 `failed` 与明确失败原因的服务用例通过；本项独立提交。

### 已修复：答案已结算后撤权导致未交付状态永久滞留

跨项目答案已由目标可靠提交到来源，随后原授权的 `Reply` 动作在来源下一次供应商边界前撤销。原投影直接报错，答案始终是 `undelivered`，来源历史编辑保护持续等待，而 `wait_question` 也因撤权拒绝整个快照。决定保留已结算答案作为审计事实，新增独立答案交付 `failed` 终态与稳定失败原因；来源在规范生命周期锁内确认当前仍未交付后写入失败事件，模型端只可由原提问方查看不含答案正文的失败元数据。撤权后不能通过重新授权把失败答案再投影，避免失败终态被倒退。真实服务用例验证跨项目提问、答案结算、授权撤销、模型投影、等待结果脱敏、双方编辑保护和磁盘重载；领域全部四百六十三项通过。此项独立提交。

### 已修复：任务结果接收后撤权阻断主会话

目标结果已经由原请求者可靠接收，但原授权在下一次模型请求前撤销时，结果投影一直报错，主会话连无关工作也不能推进。决定在请求者规范生命周期锁内冻结披露决策：仍获授权则投影完整结果；撤权则只投影 `task_result_unavailable`，包含原投递身份与撤权原因，不含结果正文。完整结果仍保留在此前已授权的可靠接纳记录中，重新授权不会改变已冻结的投影。为避免把“已完成结果不可披露”误判为“任务应用前失败”，此类回执独立于 `task_delivery_failed`。持久投影及驻留事件均按冻结决策验证，WebUI 显示明确状态。真实服务用例、AI 信封测试、领域回归、前端卡片测试及类型检查验证完成后独立提交。

### 已修复：任务结果接收前撤权造成双方回执滞留

目标已生成完整结果、原请求者尚未接收时撤销跨项目授权，原回传入口反复拒绝接收，来源等待结果，目标等待回执。不能在撤权后直接复制目标最终正文到来源，也不能把已完成业务伪称为应用前失败。现在在双方规范生命周期门内冻结接纳披露状态：目标保留完整结果；来源保存同一结果身份和终态坐标，但清除最终正文。目标确认时将自己的完整结果按该决策派生并与来源回执比较；来源投影时即使重新授权也只能投递结果不可用状态。已接纳完整结果后的撤权则保留原接纳事实，只在模型边界脱敏。真实存储用例覆盖完成的最终正文、撤权、来源与目标落盘、双方历史保护、模型信封；原有任务结果回归四项、领域四百六十三项和前端卡片十四项通过。此项单独提交。

### 本轮已排除的疑点

检查了已应用 `TaskSteer` 在无 `Claimed` 效果时的冷恢复入口。启动恢复会对所有开放根业务回合调用主执行恢复，且嵌入子会话也通过所属根恢复；该路径不依赖入站任务消息扫描条件，故未发现“方向已投影但重启不恢复主回合”的缺口。

### 已修复：跨项目读取在解析与实际读取之间撤权

`read_session` 原先在目标解析阶段检查 `Read` 授权，之后直接从目标定位器读取事件。用户撤权可以插入这两步之间，使实际读取发生在授权失效之后。采用来源规范生命周期锁包围授权复核和整段事件读取；同项目读取仍走原有边界，不增加跨项目限制。回归用例明确先取得目标定位器，再撤权，验证旧定位器不能用于实际读取；原有同项目和跨项目读取定向用例通过。本项独立提交，连续无问题审核仍从零开始。
