# 代理生命周期与可靠恢复设计

实施补充（D313—D314，替代 D310 在运行时内等待的接线方式）：原生宿主立即接收后台维护请求，在规范生命周期门下核对精确档案，并先登记可取消服务工作任务再开始等待原成功发布。共享辅助互斥覆盖等待；停止通过取消通知退出工作 Future，服务监督流程仍负责排空已准入准备与阻塞写入、发现实际转交的维护所有者、可靠结算及返回清理回执。等待者或停止调用者取消不能撤掉监督流程。原执行停止标记拒绝同次迟到调度，不阻止新的业务执行。子树选择来自真实注册表父边，包含已完成业务的维护，不依赖仅运行中业务的面板缓存；应用关闭先关闭新登记，再排空维护后刷写文档。

维护摘要使用原生本地压缩的同一规范来源、物理接收器及节点提交路径，但凭独立维护记录授权，不借用已释放的业务租约或监听器；无归属的委派及工具生命周期事件拒绝并释放失败屏障。成功摘要先提交精确节点，再独立结算维护。原生后台结果不再回写常驻历史，避免辅助互斥释放后覆盖新答疑或新业务；可靠文档保持唯一上下文权威。远端摘要仍待可靠适配，不静默切换协议。维护完整定向组 10 项通过，包含真实工作任务，但完整维护摘要服务链验收仍待补齐。

实施补充（D315）：批量停止先通知全部已登记维护，再等待各自可靠结算；某个维护保存失败不能导致其他已选答疑任务继续运行。子面板停止和 MainAndSubagents 先停止业务，再按真实注册表树清理维护与仅答疑任务，包含已完成业务下的嵌套答疑。面板关闭先清理再归档；直接运行时 close_agent 在全部任务事务锁内检查辅助预留，未结时明确拒绝，不能归档后仍写入。普通工作错误及工作 Future 异常均进入维护结算；未启动任务的启动门失败移除登记，有维护所有者却丢失原档案时明确报错而非当成无任务。运行时任务模块 171 项、服务准备 3 项通过，最终生产检查 0 错误、11 项既有警告；完整关闭/卸载与摘要验收仍需后续核对。

实施补充（D312）：维护清理必须先停止并等待所属异步执行退出，再调用精确结算。结算排空请求准备与规范生命周期写入；结算门随实际阻塞发布工作持有，不随异步等待者提前取消而释放。校验维护 ID、起始记录、历史代次、子档案和原业务回合，关闭维护 API 与维护回合分别取得可靠发布；失败保留不可分发的辅助所有者，重试发布剩余脏修订。已有维护终态不可因迟到停止或失败回调而改写；完全释放后只允许同一可靠终态的幂等重放。此函数不改变子业务结果、运行控制、Goal 或 TTL。该结算原语已编码，实际后台任务登记与停止入口尚待接通，不能将原语验证作为全链验收。

实施补充（D310—D311）：原生后台维护先等原执行的可靠父回流发布确认，确认来自真实父监听器在规范结果提交后的缓存；不消费父反馈，不以运行时 Completed 或界面 ACK 替代。先订阅再检查，取消及替换门控会唤醒旧等待者。服务维护准入使用规范生命周期锁、独立辅助预留及新推理关闭门控；Core 创建记录后，实际阻塞写入器负责将互斥交给服务，即使等待者取消或刷盘失败也保留。发布失败时不可分发，精确维护终态完整落盘后才释放。等待原成功发布与持有维护互斥是两个阶段，不把等待算作业务重新运行；服务准入模块已编码，实际压缩流、停止入口及自动失败清理接线仍未完成。

实施补充（D307—D309）：Core 维护准入先捕获已可靠发布的精确原成功证明，包括子档案、原执行、原业务回合、修订、上下文指针与原最终正文；在实际准入前重新核验。不接受停止、归档、活动 API、开放回合、排队输入或已被后继业务取代的来源。开始分配独立维护执行及辅助回合，并原子写入仅宿主日志与元数据；不得重开原业务或借用答疑。维护回合仅允许压缩 API，不消耗业务 TTL，不选择业务后继，不产生父业务回流。成功终态必须带该维护实际提交的精确压缩节点回执，失败或停止没有成功节点回执。冷加载校验日志、元数据、回合闭合及成功节点边界；未完成维护在进程中断投影中独立失败结算，既不恢复业务，也不允许继承业务继续路径。活动 API 失败、永久诊断及辅助闭合共享一个修订，诊断关联实际 API；同一失败在实时与冷加载之后重放均不重复追加。

以上是领域层实现；进程辅助互斥与服务所有者的转交、父子成功发布同步、运行中停止及取消清理仍需接入。序列化领域重载测试不等于真实文件写入、服务调度或供应商验收。

实施补充（D305—D306）：活动业务压缩与完成后维护由各自调用点显式选择，不允许宿主在活动租约查找失败后猜测维护分支。完成后的调用继续使用终态快照与最终配置；此运行时结果尚不等于服务端业务终态已经持久发布。辅助准入表由答疑及维护共享，维护要求原常驻业务成功完成且执行 ID 精确匹配，新业务准备、活动运行及其他辅助所有者均与其互斥。守卫不修改业务状态、结果或父完成计数，并保留不可变用途；答疑所有者接收守卫时必须验证 Question，用途不可互换。冷态维护不能凭已丢失的常驻身份启动，后续可靠恢复须从领域记录另行取得权威。

完成后维护后续服务接线要求：使用独立维护执行及辅助回合，不能重开原业务回合，也不能制造问题记录；原成功结果与父回流保持不变。准入需确认原成功闭合已经可靠发布，在规范生命周期门内复查代次、子档案、原执行和运行控制；不能仅凭已经发送终态事件认为父子写入结束。执行所有者须跨取消及失败发布保留，只有维护自身可靠结算后释放互斥；重启只终结维护记录，不恢复已完成业务。对应领域原语已在 D307—D309 实现，服务所有者及完整接线仍未完成。

实施补充（D304）：运行中原生子压缩通过显式宿主端口交接原任务、执行身份及已解析模型依赖。宿主在规范生命周期门内验证活动租约、持久档案、历史代次和开放业务回合，真实来源冻结后再确认其原执行归属；最终节点提交在同一文档修改中重新验证。返回快照来自已提交文档的普通规范投影。运行时的控制准备不读取驻留历史；普通执行准备仍转换自己的执行快照。无根展示的宿主事件保留原屏障，转交该执行原有监听器。完成后维护需要独立准入，远端压缩需要可靠回执适配；当前两者尚未完成，不能以活动租约规则冒充维护授权，也不能静默改用本地协议。

实施补充（D301—D303）：摘要保留工具目录时仍强制拒绝全部工具执行，父请求的选择性规则不能放宽内部用途。模型声明工具的物理终态先准入可靠拒绝链，全部工具终结且 API 关闭后才由最后屏障拒绝压缩；不启动下一模型请求，也不关闭业务回合。冻结来源额外绑定同次可靠捕获的开放回合与子业务执行 ID，即使历史文本相同，执行更替也会拒绝旧来源。该绑定用于物理准备和重捕获，不能替代尚待接入的子宿主入口、运行租约以及最终节点提交检查。

实施补充（D300）：物理响应可产生空助手事件，终态按已分配的语义 seq 封口，不能以正文非空代替事件存在判断。另已追踪到 `TaskSessionConfigResolver::resolve_runtime_policy`：配置和调用覆盖之后，`enforce_task_session_projection_boundary` 强制关闭 Hook、VMM、召回、写回及数据库投影；该策略经真实启动请求冻结到子执行档案。子压缩必须遵守这一已解析策略，不能照搬根压缩的 VMM 发布入口，亦不在本任务中擅自开启这些能力。

实施补充（D299）：根展示身份成为压缩流接收器的可选输入，可靠准备、语义、工具与 API 终态仍由精确 V1 接收器处理。无根展示的非工具宿主事件连同原屏障交回所属监听器，不因缺少展示而静默确认生命周期变化。无效非空摘要保留真实物理正文供 Provider 来源归属，关闭物理请求后向生产者返回明确错误，禁止提交压缩节点且不关闭业务回合。该共用接收器不是子压缩准入或节点提交的替代品；尚未接线部分继续按 D298 推进。

实施补充（D298）：子任务完成后的压缩输入来自实际终态结果，而不是启动快照；仅结果已提交且未启动排队后继时调度。此处不改变原任务身份或业务闭合规则。持久化压缩仍须建立独立宿主入口，运行中和结束后维护分别证明准入，不能以已释放的运行时租约代替领域状态，不能将压缩伪装为自然空闲答疑。实际接线和验证范围见工作报告。

## 一、必须独立的四类状态

| 状态域 | 负责的事实 | 不能替代它的信号 |
| --- | --- | --- |
| 业务任务与逻辑 turn | 任务归属、未结子任务、正常完成、失败或取消。 | 模型输出了一段 final、单次 API 已结束、UI Ready。 |
| 物理执行 | 是否正在调用模型、执行工具、等待或暂停；执行目的和代际。 | 历史任务完成记录、backend 曾经存在。 |
| 问答事务 | 问题正文、双方、答案、撤销、是否已交给提问者。 | 任务最终 Assistant、普通 mailbox Message。 |
| 投递进度 | 来源已记录、目标已接纳、进入请求、回执及通知修订。 | 单独的“发送成功”布尔值。 |

子代理会话可以复用；父 turn 只等待归属于当前任务的子任务，不等待所有历史子面板关闭。

## 二、问题权威与投递状态

问题业务状态至少区分：`pending`、`answered`、`cancelled`。答案交付另有消费修订，不能因回答尚未交给提问者就误判其已经取得答案。首版不设置隐式问题 TTL；等待超时不会产生 `expired`。未来若增加截止时间，必须另有明确产品契约。

投递状态独立记录已记录、已接纳、已投影及失败原因。目标停止导致投递失败不是一个伪造答案；提问者仍可查询并显式撤销。来源准入时直接拒收则没有已接纳的问题义务。

| 动作 | 前置条件 | 权威变化 | 后续效果 |
| --- | --- | --- | --- |
| 发送 | 来源真实、目标及权限有效、操作未重复。 | 来源记录问题和待投递事项。 | 返回问题 ID；异步接纳和唤醒目标。 |
| 目标接纳 | 目标状态允许，任务/turn 绑定有效。 | 目标保存投递记录及待处理关联。 | 下一合法边界投影问题。 |
| 回答 | 调用者是收件者，问题未结算。 | 来源问题记录提交答案、回答操作身份和修订。 | 回答方得到提交回执；向提问者交付答案。 |
| 撤销 | 调用者是提问者或授权用户动作，问题仍 pending。 | 提交撤销和原因。 | 通知接收方，停止该问题义务。 |
| 回答与撤销竞争 | 同一问题的权威写入串行化。 | 先提交的结算生效。 | 后到操作返回既有状态；不覆盖答案、不复活问题。 |
| 答案交付 | 问题已 answered，原问题的来源身份仍合法。 | 记录答案修订与具体交付位置。 | 有显式等待时使其返回；业务已结束则保留晚到协作记录，不复活旧任务。 |
| 等待超时 | 超时时间到达且无可交付事件。 | 无问题业务状态变化。 | 返回 pending 快照和修订。 |

“已取得答案”的工程含义是：一个合法执行上下文包含该答案或对应真实等待工具结果。仅写入数据库、显示到 UI 或排入待投递列表不算模型取得；业务已经结束时可以继续保留待交付状态，不要求恢复原 final。宿主不声称能证明模型主观理解。

等待路径以实际完成的 `wait_question` ToolCall 为凭据：同一调用的参数必须指向该问题，成功输出必须包含相同双方和不可变答案。工具结果和首次答案交付在来源文档内原子发布；失败、超时或入站问题提醒不能充当该答案的交付。已经投影过的答案再次被查询不重复改变交付状态。

晚到答案允许交付到来源的后续真实执行，问题的原始任务和 turn 关联保持不变；没有活动执行时保留待交付。业务 turn 收尾只结束其回合内答疑尝试，未回答的问题保持可查询、可迟到结算，不因此阻止业务完成。重载必须按事件顺序应用结算后发生的嵌套交付变化，不能用交付前快照与当前状态直接比较。

## 三、持久化组织

### 3.1 唯一权威

本方案选用**来源会话拥有操作和问题权威记录，目标会话拥有接纳与投影记录**的组织方式。复用 V1 事件事实和可靠发布机制，不另造一份具有独立答案真相的进程内 QuestionRuntime。

来源记录至少包含操作/问题身份、双方会话、真实任务/turn 关联、正文或受控内容引用、授权关联、创建修订、结算及答案。目标记录只声明已接纳哪一来源事实、绑定哪个执行目的、投影到哪次请求以及处理进度；答案权威仍在来源。

新增协作控制事件必须允许在没有活动 Provider API 时提交。它们引用真实源任务，不伪造新用户 turn、不回写已经完成的工具结果。现有 `SessionMutationAdmission` 是否足够、需要新增哪种控制面准入，必须在 P00 沿真实写入链确定。

跨项目授权由宿主用户操作产生。其权威存储与现有用户/项目授权记录对齐；如果需要新增持久记录，须明确版本及撤销语义，不依赖问题正文自述授权。

### 3.2 不假定跨文档事务

来源和目标的 V1 文档分别可靠提交，不在两个文档上声称一次原子写入。使用以下可恢复流程：

1. 来源一次可靠修改写入问题及待投递事项，稳定操作身份在副作用前已经确定。
2. 返回的是“宿主已记录”回执；目标已消费仍是独立状态。
3. 投递者读取来源权威，检查权限和目标状态，按 `delivery_id` 在目标可靠接纳。
4. 目标回执写回来源投递进度；若此步丢失，重放会得到原接纳记录，不新建问题或执行。
5. 回答先在来源提交唯一答案，再返回回答工具回执和安排答案交付；目标侧的已处理标记可以根据该权威修复。
6. 撤销也先结算来源，再向目标传播；目标对迟到投递及回答重新核对源问题状态。

问题与通知不进入业务正常完成门。来源答复已经提交、目标结算尚未更新时，通过权威查询修复投递记录；不能猜测答案已经被模型取得，也不能因此阻塞双方业务完成。未结事务继续可查，并用于删除或历史替换保护。

来源暂不可读取或可靠提交失败时返回明确可恢复错误，不在目标单独提交一个“成功答案”作为备用真相。

**来源归档与删除不能破坏这一权威。** 归档只是退出普通目录展示，已接纳问题仍能通过受控的宿主入口提交答案、撤销和查询；归档本身不授权自动启动来源模型。存在未结问题、未完成交付或尚未收敛的跨会话回执时，拒绝直接物理删除来源文档，并返回具体阻塞关联。先经显式取消/结算处理依赖，再按删除契约移除；不能把删除失败隐藏为回答成功，也不能另存一份未声明的正文副本充当备用权威。删除后的必要终态标记和迟到操作如何获得明确失效状态，须在 P00 与现有删除存储规范一起冻结。

### 3.3 索引、尾段与压缩

V1 `SessionDocument` 有事件流、修订、封口分片和活动尾段；只重放活动尾段不足以恢复发生在旧分片的未结问题。新增结构必须具备经过版本和修订校验的活跃协作摘要，或能精确读取所需事件区间。

待投递、未结问题、尚未交付答案、活跃子任务绑定及必要授权均不可因压缩而消失。摘要保存状态恢复所需的类型化事实和原始证据指针，不依赖模型生成的自然语言摘要。

查询索引是加速器，不是第二份权威。索引可按会话修订增量重建；启动时先恢复调度必需的未结事项，不为一次等待扫描所有完整历史。缺少一致性证据时明确报待恢复，不用空索引推定没有问题或子任务。

## 四、幂等、并发与锁

- `operation_id` 在宿主接纳真实工具调用时确定并持久绑定。同一工具调用重试用同一标识；模型另发一个调用是新操作，不能只按相同正文去重。
- 同键同语义返回原回执；同键不同目标、正文或任务关联报冲突。
- 问题结算、目标接纳和任务完成分别由各自权威写入门串行化；锁内做状态检查与提交，锁外做通知、恢复、Provider 调用及等待。
- 同一会话内的一次复合提交只推进一次文档修订：信封与投影凭据、工具结果与答案消费、业务闭合与答疑尝试结束、根输入与 Running、业务完成与 NaturallyIdle 必须共享发布修订。草稿失败整体丢弃；嵌套草稿继承外层预留修订，所有变化事件合并进同一回执。记录内部的目标修订必须直接使用该预留值，不能在提交后仅改文档计数器。
- 未发布草稿不能发出写入候选或确认持久化；服务句柄继续严格检查“已改变则恰好一个修订，未改变则零修订”，不放宽门禁以掩盖复合操作错误。
- 不持有父会话锁等待子文档锁、又让子会话持锁等待父文档。跨文档流程用稳定身份及分阶段提交，不把远程回答塞进锁内回调。
- 模型请求的投影游标与等待工具的交付声明须可恢复；若等待调用已经消失，答案仍可查询并在下一合法请求交付，不能永久锁在旧等待者名下。
- 多等待者共享持久状态，各自保存游标；一个等待者取走 mailbox 通知不能使其他等待者丢失问题。
- 答案通过等待工具或 User 事件的新投递只选择一个途径。已交付答案允许主动再查；不承诺网络或模型侧恰好读到一次。

## 五、正常完成门

主 turn 正常完成必须在同一权威结算中满足：

1. 当前物理 API/工具组满足原有完成结构要求。
2. 属于该任务的子任务预留、启动中、运行中和等待后代任务已结算；待回流结果已处理。
3. 当前任务的业务启动/引导输入已按已有任务链处理。

问题、通知和未交付答案不构成上述完成前置条件。需要答案的代理主动调用等待；不调用等待即可继续并结束任务。已结束任务的晚到答案保留原 `question_id` 与原来源身份，以独立协作事件保存展示，不将旧任务恢复为运行中。单向通知没有问题状态或回复义务。

子任务预留也要进入父级权威记录，再启动执行，防止“检查时还没运行、父已完成、随后子才启动”的窗口。启动失败必须结算预留，不能留下永久等待。

仅检查运行时活动表不够：子进程退出或应用重启会丢失进程表。完成判定依赖可恢复的任务归属和终态事实，并与实际执行所有者对齐。

模型在所属子任务仍运行时提前输出 final，保存输出但不发布逻辑任务成功完成；宿主保持该任务关联，不得先生成终态 SubagentReturn 再撤回。仅有未答问题或通知时不阻止 final。

这是对当前分散完成判断的统一要求：`complete_successful_turn` 对待回流记录的保护、服务层 `AwaitingSubagents`、Hook turn 和最终界面事件必须收敛为同一结算结论。当前代码尚未提供这一统一保证。

## 六、运行目的与停止

| 运行目的或状态 | 接纳与恢复 | 本次执行结束后的行为 |
| --- | --- | --- |
| 正常任务执行 | 启动、方向引导、临时问题各按类型接纳。 | 满足统一完成门才产生任务终态。 |
| 原 turn 内协作答疑 | 主处于等待，或 MainOnly 后收到有效子问题；保留原任务关联。 | 回答或明确结束本次未回答执行后，回到原任务的等待/暂停约束，不二次创建任务。 |
| 自然空闲仅答疑 | 目标原任务已经正常结束，收到合法临时问题。 | 一次辅助执行结束即返回空闲；回答可选，真实工具组须闭合，原任务保持完成。 |
| 停止的目标子代理/独立会话 | 拒收新问题并返回已停止。 | 不恢复，不默默加入下一轮队列。 |
| MainOnly | 保留子运行与父任务恢复关联；有效子问题可自动恢复主处理。 | 不因答疑自动解除 Goal 的暂停，不视作用户重新启动全部工作。 |
| MainAndSubagents | 父子任务整体停止，结算任务预留与已接纳问题的失败通知。 | 迟到问题/答案不得复活已取消的执行。 |

“自动仅答疑”不要求模型额外生成一个业务 final。不得为满足现有普通 turn 完成方法而伪造 Assistant、工具结果或子任务终态。答疑本身仍有可靠执行结束事实，真实用量进入当前权威计量链。

问题在目标接纳以后才遇到停止时，保留记录并通知提问者目标停止；提问者可按规则撤销。用户没有选择把这类问题都静默排队等待恢复，因此不得把“保留审计事实”实现成自动恢复队列。

## 七、等待与反向问题

父等待多个子任务时，任一需要父回答的问题都要使等待返回。返回的是可行动问题，不代表任一子任务完成。保存其他目标、任务归属和游标，回答后可继续原等待。

问题等待也应能因反向提问返回。等待期间不占据接收方唯一执行通道；唤醒后必须先形成合法工具结果边界再注入正文。

调度可继续不代表答案依赖天然无环。若双方都需要对方尚不存在的结果，应通过工具明确报告依赖、请求澄清或无法回答；禁止自动编造答案，禁止无限自动互问。重复提醒和自动恢复须按问题修订合并，不能为同一问题启动多份答疑。

## 八、故障恢复要求

| 故障点 | 必须恢复到的结果 |
| --- | --- |
| 来源可靠提交前失败 | 无成功接纳回执；查询稳定操作身份确认，不凭内存声称成功。 |
| 来源提交后、回执丢失 | 重试得到原问题和待投递状态。 |
| 目标接纳后、来源进度未更新 | 按投递 ID 重放得到同一接纳记录，不重复启动。 |
| 答案提交后、回答工具回执丢失 | 同一回答操作查回原提交，不重复回答或覆盖。 |
| 答案通知或等待接收器丢失 | 权威答案仍可查询；恢复交付途径，不能回退为未回答。 |
| 取消与在途投递竞争 | 以来源结算和修订核对，失效投递不重新产生待答义务。 |
| 父 final 与子任务预留竞争 | 相同完成准入序列决定先后；已成功预留的子任务阻止父完成。 |
| 进程重启或仅加载尾段 | 恢复未结状态、预留、待投递和授权；无法确定外部执行结果时显示待核对。 |
| 用户编辑历史、分叉或替换任务 | 新任务不能接收旧任务的迟到消息。分叉只复制可读历史，不复制可执行待投递和未结问题所有权。 |
| 删除/归档目标或撤销权限 | 提供明确不可交付状态并通知来源；保留必要审计，不借重试绕过。 |
| 来源归档或请求删除 | 归档仍能完成既有控制面结算；未结协作阻止物理删除。取消/结算后删除的迟到操作返回明确已删除/失效状态，不使目标永久等待来源写入。 |

## 九、单一新契约与实施注意

### 9.1 当前实现所采用的持久化边界

- `MetadataDocument.collaboration` 保存版本化协作摘要、历史权威边界和最后协作事件指针；事件为 `EventBody::Collaboration`，外层序列化标记是 `kind=collaboration`，内部事件种类为 `event_kind`。两层不能使用重复的同名 JSON 标记。
- 问题、单向通知、投递、答案交付、目标结算、答疑执行、子任务和授权各有强类型状态，不能根据渲染后的标签恢复权限。来源结算后，目标追加结算事实，来源再记录目标结算回执；该事务收敛不作为业务完成门。
- 答疑启动和完成操作分别保存不可变执行快照；精确重试返回原快照及原事件序号，当前状态由执行记录单独查询。启动语义包含精确父回合。已经提交的同键重试先于可变运行控制检查，不启动执行、不恢复停止状态；新操作仍必须满足当前准入。常驻事件与操作快照须完全吻合。
- 领域修改通过规范 `SessionHandle` 可靠发布，复用既有尾段及 metadata 发布机制。控制面准入允许已停止或归档来源完成查询、取消和必要结算；物理删除前封闭所有新修改，旧句柄不能重新写回已删除目录。
- 普通会话按真实索引定位；嵌入子会话须沿其持久 root 身份取得父 locator，再使用已有嵌入定位 API。子文档不进入普通索引，不能套用普通会话加载器后猜测目录。
- 编辑存在未结协作的来源须拒绝；分叉仅保留可读历史，新 metadata 不继承执行中的问题、任务、操作和授权。历史边界使旧事件保持可读而不再次授予可执行权威。

### 9.2 辅助答疑与执行证明

自然空闲答疑使用真正的辅助回合及专用 API 用途：`TurnOrigin::QuestionExecution`、`ApiPurposeKind::QuestionExecution`。启动事实创建该回合，完成事实关闭辅助执行并结算真实用量；不创建假用户输入、假 Assistant final 或第二份原业务结果。原 turn 内答疑保留父回合，答疑结束不能关闭父业务回合。

正常业务流收到问题时，`project_question_before_api` 在投影事务中创建 `InTurnQuestion` 处理记录，并将信封追加到原业务回合。该记录用于证明问题处理归属，不表示该物理 API 变成专用答疑请求；业务请求仍按原用途运行，原业务闭合时统一结算其问题处理记录。专用唤醒才使用独立的答疑流与 `QuestionExecution` API 用途，不能只看存在问题处理记录就把整个正常任务改成辅助执行。

专用启动使用 `prepare_question_execution_before_api` 将执行启动、问题 User 信封和投影回执合并为同一文档修订；内部投影失败时执行、辅助回合、分配器和事件全部回滚。组合入口的重试重新检查当前运行控制、无在途 API、运行中执行及精确开放回合，不能把历史启动回执中的运行态当成当前启动许可。原始启动操作仍保留不可变历史回执，组合入口不修改该规则。

消息接纳的服务事务必须调用 `require_document_message_admission`，重新检查写入时的停止控制。MainOnly 仅接受当前父文档子任务预留中身份一致、父代际一致、父回合仍开放且与目标绑定相同的直接子来源；共同根、相同项目、过期预检查均不足以授予该例外。子预留可以尚未记录子回合，比较其稳定身份而不把预留空回合与当前子回合强行相等。完整停止拒绝直接子来源；来源的已有查询及结算走独立控制面规则。

回复及待处理问题查询必须在异步定位完成后重新核对最初真实工具调用的物理 API 身份、逻辑回合和目标参与者，不能仅以同一回合仍活动作为原调用仍有效的证明。对已经回答或撤销的问题，获准参与者可读取来源权威结算；查询不要求处理该问题的业务或辅助执行先结束。目标侧仍需保留与问题、投递、参与者和绑定用途一致的可靠接纳凭据。

答疑准备使用单独入口 `spawn_webui_question_prepare_task`，持有已准入的可靠执行记录及精确内核代际，运行画像准备、跳过人类输入召回，通过答疑用途的共享续接构造请求。问题正文由可靠投影提供，不能伪装成人类根输入或可见提示记录。流入口 `spawn_question_execution_stream_task` 对照规范文档再次检查运行执行、回合、代际、当前控制状态和无在途 API，随后把原执行范围传入正常登记、重试和终态链。该入口不自行授予 MainOnly 子到主权限；生产调度器必须先证明直接子任务归属。

普通会话的可靠问题接纳通过 `schedule_question_wakeup` 异步调度，发送工具不等待画像或供应商执行。分发取得提交预留之后加载目标配置，重查来源问题和跨项目授权，在目标事务内证明 MainOnly 权限，再原子提交执行与问题正文。内核登记与代际捕获在同一服务锁内完成；阶段发布和准备任务继续使用精确所有者校验。已经完成的处理执行不因问题仍未回答而无限重启。

内核登记前的失败使用 `fail_undispatched_question_execution`，只在原始可靠执行仍运行、尚无物理 API 且没有替代内核或流时建立准备终态所有者。它使用答疑范围结算，不调用关闭业务回合的普通提交失败入口。嵌入子会话必须通过其子执行上下文启动，不能以普通索引目标假装完成接线；恢复和繁忙边界仍需可靠工作重新分发。

嵌入子会话通过 `MetadataDocument.child_execution_profile` 保存最新真实业务准备配置：版本、根与直接父身份、子任务身份、子文档代际、业务回合和执行 ID、已解析模型/工具/技能/压缩配置、运行时策略、固定代理提示词及子专属提示字段。普通会话和尚未完成准备的子会话没有该记录；没有记录时不能猜测子权限或套用父默认配置。

捕获发生在 `DelegateStarted` 的宿主投影屏障已经创建规范子文档之后、实际 Provider 准备之前，经仅宿主端口 `capture_child_execution_profile` 可靠发布。服务在规范生命周期准入后重查 TaskRuntime 精确活动执行及根/父身份，领域层再次校验子代际、原业务回合和无活动 API。答疑回合不能覆盖业务配置；业务结束后配置仍可读。历史编辑和分叉清除旧配置的可执行归属，未知版本及错配文档重载明确拒绝。该配置不替代模型连接、授权或工具运行时的现有权威来源。

准备失败使用 `fail_question_execution_preparation`：先证明可靠执行与精确内核所有者，再封闭该所有者并持久化答疑范围结算；禁止调用业务准备失败函数或终止父业务 Hook。辅助准备没有新的规范用户消息，因此共享记忆边界不注册新的业务活动回合，也不能借清理答疑之名放弃父业务记忆回合。内核已被停止或替换时不清理替代执行；持久化失败保留终态所有者，等待精确恢复。

运行内核使用 `ActiveTurnKind::QuestionExecution { execution_id }`，答疑 ID 必须随该精确内核代际传递。准备、流启动及准备失败同时检查内核的准备标识和执行 ID；内核停止前捕获此 ID，不从文本、UI 状态或“最新运行问题”推断。停止路径验证对应领域回合和可选物理 API，拒绝中断不同用途的业务 API，使用相同答疑范围结算并保留已有 API 中断事实。原父业务回合不因辅助停止而完成，自然空闲答疑只关闭自己的辅助回合。

答疑停止在旧流和结果工作器退出后先保存终态意图，再清理浏览器授权、中断 API 和处理其余停止状态；后续失败可依据意图恢复。原请求结果结算关卡在 API 中断落盘后释放，最终答疑归约器重新获取它；RunStop 准入与终态所有者仍覆盖整个间隔，不能递归持有该关卡造成自锁。

回合闭合事件必须携带 `purpose`，取值为 `business` 或 `question_execution`，没有旧数据默认值。辅助闭合保留真实边界和统计，但既不消费业务临时提示 TTL，也不发出其失效事件或清除生产者 metadata；下一真实业务闭合仍按原规则消费。重载时若起始事实常驻，闭合用途必须与起始所有者吻合；上下文回放直接依据闭合用途，不查询当前运行中的可变答疑记录。

终态结算意图必须保存 `TerminalSettlementScope`：普通业务使用 `business_turn`；辅助执行使用 `question_execution` 并携带精确执行 ID 及失败边界的可选活动 API ID。意图前恢复记录、已落盘意图、受控重试使用同一范围。答疑失败原子提交 API/工具终态、错误说明及执行完成，只关闭它自己创建的辅助回合；依附父回合时保留父业务、Goal 状态及 MainOnly 控制。错误的物理 API 或逻辑所有者必须拒绝，不能使用“当前最新请求”替代。

物理 API 可以先于答疑执行结算而结束。此时捕获的 API ID 仍须匹配同回合最后一次物理请求，起始事实晚于当前答疑启动回执，并具有同 ID、同答疑用途的终态事实。满足证明后保留原 API 和工具结果，只补充答疑结算；缺失证据或存在替代请求则拒绝。配置重试、压缩重启及登记失败必须携带原答疑绑定，不能清空身份后走业务失败入口。流取得真实 V1 许可后更新物理 API ID，并在放行前校验运行执行、原回合及活动 API 仍一致。

同一结算 ID 不能被改成其他范围、回合、所有者或原因。只有对应终态凭据存在才能清除结算意图：业务以回合终态为凭据，答疑以对应执行完成为凭据，自然空闲辅助还需其闭合事实。修复写入失败时保持精确所有者，后续重试刷写同一修改，不追加第二次失败或重复回报父业务结果。

辅助请求在共享准备层使用 `PendingSessionPromptSource::QuestionExecution` 与 `ExecutionPromptPurpose::QuestionExecution`。准备身份由会话及持久答疑执行 ID 确定，不创建或复用用户业务 Hook 回合，不派发用户输入 Hook，不生成用户输入边界事件；画像准备仍按当前会话配置处理，不能为了禁用业务 Hook 而清空已有画像或改变稳定顶部。

子会话身份和物理传输重试都不能覆盖答疑用途。答疑重试仍记为 `ApiPurposeKind::QuestionExecution`，不携带手动继续动作；运行时工具事件不写入保留的业务 Hook 时间线。答疑收尾必须走专用执行结算，不能调用普通完成报告来再次消费业务记忆 TTL、关闭原 Hook 或生成第二条用户回合统计。

答疑终态的进程内投影仅接纳真实对话检查点，并清理已结束执行的工具关联。既有业务完成记录及其他会话运行状态保持原值；没有检查点时不得从报告文本补造助手 final、摘要或终止记录。输入检查失败不发布部分草稿。该内存投影不承担用量、问题回答或执行完成的权威，服务收尾仍须完成对应 V1 可靠结算。

答疑流的成功收尾在普通业务报告、Goal 计量和完成 Hook 之前分流。成功凭据必须同时证明：回执修订已落盘、精确 API 终态为答疑成功、未晋升业务输入、所属回合一致、最后一次 API 起始晚于本次答疑的原始启动回执。已经提交的执行结果在丢失回执后重试时保持原值，晚到答案不能改写该次执行的历史结果。持久化失败沿同一执行范围的意图及恢复入口继续处理。

业务展示阶段在释放精确终态所有者之前恢复，避免后来的执行已经启动却被旧答疑报告覆盖。自然空闲恢复就绪，保留的运行中父任务恢复准备状态，MainOnly 及其他停止状态恢复停止展示；该映射不改变可靠运行控制或恢复 Goal。只有独立辅助回合清理自身浏览器授权，依附父任务的答疑保留父任务授权。

人类新任务不能成为独立辅助回合的过程输入。未来任务仍可可靠排队；队列晋升和直接补充输入均在领域入口拒绝辅助回合，且保持原队列、事件及修订不变。宿主协作信封仍可在合法 API 边界追加。辅助结束后必须通过专用真实业务后继调度消费队列，不能为复用普通完成方法伪造旧任务完成或自动恢复 Goal；该后继调度是独立的必做接线。

辅助完成后的队列调度使用独立操作 `ScheduleQuestionSuccessor`，发布 `QuestionSuccessorScheduled`。当前执行记录的 `queued_successor` 保存新业务 turn、原排队输入 ID、原用户动作 ID 和真实输入事件序号，调度操作保存当时完整执行快照。完成操作仍返回其原始未调度快照；调度重试返回原后继，不再消费下一条队列项。

调度事务仅接受已经完成的独立辅助执行，并要求该辅助仍是精确闭合前驱、运行控制自然空闲、没有活动 API、没有未解决终态意图。单次原子发布完成队首移除、绑定请求配置激活、真实用户输入、新业务回合、调度回执及运行控制切换。空队列不产生操作或修订；回合内答疑、明确停止、前驱已替换均不授权新调度。此事务不改写原业务统计、Goal 或旧历史。

服务在辅助终态所有者仍封闭准入时完成可靠后继选择，再恢复对应展示并释放所有者；随后只凭已经落盘的精确后继回执分发，沿既有用户输入准备、资源和模型配置入口启动。后继落盘失败保留终态恢复所有者，恢复不能把已完成辅助或已经选定的用户后继再次终结。重启后的实际自动分发及末边界后来到达队列的调度仍必须接入统一恢复调度器，不能把存在元数据回执等同于已完成恢复接线。

工具权限从原会话已准入集合中收窄：保留问答、通知、查询及原来获准的辅助工具；移除启动子任务、方向引导、停止或关闭任务，以及修改 Goal、Plan、待办列表的业务控制工具。移除同时作用于模型目录和实际调用定义；不因答疑增加新权限。原 turn 中正常处理到来的问题不适用此辅助执行限制，仍按原任务权限工作。

目标参与者在接纳时绑定；实际回复工具的回合可能是之后创建的辅助回合。服务须校验真实 ToolCall，再以持久 `question_execution` 证明它属于该问题。不能一律将 turn 置空，也不能仅删除身份检查。

工具回复成功后允许直接结束辅助执行；模型若未调用回复工具便输出 final，记录本次执行未回答，保留可查询问题，不将 final 转成答案，不无限自动重启，也不阻止业务完成。用户可通过停止后的取消入口收敛问题。

阶段通知在运行中的目标下一个合法消息边界投影；自然空闲时保存并展示，不因单向通知创建新业务或仅答疑执行。需要自动答疑的临时问题沿既有仅答疑规则处理，回复仍为可选结果。

### 9.3 任务预留与用户授权

子任务预留归父回合，并单独绑定父文档代次；子参与者的代次由实际子文档校验。两个文档的代次可以不同。启动前失败允许预留直接转失败，不能伪造激活时间或激活事件。

跨项目授权保存在来源会话，采用现有用户通道认证后的 `LocalUser` 权威；模型不能在工具参数中指定用户身份。用户授予、撤销和取消操作采用稳定请求 ID，网络重试复用同一操作。每次受限动作重查有效授权，查询与必要清理仍按既有事务归属控制。

用户已确认当前版本未发布，不考虑历史数据兼容。新增事件和状态采用唯一当前契约，保持严格解码和明确的版本检查，不实现旧格式解码、旧事件迁移或兼容分支。现有 `deny_unknown_fields` 不能靠随意附加 JSON 字段绕过。

新契约下的活跃任务不能在半个工具组内转移权威。失败恢复依赖当前代际、任务关联与可靠提交事实；不删除新提交记录来伪造回滚。不兼容历史不意味着可以清理真实用户数据。

P00 必须形成具体事件字段、状态摘要、可靠发布文件和索引重建清单。推荐实现位置为 V1 领域、SessionV1Handle、现有 workspace 会话存储和 TaskRuntime 的协调接口；不为方便而把所有状态塞入工具 JSON 或新建未经审阅的全局数据库。

### 9.4 子答疑的执行配置来源

嵌入子会话的答疑不得调用普通子任务续跑来取得执行环境，因为续跑会改写业务状态、执行身份及最终结果。业务准备阶段在规范子文档创建屏障之后，经仅宿主端口保存版本化 `ChildExecutionProfile`；配置属于该子文档，并绑定根、直接父、子任务、文档代际、业务回合和执行 ID。首次写入的执行 ID 必须等于真实根输入的客户端动作 ID。业务完成后仍可读取；分叉或编辑生成新历史时清除旧记录。

解析器结果与最终构造请求的继承结果必须区分。配置记录保存实际请求的规范化模型、推理传输值、执行模式、合并技能开关和工具策略，并保存实际温度、代理选择及固定提示字段。不能用界面显示文本编码推理，也不能在恢复时以新全局默认值替代缺失的子设置。凭据、进程句柄、浏览器绑定和当前授权由实际宿主重新准入；记录中的标签不提供权限。

消费侧仍需验证并接通：规范子句柄与 locator、原已准入工具集合、当前项目授权、仅答疑权限收窄、独立辅助执行与失败恢复。捕获记录存在本身不能证明子答疑已经实现。

原已准入工具集合从最终同步准备结果捕获，排除实际请求拒绝的调用；此时尚未进入 Provider 启动。每个公开工具 ID 同时绑定来源类别、来源命名空间及原始工具名，恢复时必须匹配来源身份。公开名称会受冲突后缀分配影响，不能单凭同名就继承权限。实际代理选择和温度同样以最终准备结果为准；请求模板中的缺省字段不能被当作最终选择。

恢复请求的 `captured_child_tool_admission` 是原工具来源上限：子答疑必填，恢复原业务同样从精确配置读取，空集合允许但不暴露任何工具。最终准备对模型描述与实际调用定义同时取交集；同名异来源拒绝，原来源因冲突而改名可保留。该上限贯穿压缩上下文捕获及内部请求重建。流启动根据规范子文档恢复配置，并在解析必需字段成功后一次性修改辅助请求；不使用业务续跑获得答疑配置，也不将持久配置当成当前宿主授权。新委派子请求必须清除父模板的捕获上限，然后从自身实际准备捕获新上限。

辅助请求必须以 `RestoredCheckpoint` 从已投影规范历史启动，不追加新用户 prompt。准备入口拒绝非空业务 prompt、业务 continuation action 或显式 `UserPrompt`；这一约束同时适用于主会话和嵌入子会话的独立答疑，不影响正常业务回合按消息边界处理临时消息。

子业务配置还必须保存实际请求中的非敏感会话覆盖：直接 Provider 工具目标、媒体工具/替代模型路由及其推理档位、启用能力、扩展目标集合，以及会话 VMM 预检和回写开关。四类可选 Provider 覆盖分别保留 `None` 与显式空集合的语义，恢复时完整替换模板字段，不能使用“存在才覆盖”的合并逻辑。连接字段只保存非敏感连接标识，实际凭据与授权仍从当前宿主取得。会话 VMM 层依据现有 V1 契约只允许两项行为开关；出现传输或项目字段时明确拒绝捕获，不静默丢失设置或保存秘密。项目配置与实时服务状态重新按当前项目取得。

子业务模型连接必须保存最终 `model_blueprint.connection_id`，答疑使用该精确连接重新解析当前凭据，不在冷启动时重新选择默认连接。输出样式保存规范化正文及来源标识，恢复时重算指纹；没有原样式时清除准备模板样式。

知识访问保存原项目、知识库集合与强类型检索策略，不保存回调。答疑启动按规范子 locator 的项目重新查询当前授权，与原集合取交集；新增授权不扩大原集合、撤销授权立即从本次准备移除。没有原访问或当前知识服务不可用时传入显式空访问上下文，避免普通流启动器继承其他会话默认值。授权查询错误明确使本次准备失败。异步解析完成后仍须核对精确内核执行归属。此处描述的是流入口准备约束；嵌入子自动唤醒上层仍需完整接线及验证。

### 9.5 子业务与辅助执行的互斥准入

子目标的物理执行互斥必须覆盖 TaskRuntime 业务准备与服务内核辅助执行两个入口。不能只检查当前活动 API：业务已经准备为 `Created` 但尚未获得后端执行权时，API 可以为空；业务在等待子任务、后续输入或压缩时也仍占用原执行。

TaskRuntime 使用独立的辅助预留表，并与业务准备、后端认领共享按子任务的事务锁。辅助准入先检查活动业务运行及强类型业务状态；活动状态返回占用，停止或归档明确拒绝。没有常驻业务记录的冷子会话允许宿主在完成规范 locator、权限和可靠控制校验后预留，预留本身不创建业务记录。业务准备和最终认领都在修改记录前拒绝辅助所有者。

辅助预留不进入 `active_task_runs`，不改变 `is_task_running`、业务执行 ID、最终结果或父任务完成计数。守卫持有唯一预留身份，离开作用域只释放自己。生产接线必须从准备前一直持有到重试、压缩、成功或失败清理完成，并保证用户停止可中止该辅助执行；仅有运行时预留 API 不表示这条上层生命周期已经实现。服务内核准入、持久执行权威和 TaskRuntime 互斥分别校验，不能相互替代。

服务侧 `child_question_execution_owners` 按子会话保留辅助执行 ID 及其 TaskRuntime 守卫。首次写入任务持有子守卫及规范生命周期锁，在 Core 原子准备成功后捕获精确回执，并在允许分发或报告发布错误之前转交守卫。即使刷写失败或等待写入的 Future 被取消，已经发生的内存修改也必须保持互斥；不能只在成功可靠回执返回后才处理所有权。嵌入流入口要求精确且可分发的所有者存在，流重试不重新争抢或替换预留。正常终态、失败终态及恢复重试均通过同一释放检查：对应执行必须已经完成、没有活动 API，且文档修改已经可靠发布。普通业务范围或另一辅助执行的清理不得释放当前预留。把守卫仅存入流 Future 不满足契约，因为停止销毁 Future 时可靠清理可能尚未完成。

嵌入子准备使用专用构建器：从规范子文档完整投影重建历史，恢复捕获配置，并按子 locator 的当前项目绑定宿主端口。不得通过普通会话索引加载、主画像/召回管线或业务续跑构造它。服务只增加子运行态及独立准备标记，不创建普通会话摘要。提交预留在分离准备调度后释放；TaskRuntime 辅助预留则由服务持有到可靠终态。用户停止、关闭和主树停止必须覆盖这个独立辅助执行，不能只中止业务 `active_task_runs`；该停止协调仍须在实施中补全。

服务持有辅助预留后，只有精确文档的发布检查成功才允许流分发。检查失败保留不可分发所有者，交由带范围失败结算及恢复释放，不能通过错误返回析构守卫提前放行业务。专用子停止必须先核对辅助记录与可选内核身份，并在调用外部清理前保存可恢复的精确答疑终态意图；没有活动 API 的准备阶段同样受此约束。停止只改变辅助执行与消息接纳控制，不能覆盖原业务结果。

活动请求停止还须等待已登记异步执行真正退出，然后排空结果发布，保存精确 API 的用户中断事实并结算辅助记录。只移除活动任务表条目不是退出证据。单节点停止已有准备阶段及活动 API 的定向验证；整棵子树、主树停止与模型控制工具仍须按完整权威归属接通，不能根据 TASK 目录层级判断代理祖先关系。首次嵌入辅助准入已增加专用写入及故障留存；独立唤醒继续复用现有 `schedule_question_wakeup` 的所有者，不增加重复任务层。原普通目标的首次准入、后台准备任务中止、重启重分发等仍需独立验证及补齐。

答疑准备必须在开始异步服务工作之前登记真实任务句柄，保存答疑执行 ID、内核代际和准备回合；这一规则同时用于普通会话及嵌入子会话。准备任务与 Provider 流分别登记，允许交接时短暂共存。停止在同一服务事务内取得这两个句柄、关闭代际，并在外部退休及领域结算之前中止和等待它们；正常准备结束只能按自身任务 ID 清除准备条目。底层服务若故意使用独立于调用者取消的转换任务，还须证明该转换与停止退休的顺序，不能把外层 Future 退出当作底层资源已经退休的充分证据。

浏览器准备绑定在产生独立转换之前，按“插件 AI 转换读门 → 精确会话连接槽锁”的顺序取得自有预留。取得预留前的等待可以取消且没有独立绑定效果；取得后将预留移入独立任务，使停止退休必定等待该任务的槽锁。预留析构先解锁，再清理没有其他持有者的空槽，最后释放插件读门，避免插件排空锁序倒置。该规则覆盖准备绑定，不能据此把其他原生浏览器操作或完整树停止视为已经验收；实际验证边界持续记录在实施报告。

### 9.6 独立会话的显式修订观察

会话等待读取精确 locator 的可靠 metadata 前沿，不以 `SessionDocument::memory_revision` 代替保存结果；草稿、工具输出等尚未刷写的修改不产生已发布变化回执。等待不持有长期生命周期锁，不启动或停止目标，不创建问答义务。磁盘读取在阻塞执行器中完成，读取错误直接暴露。

来源跨项目读取授权在每次观察前后重新验证。收到已接纳反向问题时返回其独立问题身份，并保留被等待会话和原基线游标；不是把问题当成目标任务结束。超时只结束观察，后续调用可复用原游标。普通变化回执包含可靠修订和事件前沿，业务结果由后续事件读取确定；不得在没有终态事件时推断任务完成。具体字段和代际检测范围见消息契约。

### 9.7 任务意图与目标接纳的独立持久边界

任务消息保存在新增的来源 `outbound_task_messages` 与目标 `inbound_task_messages` 中，通过既有 Collaboration 事件、metadata 和操作日志一起发布。来源创建、目标接纳、来源确认没有跨文档事务；服务必须先保存来源，再按稳定投递 ID 接纳目标，最后记录精确目标回执。恢复重放目标接纳不得重复产生队列意图；同一投递正文或绑定改变即冲突。

排队意图不捕获目标正在执行的回合，方向意图则必须绑定它。接纳不消费用户队列、不调用业务启动，也不投影模型正文。之后的执行认领必须重新校验目标状态及真实代际，并为排队任务保存自己的业务身份与结果范围；方向消息必须在同一原回合的合法边界应用。接纳状态不能解释成完成状态；当前已增加目标方向与失败转换，排队业务后继仍需继续接通。

尾段重载校验任务消息的双方所有者、操作原始结果、事件后状态与 metadata 对照；即使对应事件已经封存，metadata 中本地所有者与代际也要验证。未处理记录阻止编辑/物理删除；新代际清理同时移除两侧可执行任务消息。最终状态模型完成后，要按实际未结任务及投递替换当前阶段的未处理判定。

冷摘要校验另外根据操作事件序号归并来源最新回执，并要求 metadata 与其相同；原始发送操作必须仍可查证，目标接纳必须对应精确目标操作结果。不能只以字段形状合法认可后加的确认，也不能按操作 ID 的字典顺序选择当前状态。

目标 `task_message_effects` 保存独立的方向应用或失败回执。方向输入及效果事件在原子草稿中一起提交，修订相同；活动 API 尚未结束、原回合已结束/变更、目标停止/归档或当前为辅助答疑回合时拒绝应用。输入身份、原回合、投递 ID 和完整编码正文必须能与持久效果互相核对。明确失败可以在目标停止后保存，但不能覆盖已经应用的方向；失败后也不能重新投影。目标效果不等于原任务终结。

原始接纳回执不随处理改变，操作重试继续返回原结果。处理结果回流、来源确认及目标确认源提交仍须实现；在这条恢复链完整之前，不能只因目标已有效果就解除其历史删除保护。

### 9.8 授权撤销与请求边界写入顺序

用户授权添加/撤销与正文投影共享来源会话生命周期锁。涉及双方的投影按 UUID 固定顺序取得所有参与者的锁，取锁后验证规范句柄，在同一范围内读取来源事实与有效授权，再可靠发布目标。授权创建必须已经发布，内存中已撤销即拒绝；禁止为获得权限主动刷写来源。

所有锁由实际阻塞工作持有，不能只留在等待该工作的异步栈上；等待者取消后，写入仍持有保护直到返回。授权管理的准入预留也随实际写入保留。双方保护内不得调用会重新获取生命周期锁的协作异步修改器；来源确认在目标发布结束并释放双方锁后单独提交。失败回执修复与恢复分发仍按原工作包继续实施。

### 9.9 独立会话发送与方向候选

`send_session_message` 原生端口以真实 ToolCall 冻结来源身份，区分 `Start` 与 `Steer` 授权，可靠发布来源意图后才尝试目标接纳及来源确认。异步定位之后在实际来源写入中再次核对原物理 API，压缩/辅助答疑不能借此启动业务；来源和目标代际均继续由规范参与者及 Core 验证。

同一次调用重试查原意图，来源提交内部也处理并发胜出记录；向目标投递时使用胜出的 Core 回执，不重新捕获新业务回合。方向进入现有请求边界投影序列，仍在原回合应用，失效回合或撤销权限产生明确失败效果。来源定位暂时失败保留持久候选供后续边界或恢复处理，不在未知存储错误上结束目标业务。

当前队列模式已接入可靠接纳、真实服务认领和异步准备；最终结果已可可靠回传并内部确认，模型实际消费及完整重启恢复仍待完成。方向在最后一次物理响应附近到达时的完成门与重调度也须继续实现。MainOnly 下直接子到主的现有答疑恢复不能等同于新任务发送恢复，既有父子工具统一映射仍按原工作包推进。

### 9.10 排队任务的原子认领

Core `claim_task_message_before_api` 为已接纳的排队意图分配独立业务回合、输入和稳定执行 ID。宿主认领效果与模型可见输入相邻，后续目标配置提升及运行状态变更同属一个可靠修订。新回合来源为 `AgentTask`；人类草稿与用户排队输入不被消费。用户队列优先，已有业务/API/答疑执行阻止认领，代理队列按接纳顺序处理。

认领历史回执可幂等查询，但不授予当前物理启动权。调度必须再次核对当前回合及服务执行所有权；停止后的回执重试不得重新运行任务。恢复校验锚点、输入身份与完整编码正文，并从开放回合指针恢复已封存锚点的代理来源。服务认领使用新回合准入，关闭开始后拒绝创建任务；首次认领消费当前来源的 Start 授权，用户撤销新任务权限不将已认领执行改写为从未开始。最终结果及双方确认仍待接线。

存储层尾段加载也必须识别强类型协作起点；不能仅修改 Core 的内存重建。实际磁盘重载验证已发现并修复这一遗漏，认领与答疑事件均按事件类型和精确回合判定。标签正文不能充当宿主开始事件。

### 9.11 代理任务准备权威

待发送准备器增加独立代理任务来源，读取已认领回合、稳定执行 ID、代际和规范输入。仅运行中、完全可靠发布、尚未存在物理 API 的精确回合可取得首次分发权威，准备准入后再次比较原权威。目标当前配置与既有规范投影进入共享准备链，人类提示预检、用户气泡及重复输入追加不执行。

运行请求用途显式标记代理任务，保留正常业务工具及结束 Hook，物理启动固定恢复规范历史，不因调用方提供用户启动模式而追加第二份正文。业务请求分类沿用主/子代理的真实所有权。代理正文不解释为人类手动注入命令。准备入口已由后台唤醒调用，准备发布/分发错误走精确准备失败结算；这不代替待实现的任务最终结果回流和完整恢复。

### 9.12 生产唤醒与繁忙后的重查

目标可靠接纳排队消息后安排异步唤醒，随后来源确认单独提交。来源确认失败不取消目标已接纳事实，也不阻止目标开始处理；修复仍使用同一投递身份。认领期间持有用户提交/停止预留和双方规范生命周期锁，来源意图及授权在实际写入器中复核。外层等待取消不能提前释放写入器持有的预留。

普通业务完成且没有已选用户或 Goal 后继时，重新检查代理队列；答疑收尾没有已选用户后继时同样重查。用户已选后继和正在运行的业务保持原所有权。候选认领后从规范索引水合目标，只发布所有者仍匹配的目标切片，不覆盖其他会话或切换当前会话。已经发生物理 API 的认领不重走首次启动，交由原运行或恢复路径处理。

重启后的自动重调度、出站修复完成后的唤醒、末响应方向处理和最终结果确认继续按原工作包实施；当前普通接纳/收尾入口不构成这些路径的替代证明。

### 9.13 首次准备失败与答疑交错

可靠认领已提交但内核尚未登记时，水合或准备权威读取失败也必须结算。清理取得目标提交预留和规范生命周期锁，只处理原认领仍拥有的开放代理任务回合；有活动 API、该回合已产生任何 API 事实、有运行中答疑、或已被其他内核/后继回合取代时，不抢走现有所有权。固定脱敏错误与回合闭合在同一持久修改中发布，原认领身份保留。重复清理不新增事件，成功结算后再次检查其他排队任务。已经登记内核的准备失败沿既有精确准备所有者结算路径处理。

运行中业务尚未发出首次请求时，接纳的问题不得抢先启动专门答疑物理执行；它在正常首次请求的合法边界投影。正常投影仍登记关联原业务回合的 InTurnQuestion 处理尝试，以供回答工具证明身份，不另建辅助回合或 API。这样不会用答疑的 API 事实破坏业务首次分发身份，也不需要删除或重写历史。MainOnly 保留直接子到主的明确答疑例外，用户停止其他目标的拒收规则不变。

业务失败闭合时同样结束关联原回合的问答处理尝试，允许以未回答结束；问题事务本身不被伪造为已回答或撤销。实际闭合的 Running 业务在同一原子修订变为 NaturallyIdle，明确停止控制保持原值。进程中断仍需 Continue 的路径不闭合业务，也不提交问答收尾。物理 API 失败、问答尝试回执和业务终态共享预留修订，所有内部回执坐标从产生时即准确，不使用事后重编号修复。

### 9.14 任务结果与业务闭合同步冻结

`task_results` 由实际执行目标持有，按原任务消息投递 ID 保存不可变结果。结果绑定原接纳、精确应用效果、原业务回合及唯一终态统计，不读取随后活动的新回合。认领任务的回合起点必须等于认领事件；方向消息仍引用原已有回合。结束后的已应用效果必须拥有结果，仍开放的效果不能提前拥有结果，这项约束不依赖旧事件是否仍驻留。

成功结果保存该回合最后一次已完成正常业务 API 的唯一 Assistant 正文快照和事件坐标。当前 Core 每次 API 只有一个 `text_seq`，流式更新同一语义事件；不假定存在多个独立最终正文块。结果拒绝使用压缩、专门答疑、带工具调用或发生在方向输入之前的回复。停止和放弃只保存真实宿主终态，`final_assistant` 明确为空。完整正文不受模型投递信封的 64 KiB 限制；后续分块属于投影，不能截断原始权威或阻塞任务结束。

成功闭合、显式关闭和业务失败路径都在同一原子修改中追加结果记录。记录操作 ID 使用目标效果事件序号形成有界身份；冲突回滚整个闭合。冷恢复核对原结果事件、统计、API 及正文，封存前缀仅允许引用已离开驻留范围的事实，仍驻留的矛盾必须报错。结果在新业务开始之后保持不变。

目标侧 `task_result_recorded` 已接入独立卡片，来源接纳与内部确认见下一节，原回合正常请求前投影见 9.16；重启补送及末响应方向重调度仍须继续实现。本节不宣称模型已经消费最终结果。

### 9.15 原请求者接收与内部确认

来源使用 `received_task_results` 保存原执行者结果及本地接纳操作、发布修订、事件坐标与时间；目标使用 `task_result_acknowledgements` 保存对该精确接纳的内部确认。两种记录均不可变，按原投递 ID 去重，同操作不同内容或同投递不同结果明确冲突。冷恢复同时校验双方原始意图/结果、操作正反向绑定、真实所有者与驻留宿主事件。

服务交付持有双方按 UUID 排序的规范生命周期锁，在实际写入器内验证执行者结果已可靠发布。若来源早期任务接纳确认丢失，修复该确认与结果接纳共享一个来源原子修订；来源可靠发布后，目标才单独持久化确认。确认丢失时复用首份来源回执，不重新生成本地事件或正文。原任务已结束仍可补收，来源现有 API 与新业务保持原有身份；此阶段只更新宿主协作事实。

跨项目首次正文交付复核原来源持有的 Start/Steer 动作授权；撤销时保留待投递结果和明确错误，重新授权后可按原身份补送。已接纳正文的内部确认修复不构成新披露。每个待交付结果独立尝试，不因其中一个来源失败而跳过其他来源。普通终态释放所有权后和准备失败闭合后触发结果回传；完整重启扫描仍须接线。

`task_result_accepted` 是原请求者的结果卡片，`task_result_acknowledged` 是内部送达状态；均不表示模型已经消费。实际 User 分块投影见下一节；所有投递收敛后的编辑/删除保护仍在实施，不能仅凭内部确认清空这些后续义务。

### 9.16 原来源回合的完整结果投影

`task_result_projections` 保存本地接纳事件、原投递及原来源回合，逐块保存实际 User 输入序号和 ID，并保存原子发布操作、修订、事件与时间。结果正文从已经可靠接纳的权威重新生成确定性分块，不在投影凭据中再次复制。全部分块和凭据在同一原子修订提交，任一输入冲突或非法边界使整体回滚。重试返回首份凭据，不重复追加。冷恢复校验操作正反向引用、分块数量及顺序，并逐一对比仍驻留的输入正文、来源、可见性、身份和时间；封存输入依赖已经保存的精确坐标。

投影只允许原来源业务回合仍开放、运行控制为 Running 且没有活动物理 API。原来源回合已经结束或被替代时，仅保存既有结果历史，不生成投影、不创建新业务、不将正文追加到新任务。服务收集时和规范生命周期锁内均校验原回合。跨项目从接纳记录向模型交付时，重新检查请求者持有的原 Start/Steer 授权；接纳事实不替代新的交付授权。无需执行者在线即可消费本地不可变结果。`task_result_projected` 在界面单独表示“任务结果已加入上下文”，不冒充模型处理成功、Assistant 结束回复或新的待回答问题。

该入口接在正常下一请求的合法投影边界。末响应时若已无下一请求，由下一节成对接通的完成门与继续分发处理；完整冷恢复不能仅依据存在投影入口宣称已经完成。

### 9.17 末响应的协作继续身份（运行中链路已验证，冷恢复待完成）

继续身份从原回合的真实本地接纳派生：来源类型是精确方向投递或精确结果投递，并携带原回合及本地接纳序号，不另造 API 完成统计。按最早未处理接纳选择；未投影记录保持待处理，已投影记录由之后实际普通业务 API 起点覆盖。压缩和专门答疑请求不覆盖业务方向。问题与通知没有经此入口新增完成义务。

成功完成事务在与闭合相同的写锁内检查这些记录；Core 正常最终回复校验同样拒绝用旧正文结算未处理方向。流终态释放准入后再次查找，沿独立协作准备入口取得现有提交预留、重查原回合和控制状态，再复用现有业务 Hook 发起物理请求。实际正文仍由正常请求前投影执行并检查授权。准备不能使用真实用户后继、虚构 API 提升输入或新建任务代替同回合续跑。

`AgentContinuation` 来源不产生人类正文、用户回合边界或用户 Hook 时间线输入，不解析手动注入指令；已有业务 Hook 保持原身份。缺失原 Hook 必须先通过恢复链重建，当前入口明确拒绝伪造新 Hook。停止、替代任务、已消费记录不再获得续跑权威。完整冷恢复与被拒绝准备的自动重试仍受原恢复工作包约束。本节 Core、运行时及真实服务验证已通过，结果记录于工作报告。

### 9.18 任务出站补投递与接纳补确认

实时发送和宿主恢复共用 `deliver_recorded_task_message`：实际写入器持有双方规范生命周期所有权，从来源持久意图取完整冻结消息。来源发布失败时先尝试刷写该意图，失败则不产生远端接纳。目标尚未接纳时重新核验跨项目原动作授权；目标已有相同接纳时，只允许复制已可靠发布的原回执，不重新绑定当前回合，不要求再次授权已有事实的内部确认。尚在内存的接纳不能写成来源可靠确认。

发送 API 已结束不使可靠意图消失；方向所绑定的目标回合已结束则拒绝首次补投递，不能改绑到替代任务。已接纳的排队任务唤醒仍要经过原认领门，重新校验授权、停止控制与运行所有权。来源确认使用原消息派生操作键，正常重试和恢复取得相同回执；一项补投递失败不跳过其他独立消息。既有会话出站修复入口已接入此路径，完整自动启动扫描仍待完成，不能将方法可调用等同于重启自动恢复已经验收。

### 9.19 索引会话的启动补投递

服务完成工作区及运行时发布后调度一次启动修复，快照活动和归档索引会话 ID。每个身份在自己的生命周期槽内取得精确索引定位器，并读取、校验协作元数据；退出该槽后才加载确有待办的规范文档并进行跨会话操作。无待办会话不加载交互历史；损坏元数据明确报错，不能被当成空出站箱。

筛选覆盖未确认任务意图、未确认任务结果、尚未应用的排队启动、无结果的已认领任务，以及需要修复或唤醒的问题事务。完整文档重新校验原始 API、业务回合、代际和当前授权，元数据不作为直接执行许可。出站、结果、队列和问题各阶段独立尝试，所有会话都尝试后汇总失败并留下用户可查诊断；不因其中一项失败中止其他独立会话，不阻塞服务就绪。

此入口仍须继续补齐嵌入子会话目录、通知恢复、失去运行时所有者的仅答疑执行以及原业务 Hook 身份恢复。正在运行的完整业务不得仅凭该扫描重新创建 Hook 或新任务；这部分保持独立的恢复契约。验证证据和未闭合边界以工作报告中的实际结果为准。

### 9.20 根与嵌套子任务的启动屏障

`DelegateStarted` 属于执行准入屏障。创建规范子文档、取得真实执行事实或订阅分离事件失败时，宿主必须向原运行时等待器返回明确拒绝；不能按显示事件容忍拒绝或等待超时后继续启动 Provider。

根流负责主会话启动的子任务；子任务再次启动后代时，启动事件经由该任务的分离 `ChildExecution` 流到达，必须执行相同监听器准入。事件中的父会话必须等于分离监听器的任务身份；已经被新执行替代的旧监听器无权再准入后代，并立即拒绝启动等待器。建立后代接收器之后才进入后续显示投影与确认。

上述屏障只证明启动前已经建立接收者，不替代父回合的持久子任务预留、激活和终态。后者尚需接通真实工具路径，并保存每次执行的精确身份，使同一子会话可以再次执行而不覆盖旧执行事实。主会话的原始派生工具 API 已结束后，后续子任务终态仍必须能够依赖持久预留完成结算，不能要求原 API 永远保持活动。

### 9.21 可复用子会话与单次执行分离

`child_tasks` 以 `CollaborationExecutionId` 为键。每条记录另存物理 `task_id`、原父回合、父代际和完整子参与者；同一子会话的历史执行各自保留，不能覆盖旧记录。预留、激活、终态输入及幂等操作指纹/回执均绑定单次执行。激活和结束除查执行键外，还必须匹配物理子任务身份。

同一父文档不得同时保存同一子会话的两个未终态所有者；新预留和冷元数据校验都执行此约束。前次终态之后允许新执行绑定当前开放父回合。旧执行的重复预留或终态只返回原始回执，不新增事件、不解除后续父回合的完成义务。事件重放与元数据匹配同样以执行 ID 为准。

父子通信归属按完整参与者范围核验，不能依据映射的第一条或“最近一条”记录猜测；MainOnly 的直接子例外还须匹配目标保留父回合、父代际和开放状态。这里允许多条历史记录证明稳定会话归属，但单次执行结算仍必须使用精确执行 ID。该领域契约已完成定向验证，实际宿主预留/结束接线仍属于未完成工作。

### 9.22 原始工具认证与派生生命周期接线

模型可见派生闭包把原始 `VulcanToolInvocationContext` 和宿主端口直接传入 TaskRuntime；参数正文和显示事件不能提供替代来源。绑定以精确执行 ID 临时登记并由实际运行后端认领；认领前取消或后端未认领退出时清理原绑定。缺失宿主端口的模型派生工具明确报错。宿主与运行时共用操作指纹构造函数。

运行时先发布并等待 `DelegateStarted`，宿主建立精确子文档及监听器；之后父派生工具尚未返回，预留入口核验原 API 与 ToolCall、实际子运行的直接父事实，并从规范子文档解析项目和代际。父回合由原 ToolCall 取得；请求不携带运行时猜测的父回合或子参与者。父预留及激活完成后才派生子 Provider future。

子记录保留 `reservation_operation_id` 与 `source_tool_name`，状态恢复校验它们引用的原始预留语义和回执。激活及终态依据这份原始预留复算完整工具调用指纹，核验执行 ID、物理子会话和父代际；允许原 API 已结束，禁止另一条工具调用接管该执行。新预留仍要求活动原 API，不能以已有记录为由发起未经准入的新工作。

本节入口接线与认证已经过定向验证，不等于父子全部完成链已闭合。成功回流按下节原子提交；监听器已创建但预留/激活失败时的子文档与监听器收尾、后代未结束及排队后继仍保持未完成验收项。

### 9.23 成功正文与所属执行终态原子发布

运行时物理执行成功只更新其运行记录并发布回流事件，不调用父侧成功终态端口；该端口拒绝单独成功提交。直到精确子结果进入父文档前，原持久子任务记录保持活动，父完成门继续等待。

分离监听器使用自身执行 ID 和真实子接收器的最终正文回执读取可靠子文档，构造不透明回流输入。父规范句柄在同一发布锁内执行 Core 原子转换：验证原执行、物理子会话、父代际与原父回合，暂存正文，再以原预留派生的固定成功操作键结算终态。两份事实共用一次修订，持久化成功后才发布可等待的返回结果；完成门由“仍有所属子任务”转入“有精确待分发结果”，中间没有二者同时缺失的状态。

正文与终态必须同时新提交或同时幂等，不能将另一份正文拼到旧成功记录。任何身份或后续操作冲突都回滚完整草稿；冷加载后允许精确重试，不制造新修订。当前失败、停止、排队后继与子树恢复需要各自的收尾契约，不能通过伪造成功正文解除完成门；未登记所属预留的低层任务入口仍待生产暴露链审计。

成功来源还必须具有唯一的成功业务闭合边界、成功回合结果以及正常业务最终 API；停止或放弃时残留的完成文本、压缩结果、临时答疑结果均不具备成功回流资格。父侧已回流结果仅由之后启动的业务 API 消费；压缩和临时答疑即使启动序号更新，也不能解除原业务结果的待分发义务。这一规则在冷加载之后仍然保持。

### 9.24 启动准入拒绝与取消阶段分离

服务建立规范子文档后，先以真实根输入的执行 ID 捕获原子回合和代次。监听器后续准入失败且尚未确认启动屏障时，统一尝试关闭该原子回合、撤销该执行尚未发布的回流门及移除同执行监听器；每项清理失败都保留明确诊断，不能因首项失败遗漏其余资源。关闭前再次检查原回合与代次，替代回合或已有终态不变；活动 API 不在这条启动拒绝路径的权限内。

回流门删除在运行时同一锁内比较执行 ID；较新执行不受迟到拒绝影响，已经发布的回执禁止撤销。这样被拒启动不会留下永远等待成功正文的邮箱门。

屏障确认后的运行时失败与取消是另一条收尾路径。启动守卫已同时持有活动运行租约和精确事件流，失败或取消时先释放租约，再关闭流；租约释放失败不得提前发出流结束。成功时先把租约移入后台终态处理器，再交接流清理责任，三步之间没有异步等待间隙；未转移租约的交接明确拒绝并清理。定向验证通过占用事件流锁确认租约仍能先释放，避免仅凭销毁后的空注册表误判实际顺序。

精确中止通知及父预留失败结算已按第 9.28 节接通。父预留在持久修改锁内再次验证活动执行事实，防止等待期间已取消的执行提交新预留。不能用普通事件流结束替代明确中止语义，也不能凭当前子会话最新回合猜测待清理对象；完整停止树及故障恢复仍需要后续验收。

失败和停止反馈不得进入要求最终 assistant 正文的成功回流构造器。失败原因、原执行身份及父侧结果分发义务必须可靠保存，然后才能解除原子任务完成约束；模型应获得真实失败结果，无需人为生成成功正文。实际分离终态入口已按第 9.27 节接通，可靠恢复仍未完成，不能以运行时邮箱已经收到失败代替可靠父文档已经接收结果。

### 9.25 非成功子结果的可靠来源与原子发布

已增加领域入口 `build_child_task_non_success_input`：只从完全持久化的规范子文档构造不透明输入，核验根动作中的原执行 ID、子文档代次、唯一业务终态和来源范围。保存真实逻辑闭合结果及独立宿主结果分类；失败必须具有原业务回合内的永久宿主错误记录，不要求也不伪造最终助手正文。

父侧 `record_child_task_non_success` 从原预留取得父子归属，在同一原子修订中结算所属执行并保存完整非成功报告。操作键使用原预留事件序号；精确重复返回原回执，不同来源凭据拒绝并保持父文档不变。原预留及终态回执不因后来报告而改变快照。恢复同时校验报告、所属子记录和原报告操作，防止只有一侧记录的孤立状态。

非成功报告进入原业务回合的待处理协作查询，替代已结算活动子任务的完成约束。前端以独立代理任务结果卡显示来源、状态和原诊断。模型输入投影和消费凭据已按下节接通，实际终态分支按第 9.27 节实现；完整恢复仍待完成，不能把局部验收当成整个失败/停止回流链验收。

### 9.26 非成功报告的无损投影与业务消费

报告携带不可变父发布修订；只有该修订可靠落盘后，服务才允许在原父业务回合的合法 API 边界追加模型输入。规范生命周期锁内重新核验原预留、父代次及完整报告，停止或替代回合不投影。并发调用共用原回执，不产生重复输入。

完整来源凭据序列化为 JSON，超过单条正文容量时按 UTF-8 边界无损分块，每块包含总字节数、块序号及起止坐标。所有块使用 `task_result` 的 User 信封，并以子会话为来源、父会话为目标；绝不搬到顶部提示词。追加全部输入、投影凭据及操作事件共用一次原子修订，任何中间冲突回滚整批。原报告回执保持不变，投影通过独立 `non_success_projection` 保存。

只有投影全部输入之后启动的业务 API 才能消费该结果；投影前已经启动的请求、压缩和临时答疑不能消费。冷恢复核对投影、操作、宿主事件和仍在当前段内的精确信封，防止来源或正文替换。前端只在原报告卡显示诊断，后续投影事件不重复生成任务结果卡，协议输入不显示为用户消息。

### 9.27 真实分离终态与等待门

`DelegateFinished` 先解析强类型邮箱，并核验监听器执行及父子会话。成功继续走精确最终正文构造器；失败、停止使用原父预留中的子代次和唯一原根动作定位业务回合。原业务仍开放时先关闭：失败提交永久宿主诊断并终结活动 API，停止只中断活动 API 并记录停止。已有终态不修改，也不关闭替代回合；之后从完整可靠来源构造凭据并原子发布父结果。

后台运行时不再先解除失败或停止的父任务义务。登记了可靠回流门的任务，普通邮箱、默认等待目标和缓存终态读取均等待父发布完成；较新门同样阻止旧执行抢先发布。未登记宿主门的低层内部执行仍按其明确直投契约工作。父发布成功后仅唤醒结果邮箱，并按实际父状态安排同业务协作续跑；暂停父仍保留结果。

父存储失败不能改写真实子结果种类，不能发布伪造失败正文。存活进程保留精确监听器、未发布门及原终态凭据，通过第 9.29 节的自动重试继续处理；重启恢复仍须补齐。此处不声称已完成崩溃恢复、完整停止树、后代和排队后继的全生命周期。

### 9.28 明确启动中止及后台放行

启动守卫共享已冻结原请求，保留已观测原始错误。Future 取消而没有返回错误时，仅记录后台归属建立前结束，不按文本猜测用户停止。先释放活动租约，再记录进程失败，并向已有订阅者发送 `StartupAborted`；投递与流删除在同一锁内执行，随后才出现流结束，无订阅者不留孤立缓冲。

服务使用准入时捕获的原子回合及代次处理该控制事件，重新核验父子会话和执行身份。有父预留时通过同一可靠非成功发布器闭合来源、提交父报告，再发布邮箱；没有父预留时关闭原子文档并撤销未发布门。普通事件处理器拒绝缺少捕获所有者的中止调用。清理失败保留恢复归属，不能假装成功。

子 Future 的准备和 Provider 写入受一次性许可约束。先安装中止句柄，移交租约及终态连接句柄，最后放行；许可撤回时不得执行子 Future。已被停止的接收端由已安装终态处理器处理。运行时守卫与服务三个接纳阶段已获定向验证；新增实际 Future 取消和放行门验证的结果以工作日志为准。与完整停止树并发、存储故障及重启恢复仍属于未完成范围。

### 9.29 存活进程终态重试

监听器接纳终态时验证父子及执行身份，冻结原宿主事件和成功助手回执。一个具体执行保留一个待处理终态；完全相同的重复反馈不重置退避、不替换证据，不同终态明确诊断。成功来源始终使用首次捕获的原 API、事件序号及正文，不读取后续接收器的最新助手。

同一监听器并行等待普通流事件与单调时钟重试期限，单次处理仍串行进行。存储失败按 250 毫秒起步、最大 30 秒间隔重试；错误变化才追加诊断。等待期间继续处理嵌套启动等普通事件；流结束只停止读流，不能清除未解决的发布。成功发布使用原幂等回执，重复尝试不重复发送模型等待邮箱。

普通终态在可靠发布及后续续跑处理成功后才清理监听器，防止续跑错误失去恢复归属。启动中止继续使用准入时捕获的原回合。当前机制保存于存活任务内，不代表崩溃前意图已可靠保存；冷恢复仍需由根索引与原生子预留找到规范嵌入目录，恢复终态来源和待处理结果。实际磁盘故障、流结束与重复反馈验证状态以实施工作报告为准。

服务分发前后两次覆盖查询统一使用 Core `subagent_return_dispatch_started`：必须是原父回合、晚于结果且用途属于业务的请求。压缩与临时答疑不能使服务返回已分发。实际索引及文件夹具已验证辅助用途的否定路径和后续业务请求的肯定路径；磁盘重试验证同时证明流结束后恢复、重复反馈只交付一次以及嵌套事件仍能处理。

### 9.30 嵌入子树消息恢复的发现与加载

启动扫描从实际索引根读取同一次原子元数据发布中的代次及协作状态，沿父文档可靠子预留迭代发现后代。所有深度都从同一索引根定位器派生嵌入位置，不按直接父目录重复嵌套，也不扫描目录。一个物理子会话保留当前代次的全部执行记录，发现阶段不选择“最新执行”。跨根、跨项目、循环、多父或活动代次冲突均明确报错；不可读子存储单独记诊断，正常兄弟及根消息继续修复。

筛选快照不是修改授权。存在消息待办或尚未结算的原生预留时加载其祖先链，按统一身份顺序持有根、父及子生命周期锁，并将锁移入实际阻塞操作。规范父必须拥有已经发布的原预留、同一代次、原操作及工具名、原父回合及子参与者；物理子代次必须仍与发现一致，再执行规范子加载及既有中断投影。无待办子树只读取元数据。使用既有根用量绑定恢复定位关系，不修改统计计算规则，也不将台账作为授权。

出站消息修复接受已验证规范来源句柄，根会话入口继续走索引，嵌入来源不进入仅支持根会话的索引查询。两层真实磁盘冷恢复、重复扫描幂等及局部文件故障隔离已获定向验证。本节不代表原生子任务终态、原业务执行和 Hook、未预留孤立文档、通知及答疑全部重启流程已经完成，这些仍需后续工作包闭合。

### 9.31 原执行成功凭据与重启重建

成功回流输入与持久 `subagent_return` 事件必须保存 `child_segment_generation` 及 `child_root_action_id`。来源构造器从可靠最终业务回合的原根输入读取动作；父侧原子完成同时比较预留的子代次和执行 ID。历史唯一性、重复投递、范围重叠与覆盖前沿均按子代次分区；不同代次相同序号不代表同一结果。字段必需且没有旧格式默认值，界面同序号身份检查也包含代次与根动作，并用数组序列化避免字符串分隔符歧义。

冷恢复按原执行 ID 查找唯一根动作，再定位原回合终态及终态 API 的唯一已完成助手正文。共享构造器继续校验普通业务用途、成功结束与无工具调用。后续新任务或答疑不能改变原结果选择。尚无终态或非成功终态不生成成功凭据，畸形成功记录明确报错；此入口不从错误文案猜测失败或停止。

服务在父子规范生命周期锁内重读原可靠预留，按精确子代次读取完整来源，再通过实时处理所用同一原子父转换发布正文与完成记录。只发布已存在的原业务结果，不伪造运行时邮箱、不启动新的供应商请求；原父回合保留尚未业务消费结果的分发事实。直接及嵌套实际磁盘恢复、重复扫描、实时成功回流均已获定向验证。非成功来源的明确终态恢复见 9.32；原业务执行和 Hook 的重建仍待后续接通。

新建嵌入子绕过标准句柄提交入口，首次物理候选必须同时保存根输入及对应 Running 控制，再向注册表发布。控制身份采用标准根动作规则；续跑和精确重放继续使用既有句柄入口，不能重复覆盖用户停止。创建、续跑、精确冷重放及实际自然完成入口已获定向验证。

### 9.32 明确结束原因与非成功来源重建

每个回合边界必需保存 `reason`：`completed`、`abandoned`、`stopped` 或 `failed`。失败和主动停止可共用既有统计聚合结果，但具体原因不得互换；重载检查原因与聚合结果一致，缺失字段直接拒绝，不兼容历史数据。实际宿主失败入口在保存永久错误和闭合的同一事务内写入 `failed`，普通诊断不改变分类。

冷恢复根据精确原执行根输入查找原回合业务边界，以明确原因构造非成功凭据。来源必须完整且可靠，失败仍需保留真实宿主错误证据；新任务及答疑不能替代原来源。服务复用实时原子父发布入口，父任务终态与待消费报告同时保存，重复恢复返回原凭据，不创建第二份结果。尚未闭合来源不推断结果，也不擅自续跑。直接和嵌套实际存储验证结果以工作报告为准。

### 9.33 原业务恢复的来源与请求转换边界

Core 原业务配置选择器必须验证完整可靠来源、原唯一根动作、原开放业务回合、捕获配置的代次及执行 ID。运行控制必须允许正常业务，不存在活动 API 或正在处理的答疑。未确定效果的工具返回待核对错误，不能因中断状态自动重放。

运行时专用子业务恢复函数仅接受原会话 AgentTask 检查点请求，禁止重复任务输入、新客户端动作、旧物理传输续接或父 Hook/Goal/Plan 状态。模型、连接、工具来源、技能与会话覆盖来自规范捕获配置。原生 TaskSession 不拥有主会话 Hook，恢复时不继承或制造主 Hook；主会话原业务 Hook 必须在自身恢复链路重建。答疑入口仍不运行原业务完成 Hook。设置转换共用不代表生命周期共用。

以上选择和转换本身不授予调度权限；服务仍需在父子规范生命周期锁内重验原预留、保存实际执行所有者、恢复 Hook 和父监听器，并在异步准备后重新验证来源。完整调度接入尚未完成，不能将转换验证记为真实模型恢复执行的证据。

主会话完成消费必须在持有 Hook 所有权锁时确认原所有者存在，再执行 TTL 持久化及完成 Hook。所有者缺失返回明确待恢复错误，不从最后 UserText 推断原任务。投影下标派生的消息 ID 不能作为持久 Hook 关联，恢复需依赖 V1 原会话、代次及回合的明确绑定。

### 9.34 主 Hook 原始准入绑定

会话元数据必需包含 `business_hook` 当前契约容器，不提供旧格式默认值。绑定保存实际主 Hook ID、规范会话、事件树代次、业务回合及原起始序号，以及经宿主处理的原输入和首次 VMM 就绪状态。新业务回合可以替换最近绑定，同一回合只能精确重试；不同身份或正文拒绝改写。新事件树代次和分叉清除该可执行归属。

直接提交、排队及 Goal 准备使用实际内存 Hook 捕获，并在 kernel 注册及 Provider 请求之前可靠发布。提交预留覆盖准备、保存和注册，磁盘保存期间不持有服务或 Hook 锁；Core 在修改锁内再次校验规范坐标。后续引导导致的活动 VMM 就绪变化不改写首次准入事实。

恢复选择要求完整已发布来源、原开放业务回合、允许业务运行、无活动物理请求和运行中答疑，并确认原起始事件存在。运行时身份安装不重放用户、画像或 precheck Hook，已有匹配所有者保留实时状态。身份种子本身不包含完整 Hook 时间线；排队观察及去重的规范恢复见 9.35，其余来源仍需补齐。身份安装定向验证不代表完整冷续跑已接通。

### 9.35 排队观察的原子日志

规范排队准入在相同元数据修订中保存 `business_hook.queued_inputs`，每条带观察业务回合、规范动作、输入 ID 及原始正文。记录不依赖 Hook 是否已准备，首次 Hook 绑定保留同回合记录；无开放业务时不创建观察。重复提交不追加，未来执行被删除或移回草稿不删除既有观察；新回合及新代次不能继承旧观察。

此初始字段现已由 9.38 的统一 `observed_inputs` 契约替换，不再读取旧字段；上述准入与历史保留规则继续适用。

在线 Hook 通知先读取已发布日志，按规范顺序恢复原所有者的队列时间线和去重集合，再派发单条通知。没有匹配的活动业务 Hook 时不能由队列通知制造新 Hook。恢复遇到身份、正文、重复或顺序冲突，在修改活动状态之前明确失败；正常恢复不重放用户事件。准备入口同步该日志，用于修复持久准入之后、内存通知之前的中断。该日志只覆盖排队观察，其余时间线来源和完整冷调度继续按原工作包补齐。

### 9.36 过程续跑的逐条 Hook 身份

真实过程续跑的入口 ID 标识一次准备批次，不充当输入去重身份。服务从精确终态回执重建的规范输入列表传递动作 ID、输入 ID、事件序号和原文，通过专用共享准备入口处理；普通提交参数结构不增添可选猜测来源。

批次要求已有原业务 Hook，逐条验证身份与顺序。已观察的排队输入保留原记录，新直接输入各自清理手动注入语法后追加独立条目。完成全部校验后一次性发布并仅通知尚未准备的直接输入，合并正文仅供原请求准备使用，不再次写入 Hook 时间线。重试可使用不同物理批次 ID，但不能替换原输入坐标或正文；冲突不能产生部分时间线、部分回执或就绪状态修改。当前进程内回执不代替持久原业务来源；规范准入观察现由 9.38 保存及恢复，完整冷执行调度和显式 Continue 路径仍须继续完成。

### 9.37 辅助请求不消费业务输入

根输入与原终态回执中的过程输入，以同回合后续业务 API 开始作为已经分发的依据。压缩和临时答疑可以读取同一历史，但不能据此剥夺原业务输入的执行资格。仍活动的任意物理 API 继续阻止并发分发；辅助请求结束之后，重新校验原回合、原输入序号和内容，保留原业务权威。主生成、重试及其他业务用途仍会消费该边界，不能重复执行。

代理任务同样保留原认领，选择候选、准备权威和启动前失败结算必须一致；辅助历史不等于业务已启动。首次业务未开始时的问题依然排在该业务请求内处理，不能被压缩历史改变为独立抢先答疑。媒体参数冻结和精确答疑终态绑定属于物理请求约束，不套用业务消费筛选。

业务成功必须由最近一次业务 API 的已完成最终正文证明；辅助最终正文不能代替它，后续业务重试也不能被较早最终正文掩盖。显式继续采用最近业务终态的继续策略，压缩或答疑的相反策略不授予或撤销业务继续资格。失败收尾保留原业务进程中断的恢复路径；仅有辅助进程中断不能阻止未执行业务的明确失败闭合。独立答疑回合仍由它自己的答疑终态负责。

Goal 续跑与迟到子结果只有实际业务开始后才算已执行；结束的辅助历史不阻止用户原有的替代优先权。完成 Goal 可以关闭只有辅助历史、没有活动 API 的未分发续跑；只要任何物理 API 仍活动，就必须保留其回合和执行所有权。以上业务分类不改变辅助费用和事件的真实持久记录。

### 9.38 混合输入观察及原观察顺序

当前主 Hook 元数据必需使用 `observed_inputs`，每条保存所属回合、原动作及输入 ID、原文、排队或直接引导种类，以及首次观察的规范修订。直接插队与排队准入均在原规范事务内发布该日志；不从 User 角色或标签推断人类来源。字段缺失不兼容，原始正文不会因后续清理或队列删除被改写。

顺序以观察修订非递减及同修订内的原事务追加顺序为准，不能按输入 ID 或通知到达时间排序。组合准入共享一份预留修订，不制造额外修订。更早回合留下的队列项首次提升到当前回合时追加引导观察；同回合已观察的队列项不重复。加载校验修订及 ID 前沿，运行时恢复校验原 Hook、来源、身份、内容和相对位置；整份日志校验成功后才发布。

恢复只重建历史及身份，不派发用户事件。当前实际准备依据精确过程输入回执单独处理通知，已存在历史不能导致重复追加合并正文。进程内通知去重不代表外部 Hook 副作用跨崩溃恰好一次；完整冷调度仍须按原计划继续实现。显式 Continue 输入使用下一节的专用实际回执路径。

### 9.39 显式继续的可靠回执与原 Hook

显式继续准入返回并保留实际 `ContinueTurnReceipt`。附带补充内容时，同一规范事务追加人类输入及带引导来源的观察；纯继续不追加人类历史。服务以原动作、请求及恢复控制序号、可选输入 ID 和序号核验当前开放业务，并要求绑定属于同会话、同代次、同回合及原起始序号。活动物理请求、较新的业务请求或另一次继续均使旧准备权威失效。

共享准备使用原可靠绑定安装 Hook，继续来源为 `ExecutionRetry`；唯一可选人类输入按原坐标进入时间线，不追加合并提示或纯继续文本。允许显式用户继续恢复被停止的业务，因此此入口不能直接复用无人值守恢复的 Running 控制要求。缺少原绑定时明确失败；原初次准备尚未发布身份、完整冷调度及外部 Hook 副作用恢复仍需单独实现和验收。

### 9.40 启动修复任务的生命周期

同一规范会话注册表最多拥有一个启动修复任务，所有权在任务完成、取消或栈展开时释放。扫描失败后保留任务并进行一至三十秒有界退避，成功完成一轮后退出；这是启动待办修复，不是宣称所有未实现冷执行已恢复。每次尝试读取当前活动及归档索引，继续从可靠父预留发现嵌入后代，不猜测目录。

等待期间仅弱引用服务，避免服务和后台任务循环持有。注册表替换使旧修复任务退出；宿主关闭或关闭恢复失败暂停新扫描，准入重新开放后可以继续。选中节点在修复前重查原注册表及宿主关闭状态；已准入事务保持既有可靠写与生命周期锁语义。诊断按变化发布，永久失败保留待办与明确错误，不用尝试次数上限丢弃工作。

### 9.41 原生子代理运行身份

子执行准备配置必需保存原公开任务名称、原展示标题、描述、子代理标记及嵌套层级，直接来源为实际运行时委派请求。公开名称允许不同于物理 UUID，后续查找必须使用原名称；会话标题可以独立展示，不能成为恢复身份的备用来源。新契约不兼容缺失身份的记录。

同一业务回合及执行身份再次准备时，原根、原父与运行身份保持不可变；请求配置刷新不能改变任务归属。深度为一必须对应直接父为根，公开名遵守既有单段命名规则，非法值在规范修改之前拒绝。完整运行记录、原执行租约和监听恢复仍须按原工作包接通，本字段不等于恢复调度已经完成。


### 9.42 原调用与解析结果的冻结

子执行配置必需同时保存原 `invocation_config` 和原 `resolved_config`，类型定义归会话核心，配置解析归任务会话层。前者保留未指定、显式覆盖及原正文；后者保留实际继承解析后的请求配置、有效配置、功能提示层和运行策略。真实请求准备之后捕获的有效设置仍单独保存，因为它包括规范模型路由和合并后的技能开关。

同一业务执行的重新准备不能改变原调用或解析结果；改变全局设置或专家目录不能重新解释既有执行。宿主捕获检查原调用正文属于当前活动执行；缺少新必需字段拒绝加载。当前已完成配置捕获，不能据此宣称原执行的运行时租约、流监听或冷调度已经恢复。真正 Provider 控制器与任务记录控制器具有不同构造来源，执行限制须按实际消费者继续核定。

### 9.43 已准备原生业务的冷执行交接

启动修复在终态回流核对之后选择仍活动的原父预留及开放子业务。已经具有进程内活动所有者的子任务直接跳过，不能对其正常在途 API 做冷来源校验；真正冷候选要求完整可靠历史、原根输入、原捕获配置及没有未确认外部工具效果。

请求构造复用子会话当前宿主端口，明确选择业务用途，恢复原模型、连接、工具来源上限及固定提示；知识权限与当前授权求交。准备完成后，在父子规范生命周期锁内重查注册表、预留、开放回合及捕获配置；恢复原公开名称和执行身份，安装既有分离事件监听，再交给与普通委派共用的运行循环和终态处理器。整个过程不创建新根输入、不再次委派、不新增父完成义务。

恢复后的再次准备及压缩保持当前已经收窄的权限和工具上限，新委派则清除父请求上的恢复身份。运行时排他认领拒绝相同执行的重复启动，不能利用底层槽位替换中止已有所有者。监听拒绝必须释放活动租约并沿已有失败清理回流；首次准备前缺少捕获配置、未激活预留、主会话冷执行和全生命周期收敛仍需独立完成。目前定向验证不构成完整冷恢复验收。

### 9.44 交接前恢复准入的回滚

恢复必须在同一任务事务内检查常驻记录缺失、认领活动租约并安装新记录。已有记录直接拒绝，不能先修改其执行归属再拒绝。只有本次新安装的记录获得准入守卫；正常后台交接后放弃回滚责任，交接前失败或栈展开则先清理内部流及租约，再撤销本次投影。

回滚按既有关闭代理路径的顺序取得代理登记与任务记录写锁，同时验证任务、执行、公开名、父及根归属。不存在登记是尚未发布投影的明确阶段；存在时必须使用精确叶子移除契约，不允许删除不同归属、状态冲突或具有后代的登记。活动执行、用户停止和替代执行保持原状态。判断依据是准入守卫持有的创建所有权，绝不把任意 Failed 记录当作允许重启的业务。

### 9.45 子文档创建前的准备契约

原调用、解析结果、模型连接、工具来源上限、提示输入及非敏感覆盖通过 `ChildExecutionPreparation` 保存；它包含真实物理 UUID 与原执行身份，不包含尚未分配的业务回合和代次。运行时端口与持久领域使用同一类型，避免复制定义时丢失字段。

可信宿主校验活动执行归属后，使用实际子文档的回合与代次绑定生成 `ChildExecutionProfile`，继续通过文档的捕获校验提交。绑定本身不改文档、不重新解析默认值；严格拒绝未知字段和缺少必需配置。该类型目前已接入原捕获路径；父侧提前保存创建意图、子文件首次发布与重启补建仍需接线，不能以可序列化类型存在替代恢复验收。

普通可靠启动在父侧预留后执行准备及子配置捕获，成功后才激活预留；缺少捕获宿主、准备失败或捕获失败均通过原启动守卫终止，不进入激活。已经生成的启动结果直接交接共用执行器，预压缩及模型执行仍等待后台所有权交接。此顺序阻止新业务在缺少配置时进入 Active；Reserved 阶段及子文件创建之前的可靠意图仍需独立接通。

### 9.46 初始子创建来源与父侧义务

`prepare_initial_child_creation` 用真实根输入和 Running 转换构造尚未发布的初始子文档，随后绑定准备配置；返回文档及 `ChildCreationIntent`。创建来源保存原配置、项目和创建时间，冷重建重新走相同分配器，并拒绝无法复现的回合或代次。此契约只用于初始创建，不得用于覆盖续跑子任务的历史。

父文档 `reserve_child_creation` 将该来源与已有 Reserved 子任务义务放进一个失败原子的修订，原完成门直接识别此义务。来源不可变，精确重试不增加修订；没有创建来源的普通预留不能事后补造成初始创建。重载检查来源与父身份、父代次、子执行、子参与者、根、项目及子代次的对应关系，拒绝孤立来源。新契约必需包含创建来源集合，不提供历史缺字段兼容。

分叉和编辑建立新事件树时清空创建来源；显式协作归属清理与清空预留一起移除来源，并把原协作覆盖范围标为只读历史，避免重载再要求已清除的活动操作。当前已实现领域契约；宿主实际发布仍须接入“可靠父预留及来源先于子文件”的顺序，启动扫描须继续补建缺失文件及处理 Reserved，不得将领域类型和内存重载测试称为完整崩溃恢复验收。

运行时准备已拆成解析阶段与准入后启动组装阶段，模型配置、请求及工具快照由同一对象跨阶段保留；解析阶段提供可序列化创建来源，不执行宿主文档捕获。实际提前发布接线必须覆盖父侧已提交但监听尚未准入时的取消，不能把尚无监听者的中止事件当作已经可靠结算。创建来源是恢复事实，不是独立启动授权；宿主仍需校验原父预留的当前状态、运行控制、规范代次及排他运行归属。

### 9.47 已保存配置的预留准入与缺失初始文件

已存在子文件且保存了原执行配置的 Reserved 任务进入实际恢复准备。当前宿主重新授权准备成功后，父子生命周期锁内重查原预留及准备配置，使用原预留操作 ID 的激活阶段可靠发布，再交接恢复执行器。缺少配置或保留的是上次执行配置时，不凭 Reserved 状态推测可执行来源。

树扫描只对存储层类型化的会话缺失错误尝试补建，其他读取失败保留诊断。补建要求唯一仍预留的初始执行、完整可靠创建意图及原父开放业务回合；沿已发现的精确祖先链加载规范父，按根/父/子 UUID 顺序持有生命周期锁，重查根父代次、归属、运行控制和活动租约。用户停止、归档及进程内活动所有者阻止补建。初始文档从原意图重建，使用现有暂存目录原子发布器；已有目录必须按存储契约核对，不能覆盖。发布后继续经过既有规范加载及已捕获预留准入，不直接调用供应商。

以上接线不代表普通启动已使用父先子后发布；该生产者、监听准入前取消责任、续跑历史以及完整恢复验收仍需完成。

### 9.48 普通初始创建的可靠发布及监听交接

普通初始派生在发送 DelegateStarted 之前冻结同一次模型、工具与请求准备结果，通过可信宿主 `create_child_task` 传入原工具调用预留和初始配置。宿主校验实际运行时事实、原父 API、根/项目与代次，按根父子 UUID 顺序持有生命周期锁，先可靠保存父预留及创建意图，再使用既有原子发布器写出带完整配置的子文档。只有子文件发布并取得精确规范句柄后，才允许监听接管。原准备对象继续用于后续执行，避免跨阶段再次选择不同配置。

初始创建与续跑按实际 `is_resumed` 分支，续跑仍从既有子历史追加业务输入，不允许套用初始重建。展示启动事件仍保留原投影屏障，但不再承担初始持久身份的首次创建责任。

监听采用严格活动流订阅：开放状态校验与订阅者登记使用同一个流锁。取消先发生则宿主明确拒绝，取消后发生则已登记监听取得中止事件。宿主初始发布在领域真正接纳精确意图后才取得失败清理权威；文件或监听失败时使用原子回合归属闭合已发布子任务，并将原父 Reserved 义务以启动失败结算。该阶段没有子文件也可结算，且不伪造 Active；冲突意图、替代代次和已经激活的执行不得被误终止。

此节为当前已接入的生产路径，验证进展以实施报告为准。完整取消、停止、续跑、主业务冷恢复及最终全范围审核仍须独立验收。

### 9.49 文件准入与续跑的单文档原子边界

初始子文件发布在注册表加载准入内部执行。注册表已经关闭或删除接纳被封闭时，在写出首次子文件前拒绝；若文件已写出而注册表随后拒绝，创建者仍保留该精确句柄并尝试闭合原回合，错误同时保留发布及清理原因。已有规范句柄的快速返回必须重新核对定位器、原执行配置、运行控制及活动请求，不能以物理 UUID 相同代替业务归属证明。

续跑子文档的旧物理请求中断、旧业务回合停止、新根输入与 Running 控制必须在同一次原子修改中发布。新输入被拒绝时，旧请求、回合、事件、修订和元数据都保持原状。精确重放只校验已有输入，不重新停止当前任务，也不恢复被用户停止的控制状态。此约束解决子文档内部失败原子性；父侧续跑意图先于子侧变更以及跨文档恢复仍为独立必需工作，不据此宣布整个续跑准入完成。

### 9.50 基于精确已有历史的续跑来源

执行创建意图具有必需的初始或续跑模式。续跑来源保存子文档原修订、由实际已有分配器获得的新回合、完整配置、项目及原准入时间；模式不可省略，不提供历史字段默认值。初始重建入口明确拒绝续跑意图。

正常可靠执行统一在 DelegateStarted 前准备并调用宿主发布。续跑宿主在生命周期锁内读取规范已有历史，在副本上分配后继，随后先可靠提交父预留及不可变来源，再原子发布子侧后继输入、旧请求中断、旧回合停止、Running 与新配置。监听交接和失败清理继续按原精确执行归属处理，不重新解析准备快照。

启动树加载对仍 Reserved 的续跑先验证根与父的当前控制、开放回合及完整记录，随后在通用进程中断恢复之前应用原后继来源，避免通用恢复先改变来源修订。已经有进程内运行所有者时不重复发布；子来源修订或代次变化时明确拒绝，不覆盖变化历史。已发布同一配置的重试不增修订；实际执行仍走已有恢复配置、激活与监听交接。源码已接入，完整验证以实施报告为准，不能据此省略全树停止、并发替代与其余原验收要求。

### 9.51 主业务原归属的启动恢复

启动筛选读取既有元数据的开放回合序号，作为独立于消息出站箱的待办线索。后代恢复及回流修复完成后再检查原索引根；实际执行权威来自完整可靠文档，不来自筛选快照。已停止、归档、物理请求或辅助执行占用的会话不进入自动主业务准备。

恢复保留原业务回合、原 Hook 身份、原清理后输入及有序观察记录；精确持久化修订防止旧请求在后续业务推进后再次取得准入。未确认的工具外部效果明确阻止自动执行，缺失原 Hook 不允许从内部提示合成替代身份。

恢复沿原提交互斥、目标项目水合、内核登记及异步准备链执行。内部准备类型明确标识主业务恢复，消息来源沿用不追加人类输入和新回合的续跑语义。只发布目标切片，不改变界面当前选择。已有可靠恢复候选却因准备繁忙未启动时必须保留重试责任，不能把 false 当作恢复完成；下一轮重新检查当前可靠状态。第一次 Hook 尚未保存的窗口和完整停止树仍需独立闭合，验证结果以实施报告为准。

### 9.52 首次用户观察的发布顺序

共享准备构建 Hook 身份和不可变观察请求时不运行用户观察器。实际主会话提交、目标续跑和精确排队准备先可靠保存原 Hook，再由宿主释放延迟的 conversation.user.event 请求。保存或同步失败时不能释放观察；临时答疑、同业务协作续跑和已有规范批次不生成额外首次观察。

克隆的准备对象共享一次性进程内派发准入，外来 Hook 身份不能释放请求。观察仍使用原异步调度与失败诊断机制，此顺序约束不等同于跨重启恰好一次的外部效果保证。首次业务恢复仍须证明原回合的准确起点及尚未执行状态，不能以没有物理请求替代生产者的发布顺序证明。

### 9.53 业务输入的实际分发确认

分发确认只接受同一回合中严格晚于输入序号的业务 ApiStarted。压缩和临时答疑即使读取了该输入，也不构成业务已分发的凭据。外层快速返回、内部准备权威和准备繁忙后的复查必须遵循同一规则；物理占用只阻止并发，不自动等于业务启动成功。

该查询不授予执行许可，也不证明任务完成；调用方仍负责原输入、回合、代次及当前准入校验，并提供完整相关历史。当前修复及逐入口验证进展见实施报告。

排队后继、原根与回合内方向输入遵循同一规则。排队后继的历史回执仍可查询；一旦业务请求已经覆盖其输入，外层重试确认原分发，不再次准备。排队准备取得提交预留后也须再次校验物理空闲及业务未分发，防止较早读取的身份快照被误用作新的执行许可。

### 9.54 原人类输入的首次准备

启动扫描明确区分已有本回合业务身份和从未发布的首次人类准备。首次来源凭据由完整可靠历史产生，包含会话、代次、修订、原回合、原输入序号和完整强类型输入，只接受 UserRoot 下的 Root 或 QueuedScheduled 起点。停止、归档、子执行所有者、活动物理或答疑执行均不能取得首次准入；已有业务请求、委派记录或未确认工具效果也不能因缺少 Hook 而重新准备。

目标按自己的项目索引水合，原资源引用通过所属项目资源目录解析。在共享提交预留内以及创建 Hook 前重新核验完整凭据。只有从未发布的进程内准备残留允许清理，清理不发送完成或观察事件；已发布身份继续沿原 Hook 恢复。首次准备复用原规范输入，不追加用户消息或新回合。

目标切片发布与异步准备沿正常失败结算边界，预检计划由实际来源决定。首次人类输入保留用户预检；代理任务和业务续跑保持各自来源策略。没有取得准备准入时保留启动重试责任。目标、代理任务和子回流的首次初始化接线属于各自领域来源，不能套用人类凭据；当前实现与验证范围见工作报告。

排队输入只有在本次新提交确实替代 Goal 并生成用户后继时，才与后继原子发布 Running。普通队列接纳不修改运行控制；精确重试保留后来的停止状态，不能通过重复旧动作再次唤醒会话。冷恢复只使用已经可靠发布的许可，不负责临时补造运行状态。

### 9.55 Goal 重启暂停与独立业务归属

沿用既有 Goal 规则：进程重启后，活动 Goal 转为暂停，等待用户显式恢复。自动恢复扫描不将这个暂停改回活动，也不为其创建新的推理执行。

中断投影因该规则关闭回合时，只能关闭 GoalContinuation 来源。已经接纳的 UserRoot、AgentTask 或 SubagentReturn 属于独立业务，不能因为同一会话仍启用 Goal 而被关闭。其活动物理请求仍按既有中断规则处理，之后是否恢复由各自可靠身份、运行控制和未确认工具效果判断。用户后继保留原回合与输入，Goal 暂停作为按顺序追加的模式消息进入原历史。

### 9.56 代理任务认领与 Hook 准备身份

代理任务第一次物理业务请求之前的准备重试，从同一次完整可靠读取取得原认领和 Hook 状态。已有本回合绑定时使用 Published 准备，携带原 Hook、有序观察及精确修订；尚未绑定时使用 Initial 准备，携带统一首次业务凭据。不得通过捕获缺失绑定错误来猜测分支。

通用首次凭据只证明尚未执行和归属允许，来源事件仍由对应入口验证：人类要求原 Root/QueuedScheduled，代理任务要求原认领效果、输入 ID、输入序号及 AgentMessage 类型。两者不能互换。此凭据为进程内临时对象，不新增历史兼容格式。

共享提交预留内重验完整代理任务权威，再恢复已发布 Hook 或清理未发布局部残留。已发布恢复使用 AgentContinuation，不再次制造任务输入观察；首次准备继续使用 AgentTask，不解析人类手动指令。辅助请求保留任务执行身份，但改变可靠修订，旧准备快照必须重新获取。当前实现与生产验证范围以工作报告为准。

### 9.57 子回流内部指令与用户观察分离

### 9.58 显式用户 Goal 激活的执行许可

用户保存并实际创建新的目标续跑回合、显式恢复目标、以及将暂停目标切换为活动时，模式与 Running 在同一领域原子事务和可靠修订中发布。许可操作身份来自会话、代次和本次规范转换通知序号。中途失败不得仅留下活动模式或单独运行许可。

### 9.59 内部续跑的首次准备与原身份恢复

Goal 与子回流准备在既有提交互斥范围内，通过一次完整可靠读取同时验证实际来源与主业务 Hook，随后才更新进程内所有者并同步活动观察日志。来源校验函数与常规读取入口共用；临时分发权威携带父历史代次，不能只凭可能重复的局部回合和序号跨代次使用。准备创建 Hook 前保留原来源复查。

### 9.60 本地维护摘要的实际执行边界

明确的答疑和压缩用途优先于子身份；网络重试保留辅助用途，也不能绑定业务继续动作。压缩的启动上下文保留原捕获温度，模型能力处理仍走实际准备规则；不支持显式温度的路线不能伪造原请求参数。已初始化的顶部固定宿主指引逐字节保留，测试原业务必须同样建立该基线。

### 9.62 远端检查点与本地摘要的持久化区分

压缩节点以 `content.kind` 明确区分 `summary` 与 `remote_responses`，不再使用单一摘要字段承载全部结果。当前未发布版本直接采用新结构，不迁移旧节点。远端类型必须保存完整有序规范输出、供应商、连接、协议、模型、普通 Responses 重放端点及实际上游响应 ID；原生项的字节内容不得替换为展示文案。

Core 校验其实际捕获的供应商、连接、协议和模型，并在封存来源事件不驻留时继续校验检查点结构。端点比对和真实返回来源由宿主准备/接收链负责；仅凭领域节点通过不能证明物理调用或后续重放已经完成。主、子入口必须在发送前可靠登记物理请求，在完整接收真实输出后提交节点；下一请求必须重建原生项并核对实际冻结路由，禁止丢弃检查点后只重放尾部。

### 9.64 每次压缩尝试的来源模式

宿主冻结来源区分未准备、本地完整、本地剪枝和远端原生前缀，四者互斥。运行时每次切换尝试先公布精确来源；来源事件只能选择输入，不能替代实际物理 API 的持久化准入。失败选择不改变此前有效选择，活动物理请求不能被替换来源。

远端原生模式要求来源逐行等于冻结规划前缀。截取以规划行对应的投影项位置为准，不能以事件序号大小推测顺序：已发布检查点位于保留历史之前，其成功终态序号却可能更大。物理请求及媒体准备都只处理选定前缀；准备证明仍保存真实当前可靠前沿，不能将截取后的可见范围冒充整个文档前沿。远端输入不追加本地摘要用途的控制文本，固定基线仍按原规则处理。

从远端切换到本地尝试必须明确替换来源模式，不能残留远端前缀长度影响本地完整窗口。是否允许该切换、每次 OAuth 真实重发的独立准入，以及远端成功终态与节点提交，由后续物理执行接线共同落实；本条的来源模式实现不代表这些剩余环节已完成。

### 9.65 远端单次传输的观察顺序

`stream_responses_compact` 是单次惰性 HTTP 流，只有开始轮询才会进行编码和发送；不持有 OAuth 刷新能力，也不自行重试。先产生真实响应头观测，再读取有界成功或失败正文，最后返回完整原生结果或脱敏失败。401 同样先产生观测，不能在刷新后抹去前一次失败。原一元调用共用此编码、传输与解析实现。

会话宿主必须在轮询前完成 API 可靠准入，收到观测后完成持久化屏障再继续轮询；OAuth 刷新后的再次发送需要新 API 身份及新许可。可选的线路追踪仅沿既有尽力写入契约保存最终编码请求，不是准入凭据。D325 的真实回环 HTTP 验证覆盖先头后体、请求正文一致、成功原生结果、401、错误脱敏和单次流结束；高层 OAuth 重试与主子完成器仍待迁移，不能据此标记远端全链完成。

主、子会话共用提交校验：本地结果必须逐字匹配同一 API 的助手语义，且语义序号先于统计终态；远端结果必须匹配已接收原生内容、五项路由身份和响应 ID，使用同一 API 统计终态序号提交。两种结果互斥。远端诊断文字只进入展示用途，不承担可靠历史语义。

### 9.67 原生成功遥测

原生成功使用独立输出种类，不能借普通助手完成的重放来源。当前会话入口必须具有已确认的活动物理请求、明确压缩用途、精确 Codex 协议及实际成功 HTTP 响应头；若出现可见助手 Token、失败状态、未确认准备或身份不符，拒绝时保留原活动请求的失败/取消责任。

不透明原生结果视为已观察到影响重放的输出，但没有首个助手 Token，也不生成工具调用、对话来源或延续资格。401 失败先结算，再为刷新后的实际重发申请新请求身份；每次的用量和终态独立。D327 已验证遥测状态机，尚未由实际远端发送侧调用，不能将此处的准入状态测试当作宿主可靠许可或真实 OAuth 网络重试证明。

### 9.68 准备许可的取消责任交接

会话 API 一经可靠准备成功，消费方立即接管取消责任，再释放发送许可。不能等待生产者回送普通开始遥测才接管：接收端可能在交接时被取消，后续所有者检查也可能拒绝发送，已经提交的 API 仍需要明确结算。主会话、分离子代理和上下文压缩使用同一交接方法。被拒绝、配置发生变化以及明确排除的非会话许可不激活会话取消责任。

尽力转发开始遥测仍不能自行授予发送或取消归属。已准入请求收到匹配身份的首 Token 时，取消跟踪保留时间及输出已观察证据；其他请求的首 Token 不污染当前活动请求。物理终态清除相同身份的取消责任，避免重复合成终态。此交接只补齐遥测取消与用量责任；可靠文档中断仍由原会话/维护所有者按既有顺序执行，不能以遥测代替领域持久化。

### 9.69 主子会话的远端发送所有权

### 9.70 根物理删除覆盖全部嵌入所有者

递归删除的范围由 SQLite 定位的精确根及存储门面声明的嵌入目录决定，不由当前业务代次的父任务记录决定。代次切换会清除当前协作记录，但不会自动删除历史子文件。存储门面仅沿自身固定布局枚举并验证元数据身份，遇到不规则目录、重复身份或不可读元数据明确拒绝删除，不忽略条目或搜索替代位置。

服务将根与全部物理后代按会话身份统一排序获取生命周期锁，随后再次检查物理集合。每个冷态成员完整加载并核对身份，驻留成员必须持有同一精确定位器；任何成员存在未结协作即拒绝根删除。全部成员封存、刷写并再次核对物理集合后，才注销规范句柄并执行物理删除及 SQLite 行删除。删除前失败逐个回滚已封存所有者；开始物理删除后的失败或取消保留墓碑，避免旧写入者重建可能已经部分删除的目录。

### 9.71 目标结算回执的跨会话删除保护

目标本地已有终态结算，不代表来源已经可靠取得该结算确认。根删除前必须保留树内目标的终态回执，直到仍可寻址的同代次来源已经保存匹配确认。删除锁集合因此包含所有入站投递的来源及其根身份，与物理删除成员统一排序，取得锁后再次核对对端集合；只读对端不参与封存或删除。

检查精确问题和投递身份、双方参与者、结算状态、来源事件、目标结算事件及确认修订边界。缺少来源确认时拒绝目标删除，由既有结算或恢复流程补齐，不在删除入口取消问题、自动作答或合成确认。来源根已不在 SQLite 时不扫描、不重新创建；仍有定位但读取或身份冲突时明确拒绝。更高来源代次只有在 Core 原有未结协作保护允许编辑后才合法存在。同代次缺失原问题或出站记录不能当作已结算。

外部冷态来源采用完整文件读取，不为一次检查发布运行时初始化不完整的句柄；物理删除树内需要注册的成员保留普通冷启动中断恢复和根用量初始化，保证删除拒绝后仍可正常使用。D331 已验证归档冷态下的本地用户撤销重放、两个正常删除顺序及迟到撤销拒绝；模型回答与代次编辑的完整交互证据仍需后续补齐。
