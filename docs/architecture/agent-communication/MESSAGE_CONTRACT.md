# 代理消息与工具契约设计

> 对应[正式总计划](../../plan/20260920-04-AGENT_COMMUNICATION_AND_DYNAMIC_CONTEXT.md)。状态：实施中。设计契约与实现完成情况分开记录；当前证据见[工作报告](IMPLEMENTATION_LOG.md)。

## 一、身份与关联

宿主根据当前执行上下文确定发送者；模型只能选择获准的目标和填写正文。不得允许模型填写另一个会话作为自己的来源。

| 身份 | 语义与权威 |
| --- | --- |
| 会话 ID | 宿主会话目录中的真实稳定标识；标题和别名只用于显示。 |
| 项目归属 | 服务侧目录和已验证项目记录；不能依据标签、显示用 `project_tag` 或任意路径相似性授权。 |
| 任务关联 | 当前执行所属业务任务及其父级归属。普通会话与子代理使用各自真实类型，不要求为普通会话伪造子任务 ID。 |
| 逻辑 turn | 业务处理和最终回复的边界，可能包含多个物理 API 或暂停恢复。 |
| 执行/API/工具调用身份 | 绑定一次真实操作和回执；不同会话的工具调用 ID 不可交换。 |
| `operation_id` | 宿主在发送副作用前绑定真实调用的稳定操作标识；同一次操作重试必须复用。 |
| `delivery_id` | 一次投递的稳定标识，用于目标幂等接纳与消费位置。 |
| `question_id` | 问答事务的稳定标识，绑定提问者、收件者、问题和结算；不等于工具调用 ID。 |
| 修订与代际 | 区分同一事实的状态修订、文档历史代际和物理执行代际，禁止将迟到消息投到另一个新任务。 |

以上标识由宿主保存和校验。模型可见信封携带理解任务所需的子集；完整授权与关联不依赖正文解析。

协作消息即使投影成 User，持久事件也保留 `AgentMessage` 来源。用户输入中出现同名标签不改变其真实用户身份。显式等待每次读取新正文时重新校验来源拥有的当前跨项目授权，不能用等待开始时的许可无限读取后续答复。

## 二、消息种类及回复规则

| 逻辑种类 | 接收方行为 | 结束与回复 |
| --- | --- | --- |
| `task_start` | 接纳一个业务任务；目标繁忙则进入明确任务队列。 | 最终 Assistant 由宿主绑定该任务回流；无需收件方再向发送者确认收到最终结果。 |
| `task_steer` | 在下一合法 API 边界调整仍活动的原任务方向。 | 不取消当前执行，不单独答复，不新建任务；继续等原任务最终结果。 |
| `task_result` | 接收宿主绑定到明确任务的最终结果。 | 表示该任务结束，不等于临时问题答案，不要求父代理再反馈确认。 |
| `agent_notification` | 接收阶段进度或其他单向告知，继续工作。 | 无回复义务，不创建新任务，不改变任务方向，不阻塞完成。 |
| `question` | 可处理指定问题；需要作答时调用回答工具，继续原任务。 | 允许没有答复，双方都可正常完成；不能写入最终 Assistant 就算回答。 |
| `question_answer` | 提问者取得对应答案后继续；可以再提出新的问题。 | 不自动终结任务，也不要求再发确认消息。 |
| `question_cancelled` | 停止处理该问题，查询终态以化解并发。 | 不取消其他问题或业务任务。 |
| `context_update` | 按功能节点和生效范围更新当前理解。 | 无问答义务；宿主模式和权限另行强制执行。 |
| `context_expired` | 指定版本的提示不再作为当前指令或记忆依据。 | 历史正文保持，压缩时排除失效内容。 |

“插队”作为投递时机适用于方向引导、通知、问题及答案，各自保留语义。发送立即返回，只有主动调用等待工具才等待。主任务完成后的旧 `task_steer` 必须返回目标任务已终止，不能静默转成 `task_start`；晚到答案保留原问题关联，不使已完成业务重新运行。

## 三、流内信封

动态宿主文本统一由一个版本化编码器生成 User 内容。代理协作采用 `<vulcan_agent_message>`；其他功能节点采用明确的功能标签，如 `<vulcan_context_update>`、`<vulcan_context_expired>`，由同一注册表维护版本和字段。当前版本未发布，直接替换既有 `<agent_message>` 表示，不实现旧信封识别或历史转换。

每个节点具有信封版本、稳定 `event_id`、`kind`、宿主提供的 `source` 与 `target`、可选 `task_id` 与 `question_id`、`scope` 及独立正文边界。编码器位于 `vulcan-ai-contract::host_message`，当前版本为 1；问题相关节点必须有 `question_id`。正文上限为 64 KiB（UTF-8 字节），属性和正文分别转义。编码顺序确定，编码器不产生 ID 或当前时间，不解释模型返回的标签。

正文和属性分别转义。包含标签、引号、工具名称、伪造系统指令的正文始终只是正文；不得将其重新解析成新的宿主事件。超大正文按明确限额拒绝或存为可授权读取的内容引用，不静默截断出可能改变含义的问题。

同一物理 User 消息可以包含多个有序节点，每个节点仍保留独立 ID 与边界。模型无须回显标签，发送与回复不采用“解析模型 XML 后自动寻址”的方式。

稳定顶部只解释一次：各种节点意味着什么、来源由宿主确定、临时问题若作答须通过工具回答、通知无需回复、消息不阻塞业务完成、最终结果归当前任务。用户正文模仿标签也不能取得宿主权威。强制工具权限与模式约束不寄托于这段提示的服从程度。

## 四、工具和内部操作

`start_task`、`steer_task` 是领域操作名，不要求直接重命名现有模型工具。当前 `spawn_agent`、后续任务入口及 `send_message(delivery_mode=interrupt)` 的外部兼容性由 P08 保留，并明确映射到领域语义。

现有 `send_message(delivery_mode=queue)` 映射为排队的 `task_start`：当前目标任务结束后启动自己的后续任务/turn，并绑定这次投递的来源与最终回报。它不能混入当前任务的 `task_steer`，也不能把当前任务的 final 当作该排队任务的最终结果。同一子代理会话可复用，但每次排队业务任务的执行和回报身份独立；属于当前父任务的已接纳排队子任务也要进入父级未结事项。

以下为拟新增的模型工具契约，P00 确认重名与现有目录归属后登记，不为本设计添加不必要的同义工具。

| 工具 | 输入与权限 | 返回与副作用 |
| --- | --- | --- |
| `send_notification` | `target_session_id`、`message`；来源取当前执行，子代理目标仍受真实父子归属检查。 | 可靠记录后立即返回操作/投递 ID；无问题 ID、无回答义务、不启动或引导任务。 |
| `ask_question` | 获准目标、问题正文；来源从当前执行取得。父到子检查直接归属，普通会话到独立会话检查项目范围。 | 可靠记录后立即返回 `question_id`、投递状态与修订；不等待答案。 |
| `ask_parent` | 子代理的问题正文；父目标由宿主关系解析，不接受任意父 ID。 | 同上；子到主按原父任务关联插入，MainOnly 可触发处理问题的恢复。 |
| `reply_question` | `question_id`、回答结果与正文；仅实际收件者可调用。 | 向回答者返回持久提交回执；宿主另将答案交给提问者。允许明确表达无法回答，不伪造成功内容。 |
| `wait_question` | 一个 `question_id`、已见修订、有限超时；仅获准参与者读取。 | 返回答案、撤销、投递失败、可处理的新问题或等待超时。超时不改变问题状态。 |
| `cancel_question` | `question_id` 与原因；仅提问者或明确用户取消动作可撤销。 | 返回权威结算状态；与回答竞争按提交次序处理。 |
| 会话协作工具组 | 列出、读取、向已存在会话启动/引导、等待；具体名称在现有目录核对后冻结。 | 有界目录/历史、稳定 ID、游标和明确投递回执；不承担创建新会话的隐式副作用。 |

不得开放通用人类 `ask` 代替 `ask_parent`。人类问卷的拒绝会中断运行，与代理取消问题的语义不同。

#### 任务消息持久意图与接纳（2026-09-21）

`CollaborationTaskMessage` 独立承载 `task_start` 和 `task_steer`，保存投递 ID、来源操作、双方参与者及正文；不复用通知记录，不生成问题 ID。`task_start` 的目标参与者没有当前回合绑定，后续调度必须为其分配独立业务执行和结果关联；`task_steer` 必须携带精确目标回合，接纳时拒绝已经结束、变更或仅答疑的回合。

来源 `outbound_task_messages` 保存原始意图及可选的精确目标确认；目标 `inbound_task_messages` 保存原始接纳操作、修订和事件坐标。来源记录、目标接纳、来源确认是三个分别提交的步骤。相同操作重放返回该操作原始回执，不能把后来增加的确认当成最初发送结果。目标按投递 ID 去重，即使恢复使用另一接纳操作 ID，也不能再次接纳；正文或绑定冲突明确拒绝。接纳回执不表示已经开始、已经投影或已经完成任务。

目标将接纳与实际处理分开保存：`task_message_effects` 记录方向已应用或应用前明确失败。方向应用使用既有 `<vulcan_agent_message kind="task_steer">` User 信封，输入及宿主效果回执共用一次修改修订；它不关闭原业务回合，也不是任务最终回复。已应用方向不能改写为失败；失败消息不能再次应用；重试返回原回执。

当前已增加持久意图、接纳、确认及目标方向/失败领域处理，发送工具已接入来源记录、目标接纳和来源确认，方向进入请求边界候选。真实队列认领、最终结果冻结及来源接收/目标内部确认已接入；模型实际消费、应用前失败效果的来源回流、完整恢复和既有父子义务统一仍须继续实现。未处理或未确认记录继续阻止编辑/物理删除，不能因目标已有处理结果就丢失来源恢复所需凭据；所有协作完成后的保护收敛仍待独立验收。

发送工具回执包含 `status=recorded|accepted`、`operation_id`、`delivery_id`、`message_kind`、来源 `record` 和可选 `delivery_error`。`accepted` 只表示来源已确认目标接纳，不表示排队任务已启动、方向已投影或业务已完成。同一次操作重试使用首次来源意图，不能根据目标新回合改写原方向绑定；相同调用更换正文、目标或模式明确冲突。来源发布后的投递失败仍携带原身份供恢复，不能诱导分配新操作重复发送。

#### 任务最终结果的目标权威（2026-09-21）

`CollaborationTaskResult` 在原业务闭合时冻结，携带原接纳、应用效果和真实终态；成功的 `final_assistant.source_text` 是唯一完整原始 Assistant 快照，附带精确 API、正文事件和统计事件坐标。停止或放弃没有伪造的 Assistant。它独立于接纳/认领回执、临时问题答案及任何新业务，不要求请求方模型再确认收到。超长原始正文完整保存，后续投影分块需保持可重建坐标。

`task_result_recorded` 展示为“代理任务结果”独立卡片，结果来源是执行者，接收者是原任务请求者。已完成、已停止、已放弃分别展示，不继承问题撤销控件、不显示成人类输入或当前主助手最终输出。该事件是目标结果权威；来源使用下述独立接纳事件，不复用目标本地坐标作为来源事件。

原请求者的 `task_result_accepted` 同样展示精确结果；执行者的 `task_result_acknowledged` 只展示“任务结果已送达”，不重复显示回答正文，不要求模型回复。这两个事件分别证明来源可靠接收和目标已保存接收确认，不代表模型已看见。接收接口接受迟到的原任务结果，但不把它重新绑定到当前新任务。

结果投影按接收会话的可靠接纳事件序号生成稳定块键，不能拼接不定长原投递身份作为输入动作 ID。每个 `task_result` 信封的正文第一行是固定结构的 JSON 元信息，含原投递、原业务回合、原终态、来源正文事件序号、块序号/总数、原正文总字节数及本块字节区间；第一行之后是原始正文片段。区间按 UTF-8 字节计量，边界必须落在完整字符之间。停止、放弃及合法空正文仍产生一块明确事实，不伪造文本。头部计入 64 KiB 正文预算；渲染时的 XML 转义仍由统一信封处理。

这种分块是固定版本的表现形式，不能由模型提供的标签或 JSON 构造任务权威。接收侧须依据持久结果记录验证整组分块，并在同一合法边界处理投影；记录部分投影进度和重试身份的具体接线仍属于实施工作。模型不用回发确认。

#### 独立会话等待的冻结回执（2026-09-21）

`wait_session(session_id, after_revision?, timeout_ms)` 只观察已有会话，不启动或结束业务。`after_revision` 省略时以本次第一次读取的可靠发布修订为基线；传入时使用调用者原游标。普通回执包含 `status`、`wait_status`、`session_id`、`project_id`、`after_revision`、`document_revision`、`segment_generation`、`next_seq`、`open_turn_start_seq` 和 `operation_id`。`wait_status=changed` 仅表示有新发布事实，不代表任务完成；调用者通过 `read_session` 读取事实并保留自己的事件游标，不能把新的 `next_seq` 直接当成已消费事件范围。

等待过程中发现代际改变或发布修订倒退时返回 `wait_status=reset`，供调用方重建读取视图。当前输入只有修订游标，代际比较范围是本次等待内部；跨调用的历史重建仍需结合读取返回的代际事实，不能宣称单独修订游标能识别所有历史重置。

反向问题优先返回已有问题回执，额外保留 `waited_session_id`、原基线 `after_revision` 及 `wait_status=incoming`，不把问题自身修订用作原目标的新游标，不消费或提前投影入站消息。超时返回 `status=timeout` 和 `wait_status=timeout`，不修改任何会话、问题或授权。跨项目读取权限在每次持久前沿读取前后重新核对；存储读取或授权失败明确返回错误，不用内存修订代替可靠发布。

长等待的来源必须仍是注册表中的同一规范句柄；来源被移除或替换后拒绝继续观察。跨项目读取授权的创建修订必须已经可靠发布，撤销从当前内存事实立即生效；不主动刷写未发布授权来让等待通过。

实际工具名称、说明、参数描述和错误使用英文。本文用中文描述其含义。完整实现必须覆盖注册、请求构建、模式可见性、策略过滤、执行准入、事件持久化、结果投影与界面。

## 五、固定发送与接收

原生所属子任务的非成功报告使用 `child_task_non_success_recorded` 宿主事件，后状态仍属于原 `child_task` 预留；它不伪装成独立会话任务消息接纳。`non_success_result` 保存原子执行、子文档代次、业务回合、根输入及终态序号、真实闭合结果、宿主结果分类、永久错误诊断与父发布修订。正常停止允许没有错误诊断；失败必须有精确来源错误证据。父侧领域发布已与终态原子绑定，前端使用独立代理结果卡显示真正来源子会话及原诊断。可靠报告通过 `task_result` User 信封无损分块追加，块头声明 `child_non_success_json` 编码、块数和字节坐标；`non_success_projection` 独立记录整批输入及 `child_task_non_success_projected` 事件，不修改原报告回执。业务消费必须晚于全部输入，辅助 API 不消费。实际分离终态已接入此报告，成功、失败和停止的邮箱反馈均等待父结果可靠发布。启动中止使用带原执行身份的明确控制事件，按准入时捕获的原回合处理；已预留任务同样可靠发布非成功报告，未预留任务仅清理准入资源。完整停止树与恢复尚待完成，不能把宿主报告已保存等同于模型已收到结果。

1. 来源操作先取得宿主身份、目标、任务关联和稳定操作标识，经过权限与目标状态检查。
2. 将操作和待投递事项可靠提交后返回接纳回执。该回执表示宿主已记录，不表示对方已看见、已回答或已完成任务。
3. 目标按稳定投递 ID 接纳，在下一合法边界投影 User 信封。原生工具组未满足结构要求时延期，不前移到顶部。
4. 模型回答问题时调用 `reply_question`。回答方的工具结果只确认提交，不复用为另一会话的工具结果。
5. 提问者有真实等待调用时，可由该等待工具交付原生结果；没有等待调用时，追加答案 User 事件。宿主记录交付途径及修订，一次答复不同时产生两个新的通知事件。
6. 再次按 ID 查询可以返回同一历史答案，明确标记已有结算；查询与新投递区分。原 `ask_question` 的已完成工具回执永不回填改写。
7. 最终 Assistant 通过任务绑定回流，与问题回答分开，不要求父代理反馈确认。

## 六、权限与状态矩阵

| 场景 | 准入与调度 |
| --- | --- |
| 运行中父问子 | 归属校验后记录问题，下一合法边界交给子；回答工具回复。 |
| 运行中子问主 | 绑定原父 turn；主若在等待，立即返回可处理的问题。 |
| MainOnly 下子问主 | 允许接纳并自动恢复主执行处理问题，保留原父任务关联；不自动解除其他暂停权限。 |
| 自然完成且空闲目标 | 获准后启动仅答疑执行；已完成业务任务保持完成。 |
| 停止的目标子代理或独立会话 | 拒收新问题，返回目标已停止；不创建等答案的已接纳问题。 |
| MainAndSubagents 已取消全树 | 不存在仍有效的子到主恢复资格；迟到旧消息返回原任务取消或失效状态。 |
| 同项目独立会话 | 按宿主项目身份允许规定操作，并保留来源记录和有界读取。 |
| 跨项目独立会话 | 用户授权后才允许其动作范围；模型不能通过文本或工具自批权限。 |
| 尝试绕过父子策略 | 即使同项目，也不能将受限子会话改称独立会话放行。 |

授权记录至少保存真实授权主体、来源范围、目标范围、允许动作、创建与撤销修订。唯一权威保存在获授权来源会话的 V1 协作 metadata，由用户服务入口创建和撤销；目标不复制第二份授权，模型工具只能消费已有授权。发送准入与真正正文交付均检查仍有效的授权；终态查询和明确取消仍保留必要的收敛路径。

## 七、错误与边界

- 目标不存在、归档或删除：明确拒绝，不按标题寻找近似目标。
- 来源会话归档后仍允许已接纳问题的受控结算和查询，不自动启动来源模型；存在未结协作时不得直接物理删除来源权威，须先完成显式取消/结算流程。
- 同一操作重试：相同键、目标和正文返回原回执；冲突明确报错。
- 执行回执不确定：携带已有操作身份供查询或恢复，不盲目发起新的问题。
- 收件者不匹配、旧任务代际、已撤销或已回答后企图改答：拒绝并返回可查询的权威状态。
- 目标在接纳后停止：保留已接纳事实，通知提问者目标停止；提问者可显式撤销，不伪造答复或静默转为恢复队列。
- 反向问题打断等待：返回可行动的问题引用，保留原等待目标和游标；不把问题当作任务终态。
- 等待超时：只结束本次等待，不结束任务、不取消问题、不更改授权。
- 新模型调用主动再次提问不等于旧工具调用的重试；不得单凭正文相同去重两次真实意图。

## 八、界面与资料要求

普通用户输入、动态上下文、代理消息、问题、答案和任务结果分别展示来源类型。代理交互使用独立框体及清晰的来源、目标、消息类型，视觉上区别用户提示词；不因模型协议采用 User 角色就显示成人类输入气泡。消息卡展示可导航的真实会话与任务关联；`question_id` 等技术字段可置于详情，不要求用户手工填写或解析标签。未答问题不能显示成阻塞业务任务；阶段通知不显示等待回复状态。

代理间问题通过协作事件和工具卡展示，不进入面向真实用户的 Ask 弹窗队列。确实需要用户决定时仍使用独立的人类 Ask 契约，不能让界面代替另一代理回答。

答疑结束后选定排队任务的 `question_successor_scheduled` 是宿主调度事件，使用“已调度排队任务”标识；其 `queued_successor` 指向真实用户输入。该事件不是问题答案、不是原任务再次结束，也不创建新的伪用户正文。实际排队用户输入继续保留原用户动作和输入身份。

状态显示至少区分已记录、目标已接纳、已进入请求、已回答、已取得、已撤销和失败。模型是否真正理解内容不可由“已进入请求”推定。翻页、重连和多个窗口以持久记录查询，不争抢一次性消息。

### 当前界面实现边界（2026-09-21）

- ChatArea 使用的分支时间线与事件原生时间线共用 `conversation-collaboration-card.tsx`。分支适配器将协作与子任务结果保留为强类型 `agentInteraction` 展示记录；该记录不是持久化权威，也不从 XML 标签或正文识别角色。
- `input_source=agent_message` 是协作事实的供应商镜像，两条时间线都不将其重复显示为人类输入。真实根输入继续使用用户气泡及原有编辑锚点。
- `subagent_return` 使用独立子任务结果卡。父助手最终回复后到达的协作记录保持在回复之后，不抢占父回复的结束操作，不创建隐式运行中的业务过程。阶段通知没有回答或撤销问题控件。
- `subagent_return` 的持久来源身份必需包含 `child_segment_generation` 和 `child_root_action_id`，与物理子会话、任务及来源序号共同标识原结果。界面不能将不同代次的相同序号视为同一来源；同一父事件的身份变更必须拒绝。该来源身份不把结果转换为需要主会话回答的问题，也不修改统一 User 信封的传递角色。
- `conversation-collaboration-navigation.ts` 仅使用宿主提供的直接会话列表和子任务导航快照；没有精确路由时按钮禁用。ChatArea 显式传入这些路由，不由消息正文推测参与者。
- 问题撤销携带精确 `question_id` 与 `source.root_session_id`，并沿现有用户撤销服务取得可靠回执后刷新绑定窗口。单卡重复点击受同步守卫保护，失败显示提示并允许重试。当前窗口的最新问题快照控制历史卡片的撤销可用性；服务仍须在实际变更时重新验证权威状态。此视图集合不是全局问题状态表。
- 已取得界面投影、实际组件挂载与控件回调的验证；这些结果不代替后台启动、跨会话授权、可靠重投递、所有子代理面板及真实供应商协议的端到端验收。
- 新增任务意图、接纳/来源确认和方向效果事件沿同一独立框体展示为“代理任务消息”，显示投递状态，不显示成人类输入或子任务最终结果。效果回执没有参与者快照，卡片不从投递 ID 推断导航地址。该事件原生分支已补类型与渲染验证；最终任务回流卡片仍随任务生命周期继续完善。
- 排队消息增加 `Claimed` 效果，记录稳定执行 ID、独立回合和输入锚点，界面显示“任务已认领”。该状态仅证明可靠认领，不证明供应商请求已启动，更不表示业务完成；任务最终结果仍须独立关联。
- 代理任务准备沿用该规范输入，使用独立启动来源及业务请求用途；不得再产生人类输入记录，不执行正文中的人类手动注入命令。最终助手回复仍属于该代理业务任务的结束回复，需按原投递和执行身份回流。
- 排队发送在目标可靠接纳后安排非阻塞唤醒；发送返回不等待目标模型结束。来源确认失败与目标是否已开始是两个独立事实，重试仍查询原投递，不创建第二份任务。终态结果已可回传来源并内部确认；开放原来源回合的正常下一请求已接入完整分块投影。末响应继续调度、完整恢复与应用前失败效果回流仍须完成。
- `task_result_projected` 仅展示“任务结果已加入上下文”，其凭据逐块关联实际 User 输入，并与输入共享原子修订。不重新显示最终正文，不提供回答或问题撤销控件。已结束回合的结果保留历史接纳，不创建虚假的投影或新任务。
- 已接纳但尚未进入普通业务请求的方向与结果使用原回合续跑锚点；该锚点不是新的任务消息，也不是需要模型确认的问答事务。宿主 `AgentContinuation` 准备不添加人类提示词或用户回合边界，不改变已经持久化的原消息身份。末响应完成判断与终态分发的实施验证见生命周期设计 9.17 和工作报告。
- 认领后首次准备失败保留原 Claim 回执，另行记录精确业务闭合，不将历史认领改写为“从未开始”。业务失败结束当前回合内的问题处理尝试，但不伪造问题答案或撤销；允许原问题保持未回答。首次业务请求之前收到的问题在该请求边界投影，不抢先开启专门答疑 API。具体失败结果的来源回流仍必须沿任务结果链完成。
