# 会话元数据版本迁移

## 权威与入口

本契约归属于 `vulcan-session-core::v1::config::MetadataDocument` 与工作区存储层，修改其中任何持久字段、嵌套字段或迁移步骤时必须同步本文及回归测试。

- 当前版本只在 `METADATA_SCHEMA_VERSION` 定义；元数据家族仍为 `vulcan.session.v1`。
- 唯一自动读取入口：`session_v1::documents::read_metadata`。
- 迁移实现：`session_v1::metadata_migration`。
- 普通发布仍经 `write_json_document`；精确 `metadata.json` 写入与迁移共用 `metadata.write.lock`。
- 元数据版本与 `runtime.json`、`compactions.json` 的版本独立，不一起递增。

## 首个迁移：1 → 2

旧版本 1 曾在不修改版本号的情况下新增 `business_hook.binding.observes_user`。此次显式登记这两种已知结构：

1. 无绑定，或绑定中已有合法布尔字段：保留内容，升级版本。
2. 绑定中缺少该字段：按照绑定的会话、代次、回合与起始序号，读取分片表声明的唯一分片。根据起始事件确认用户输入、目标续跑、子任务返回或代理任务来源。代理任务为 `false`，用户业务来源为 `true`。

不会根据正文、协议 `user` 角色或当前是否运行来推测用户身份。找不到绑定的原始事件、归属不匹配、分片路径不合法时拒绝迁移。不会清空绑定或新建用户回合。

这一步不承诺修复版本 1 的任意更早开发格式。例如缺失整个协作域、未知字段、其他必填字段缺失，需要另行定义可验证的迁移，不能批量填默认值。

## 第二个迁移：2 → 3

新增必填的 `config.html_answers`，统一保存期望开关、偏好修订号和最近请求准备快照。
旧会话迁移为默认关闭、修订号零、准备快照为空，不注入关闭提示，不改写其他设置或历史事件。
版本 3 缺失该对象或其必填成员属于损坏；拒绝无来源的新默认值。版本 2 已含该未来字段也拒绝迁移，
避免把未知写入当成合法旧偏好。修订号必须可由 JavaScript 精确表示，准备修订不得领先期望修订，
相同修订下的开关值必须相同。

版本 1 的 Hook 来源校验只读取其当时已存在的精确来源字段，再进入后续步骤；全部步骤结束后统一按
当前完整类型校验，避免早期迁移意外要求后续版本才存在的字段。未知字段仍由最终强类型解析拒绝。

## 第三个迁移：3 → 4

HTML 回答子系统移除，`config.html_answers` 改为 `config.answer_mode`：`mode` 为会话回答模式
（`standard` 或 `interactive`，新会话开始时从全局默认值复制，之后不随全局设置变化），`revision`
与 `prepared` 语义不变。版本 2 → 3 的默认结构在迁移代码中冻结为字面量，不再依赖已删除的类型。

1. `enabled = true` 变为 `interactive`，`enabled = false` 变为 `standard`。
2. 修订号原样保留；准备快照的 `enabled` 按同一规则映射，修订号不变。

版本 3 缺失旧对象、旧对象成员不合法，或已含 `answer_mode` 时拒绝迁移。动态上下文生产者键仍为
`dynamic.html_answers`（常量 `ANSWER_MODE_CONTEXT_KEY`），已有历史中的旧指引在下次准备时被新指引替换。

## 发布与失败语义

1. 先读取并校验家族和版本；当前版本仅强类型读取，不写入、不创建备份。
2. 旧版本取得文件发布锁后重新读取，避免使用锁外的过期快照。
3. 在独立内存候选中按版本顺序转换，并通过当前强类型解析及本次新增字段所需的来源校验。
4. 原始字节保存到同目录 `metadata.schema-<旧版本>.backup.json`。相同备份可复用；不同备份明确报错，禁止覆盖恢复点。
5. 通过既有暂存文件、刷盘和原子替换机制发布新元数据；不改变会话修订、时间、配置或事件文件。
6. 任一步失败不继续发布。损坏 JSON、未知未来版本不能被当成空会话或自动降级。

发布锁是协作式锁，进程退出会自动释放；锁文件本身永久保留，不能因“看起来为空”而删除。旧程序不认识新版本，更新后不要同时运行旧程序写同一存储目录。备份含会话元数据，应按原会话隐私边界保存，不上传仓库。

显式供应商能力重建可以先替换其授权的能力子树，再复用同一迁移引擎；验证通过后保留原字节备份，后续仍由原重建流程发布。自动升级本身不改变用户的能力配置。

正常加载仍负责完整会话、运行时及协作状态校验；元数据迁移不宣称整个历史已通过加载，也不修复与本次模式演进无关的历史损坏。

## 后续新增字段的固定步骤

**发布阶段门槛（`AGENTS.md` 第一节第 12 条）：** V0.1.x 期间新增或修改字段只执行第 1 步并递增版本，
不新增迁移步骤、不写备份；旧版本会话在读取时明确拒绝，不补默认值。以下第 2–7 步自 V0.2 正式发布起适用。
已存在的 1 → 4 迁移步骤是该规则之前的遗留，不再扩展。

1. 修改强类型模型，将当前元数据版本递增一位，禁止只增加必填字段却继续写旧版本。
2. 在 `upgrade` 的版本分派中新增 `migrate_vN_to_vN_plus_1`；保留既有步骤，确保较老数据可以逐步升级。
3. 明确每个新字段的旧值来源。纯展示默认值可以在迁移步骤中明确定义；执行归属、授权、用户观察策略必须根据原始事实转换。
4. 迁移函数只转换内存候选。文件锁、备份和原子发布继续由统一入口负责，不在其他读取点散落修复逻辑。
5. 已升级版本缺字段属于损坏，不能再次套用旧版本迁移或添加全局反序列化默认值来掩盖。
6. 增加旧形状到新形状、重复读取、未来版本拒绝、无关字段保留、备份冲突、写入故障、并发首次读取及正常业务读取入口的测试。
7. 若步骤依赖事件回放中的来源定义，回放来源规则变化时必须重新核对迁移证据；不可把文档转录当作第二权威。

## 定向验证

```powershell
rtk cargo test -p vulcan-workspace-store metadata_migration --lib -- --test-threads=1
rtk cargo test -p vulcan-workspace-store workspace_store::session_v1::tests --lib -- --test-threads=1 --skip performance_
rtk cargo check -p vulcan-workspace-store --all-targets
```

另有默认忽略的 `metadata_migration_external_session_copy`：将环境变量 `VULCAN_METADATA_MIGRATION_FIXTURE` 指向待验证的会话目录，再单独执行该测试并传入 `--ignored`。测试把整个目录复制到临时目录，只升级副本，并验证完整加载及源元数据字节保持不变。夹具应来自静止的快照；真实会话内容不写入仓库。大规模性能测试独立执行，不混入迁移正确性验收。

新代码须编译并由新 Core 载入后，旧文件的第一次读取才会执行升级。仅修改源代码不会让已运行旧 Core 自动获得新读取逻辑。
